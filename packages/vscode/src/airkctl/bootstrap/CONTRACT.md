# Explicit service bootstrap

An absence notification offers automatic installation, manual instructions and defer. Activation and absence detection do not download or execute payloads. Manual/defer make no network request. Unknown, stopped, damaged, incompatible or unverified installations are recovery states and refuse fresh installation. Workspace trust, user native-execution permission, supported local OS/architecture and no active setup are checked before discovery and immediately before execution.

Automatic choice discovers the official iokaio/airk release, checks compatible version/channel/target and its bounded installer metadata, and reviews version, target, default locations, skipped trust and predecessor-reset refusal before downloading executable bytes. Only a private verified installer can execute. The host checks its hash and platform signature again immediately before exact --silent, with closed stdin and no shell. Failure/cancellation reports recovery paths; process exit zero still requires fresh verified I4 discovery and native readiness. No PATH executable discovery, elevated prompt, hidden reset acknowledgement or automatic trust is added.

Controller tests prove decision ordering and refusal/cancellation handling. Actual host download/signature/process and installed journeys remain separate qualification requirements.

Explicit Not now persists a user-scoped deferral; setup remains discoverable. Once an installer is launched, a user-scoped pending marker prevents automatic replay after unknown/failing outcomes. Clearing it requires installer exit zero, the fresh verified I4 candidate identity, the generated native setup-receipt summary with matching installation/operation IDs and closed successful status, and readiness. The full Core receipt remains opaque to TypeScript. These editor preferences are not native installation authority. Cancellation after admission never kills the native installer; bounded observation may report unknown while the native operation continues. Manual recovery remains available.

Network requests follow at most four redirects, with HTTPS only, no URL credentials and exact official GitHub repository paths or approved GitHub release-asset CDN path prefixes. Three pages of at most twenty releases bound discovery. Metadata, manifests, executable bytes and process output have separate bounds. Failed partial downloads are removed only if their originally created file identity is still present; recovery folders and process evidence remain.

## Publisher provenance

Every automatic installer also requires a cryptographically verified Sigstore v0.3 DSSE SLSA v1 attestation for its exact asset name/hash. The pinned Apache-2.0 verifier 3.1.1 and pure JavaScript SnappyJS 0.7.0 are bundled with complete licenses; no GitHub CLI/Python/native addon is shipped. The static public-good trust root is exported through `gh attestation trusted-root` TUF verification at build preparation, embedded and source sealed. Runtime root downloads are forbidden. Verification requires certificate chain, SCT, Rekor and authenticated timestamp thresholds of one; GitHub private release-attestation roots without those logs are not accepted by this profile.

The signed issuer must be token.actions.githubusercontent.com and the signer workflow iokaio/airk/.github/workflows/github-release.yml at the approved main or feat/advanced-split ref. Certificate OIDs and the signed SLSA body independently bind GitHub-hosted runner, immutable repository ID 1418150478/owner 152147161, source commit and release run/attempt. The selected statement subject binds the installer bytes. Public GitHub attestations are fetched from the exact repository API with five-candidate and 2 MiB bounds; current compressed storage is restricted to tmaproduction.blob.core.windows.net/attestations/1418150478/... and decoded with a 2 MiB maximum. Unexpected storage or policy changes refuse to the manual path.

The separate public GitHub CLI fixture proves the real cryptographic library/roots and wrong-publisher refusal, not AIRK release qualification. A new AIRK published-byte installed journey must supply its actual matching attestation. See [GitHub's attestation identity requirements](https://docs.github.com/en/rest/orgs/attestations), [Sigstore verifier](https://github.com/sigstore/sigstore-js/tree/main/packages/verify) and the patched [3.1.1 advisory](https://github.com/sigstore/sigstore-js/security/advisories/GHSA-xgjw-pm74-86q4).

Mac automatic bootstrap additionally requires built-in `/usr/sbin/spctl --assess --type open --context context:primary-signature` to report a notarized Developer ID image before mounting or launching it. C10 codesign verification still binds AIRK's team. No Xcode tools are required and a local policy override without the notarized-source result does not qualify. See [Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/) and [Apple notarization assessment](https://developer.apple.com/videos/play/wwdc2019/703/).

## Publication /3 opaque binding

Historical publication /2 validation retains its complete roster and headless semantics. /3 adds only the exact opaque Rust-emitted optional publication projection bound into the existing release.js bundle. TypeScript does not decode Profile or reimplement native publication policy. It compares the entire projection with the sealed build input, adds exactly its part basename/SHA entries, and validates the unchanged complete /2 base inventory. Hypothetical owner injection is a pure test seam; the application uses only its compiled binding.

The owning Node build binds publication_catalog.json, exact compiled native catalog bytes, version and release parser source into the release bundle. Missing production capture is allowed for development output and makes /3 automatic offers unavailable; manual/defer continue. Final packaging invokes --verify-release-stdin on already captured bytes and requires the actual native production projection for this version/catalog. It never substitutes an evaluation or hypothetical capture. Both release and provenance verification compare exact deterministic source compilation and reject added executable/static/dynamic import code; source labels alone are insufficient. Native model qualification and actual released-byte installation remain separate required evidence.
