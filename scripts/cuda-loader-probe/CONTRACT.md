# Bounded CUDA loader diagnosis

This developer diagnostic follows the failed original Compact17 R1 process40388,
exit101, Windows loader error1114. It does not execute a model, cuInit, an ORT API,
provider factory, session, tensor or scoring operation. The exact failed receipt,
retained runtime census and manifest order are immutable input. Preparation and
execution reopen the original native result/stdout SHA pins, exact1114 error,
zero score rows and empty journal, plus actual natural101 retained PID/HANDLE/Job
settlement. The original missing-empty-journal final-proof error stays a failure;
it is never erased or relabeled as success. It neither
supplies ProviderHost nor calls Provider_SetHost. No runtime DLL is rewritten.

The maintained component owner supplies the reviewed read-only identity/output
guard, token-owner observation and suspended Job readback. Its unchanged NN0
helper supplies source hashing and the retained process/Job/HANDLE owner. No new
process-control framework is introduced. Parent and Python worker retain the
human user/default-owner token. One original120s phase, process16GiB, Job24GiB,
log64MiB and five-second cleanup apply unchanged. All writes are create-new in a
checked protected private campaign child; Python uses -B -S, with run-owned temp.
No model or training input is needed or sealed by this diagnostic.

Preparation takes --component-receipt, its --component-receipt-sha256, fresh
--output-root and --plan, plus --prepare and --approved-script-sha256. It creates
only the reviewed plan. Root reviews that plan before a separate
--execute-reviewed-probe with --plan, --plan-sha256 and the script SHA. Internal
--worker is launched only by the reviewed owned parent. It does not constitute a
standalone admission or qualification entry point.

The worker authenticates the retained complete runtime roster and loads native
System32 nvcuda first, followed by every literal manifest module in original
order. It uses the native owner's process default DLL search flags
APPLICATION_DIR|SYSTEM32 and per-load DLL_LOAD_DIR|SYSTEM32. Python's application
directory differs from the native AIRK image directory: this is a diagnostic
observation of explicit DLL loads, not proof of native application's complete
module baseline or service admission. No DLL search, PATH or host policy is
relaxed to hide a load failure. Relevant ambient AIRK/ORT/Python/CUDA/cuDNN
variables are cleared as in the original component parent.

Every attempt and result is flushed before another load. Before CUDA provider
load the already-loaded shared provider's exported Provider_GetHost is observed
and its raw null/non-null value retained. The pointer is never fabricated or
used as a vtable. The loaded handles remain mapped through worker process exit;
no explicit module-unload settlement is claimed. The parent proves actual natural
process/Job/HANDLE settlement separately.

A first failed LoadLibraryExW stops immediately and reports exact module,
Win32 last error and the attempted/loaded prefix. A successful observation of
such failure has a normal worker exit and diagnostic_complete=true with
outcome=load_failed. This means the diagnostic captured the failure; it is never
a loader success, component pass, activation or qualification. Unexpected worker
exceptions, unknown/forced settlement, source/output drift, incomplete events or
expired original clock make diagnostic_complete=false. loaded_all similarly
means only those DLL calls returned handles in that Python process.

The parent independently validates exact ordered attempt/result events, optional
host observation at the required position, terminal prefix counts, actual worker
PID/SID/default-owner and original manifest. It retains the entire log, original
input hashes, exact command, UTC start/finish, original deadline and process/Job
peaks. Every execution-phase guard is bounded by the remaining original cutoff, including
its subprocess timeout and a post-return clock check. The sealed protected-policy
helper's two subprocess.run calls are similarly bounded through a temporary
module-local proxy, restored even on failure. Shared subprocess.run and retained
helper bytes remain unchanged; its pwsh lookup must match the sealed executable. The receipt path is audited
before the final clock. Final UTC precedes final monotonic time; the explicit
timing_scope excludes subsequent create-new receipt serialization/fsync and its
postwrite owner audit. No extra prewrite guard occurs after that clock. Retention
failure preserves an active original exception with diagnostic notes; without an
original exception it raises normally. Missing final proof cannot become a pass. Source and
runtime hashes are checked after failure as well as success; original primary
failure survives subsequent retention errors.

Tests use independent literal events and injected loader results only. Actual
module initialization still requires root review and a separate owned execution.
