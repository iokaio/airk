# Upstream projection contract

Inputs are two SHA-pinned source inventories, the maintained ORT 1.30 lock and its sealed source inventory, and the distinct retained ORT 1.22.1 build/dependency receipts and Git tree. The tool must not equate these versions. It compares source path, byte length and SHA-256, or explicitly declared CRLF-to-LF Git blob identity. ZIP archives and the exact locked protobuf v33.6 TAR.GZ release are SHA/size verified before bounded member reads; no extraction or candidate execution is permitted. A mismatch never becomes an upstream exclusion.

The projection is over retained per-file observations. Final reconciliation independently rehashes live candidate files and evidence. Each disposition links to its exact projection binding and upstream path/revision, with original representation explicit. Proof and map files must remain at most 16 MiB each; larger groups split before output. A proof cannot authorize builds, imports, deletion, publication, model execution, or current caller claims.

The projector writes stdout only. The separate materializer authenticates the entire bundle, checks the current human identity/default owner, restricts paths to a fresh repository-artifacts destination, guards every created directory/file, uses create-new writes, and audits outputs before consumption. Failure retains partial evidence without claiming completion. Existing files are never overwritten. Private receipt outputs are not staged; maintained code and these instructions are.

Every bundle kind, including the legacy Git tree and unresolved summary, receives the same 16 MiB output cap. Archive parsing consumes captured bytes whose SHA and size match the declared archive, and the materializer parses only its bounded authenticated memory snapshot. Filename rechecks alone are insufficient proof of consumed bytes. Conflicting optional normalized Git identities refuse, as do conflicting raw identities.

Patch diagnostics bind the source helper pins, input index, separate upstream revisions, captured archive members, ordered upstream patch pins and final live source hashes. Exact old context, old/new counts and target positions are required; no fuzz, path changes, orphan operations or duplicate file sections are admitted. Unsupported patch syntax remains a refusal and cannot become an upstream disposition. The diagnostic does not prove which historical commands ran, and emits stdout only.

Observed-source recovery is separate from upstream patch interpretation. airk.exact-byte-recovery/1 stores ordered base offsets, deletion lengths and hashes, inserted bytes in canonical base64, and complete base/target SHA-256 and sizes. Recovery requires exact identities and bounds, never fuzzy matching. Capture deduplicates identical records, refuses an entire-target insertion, limits each actual input to 1 MiB, preserves upstream notices, and verifies all roundtrips before emission. airk.observed-source-recovery/1 binds each original source to its archive/member, record, notices and helper code. This preserves observed changes without asserting AIRK authorship or historical execution; it does not change build selection. Materialization accepts only a bounded authenticated capture and a fixed fresh maintained destination, with guarded create-only writes and owner audits.

Generated-build role diagnostics require each candidate to lie under an exact retained configure -B output root, with the configure receipt and generator identity recorded. Positive content evidence is an explicit producer marker or the complete literal skeleton of a CMake template with named substitutions. Template comparison uses ordered linear literal searches, bounded to 1 MiB and 256 literal segments, never wildcard-regex backtracking. Source hashes/sizes are verified and all consumed evidence is rehashed. These observations establish only a build-output role: exact historical bytes, absence of later edits, full-directory coverage and qualification remain unproved. Unmarked or unsupported files remain unresolved.
