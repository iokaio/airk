# Fresh CUDA graph metadata

The fresh route consumes an actual environment/6 chain and its preserved native
Inference image. It uses the existing graph diagnostic selector and Job owner.
The private result records graph metadata without creating product approval.
The frozen producer and historical graph launcher keep their existing identities.

Use the verified Windows human execution path. The reviewed bootstrap JSON
contains exactly four SHA-256 strings. Keys and source paths are fixed.

| Key | Maintained source |
|---|---|
| component | scripts/cuda-component-execution.py |
| lease | scripts/cuda-component-execution/graph_provenance.py |
| preserver | scripts/preserve-cuda-test-images.py |
| native | scripts/cuda-native-execution.py |

Each invocation also takes the reviewed SHA-256 of fresh_graph.py and this
contract. The native metadata parent receipt identifies the exact maintained R8
output-policy source and lock. Its original six-file output roster, the actual
manifest and model source pins, and the fresh image packet are required.

```text
python -B -S scripts/cuda-component-execution/fresh_graph.py --prepare-graph-provenance
  --approved-script-sha256 SHA --fresh-contract-sha256 SHA
  --approved-sources PATH --approved-sources-sha256 SHA
  --metadata-receipt PATH --metadata-receipt-sha256 SHA
  --image-packet PATH --image-packet-sha256 SHA --powershell ABSOLUTE_PATH
  --output-root FRESH_EXECUTION_ROOT --graph-preparation FRESH_PREPARATION_RECEIPT

python -B -S scripts/cuda-component-execution/fresh_graph.py --prepare-graph-diagnostic
  --approved-script-sha256 SHA --fresh-contract-sha256 SHA
  --approved-sources PATH --approved-sources-sha256 SHA
  --graph-preparation REVIEWED_RECEIPT --graph-preparation-sha256 SHA --plan FRESH_PLAN

python -B -S scripts/cuda-component-execution/fresh_graph.py --execute-reviewed-graph-diagnostic
  --approved-script-sha256 SHA --fresh-contract-sha256 SHA
  --approved-sources PATH --approved-sources-sha256 SHA
  --plan REVIEWED_PLAN --plan-sha256 SHA
```

The first command performs the full fresh verifier within 600 seconds of its
original start, clipped to the campaign end. The second checks the independently
reviewed preparation and prepares the exact graph plan within 120 seconds.
The third verifies the reviewed plan and reopens the held current boundary
within the same 120 seconds used by the native selector and final observations.
Its owned process and Job limits remain 16 and 24 GiB. The existing five-second
cleanup, 16 MiB native output and 64 MiB log limits apply. The output guards are
the same checked Windows guards used by the existing component owner.
A successful fresh execution retains execution.json in the reviewed output root.

The preparation records the current sealed files, bytes, Windows identities and
ACLs. It verifies the full source, compile and archive lineage before that record
can pass. The held execution boundary reopens the fresh configure, compile and
aggregate documents, the original configure stage receipt and its captured process
evidence, source and graph pins, session
and aggregate archives, provider identities, native metadata and image,
model/fixture inputs and exact verifier sources. It replays those relationships
and actual Cargo static link and executable exports through the retained handles.
Rechecking the current boundary does not perform a second full compiler input
and static archive reconstruction in the native phase.

The focused controls run with
`python -B -S scripts/tests/test_cuda_fresh_graph.py`. They use inert documents
and injected handles and do not launch Cargo or GPU binaries. Actual readiness
requires measuring this exact preparation and held boundary at the required
limits. An expired preparation cannot authorize a native dispatch.
