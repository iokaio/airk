# Service worker ownership and durable jobs, protocol 1

This is an implemented storage contract for the opt-in 1.4 service work. The default 1.3.2 scheduler and collection format remain active until cutover. Native management is available through `airk service rpc --runtime-dir <private-directory> --request-file <json>`. The file contains a protocol-1 `ControlMethod`, with a maximum of 64 KiB. The metadata actor has 32 queue slots; overload is explicit. Health uses an independent cached observation and remains available while the ledger is locked or unavailable. The [supervised project runtime](service-protocol.md) now executes index/reconcile, explicit bundled `model_setup`, vectors and verification jobs under process-lifetime leases. Replacement rebuilds now use the [owned sibling/manifest publication contract](service-publication.md).

The native adapter first establishes a private same-user runtime directory. The service registry uses a separate owned SQLite ledger with a 32 MiB ceiling and a bounded rollback journal. It never opens source or collection databases. Project registration is capped at 1,024 entries; pages contain at most 32 projects and 48 KiB, and continuation requires the same registry revision.

Registry initialization now has an OS-serialized, checksummed ownership receipt with separate initializing and ready states. Only a proven unfinished first initialization can resume an empty database. Once ready, a missing/empty database or missing required table is preserved and refused; startup cannot recreate request aliases or fencing metadata under the old namespace. Earlier development ownership receipts upgrade only alongside a complete matching database. Restoring the original owned state preserves its namespace and accepted keys.

A worker must acquire its project's process-lifetime OS lock before the registry increments its fencing generation. That handle survives for all work under the generation. A replacement cannot acquire it while the old process survives. Completion requires both the current lock-bearing lease and the generation saved with the running job. A service restart does not permit bypassing a surviving worker's lock.

`model_setup` provisions the bundled offline model into the private global store and preserves an explicit custom collection selection. It records an independent success/failure receipt and does not publish source evidence. Source jobs never perform model installation; a durable continuation requests the next source pass to apply the installed model reference. Trusted custom-model setup integration remains cutover work.

Jobs have `pending`, `running`, `succeeded`, `failed` and `canceled` states. Acceptance atomically saves the job and its request receipt before responding. Keys contain the retained registry namespace, request epoch, caller identity and random nonce. Repeating an accepted key returns its current receipt; changing its project or kind conflicts. Matching pending work can be joined. Changes arriving during a running pass form later work. One project can claim only one running job.

The ledger retains at most 1,024 jobs and 4,096 request aliases. At capacity it retires up to 64 oldest terminal jobs, cascades their aliases and advances the request epoch in the same transaction. Unknown old keys expire explicitly instead of repeating a mutation. Known keys remain readable even at capacity. A new request rejected before acceptance can fetch the current epoch and use a fresh key. Active work is never evicted to create space. [Explicit retry](service-events.md) binds a new request to an original failed/canceled job, preserves its receipt and resets the applicable finite automatic retry policy only once. Retention protects that original during acceptance.

A [bounded transactional event log](service-events.md) retains content-free project/job observations independently of terminal receipt rotation, with snapshot paging, restart identity and explicit retention gaps.

Recovery acts only on running jobs from older generations. Reconciliation can retry up to three attempts; a matching durable manifest receipt settles an interrupted rebuild at its exact committed token. Without that receipt, an interrupted rebuild or exhausted job receives a content-free failure and needs explicit recovery planning. Calling recovery again under the current live lease cannot requeue its active job. Pause prevents new source/maintenance claims and survives restart; explicit read-only [inspection](service-inspection.md) may use an idle paused project's execution slot while its other work stays paused. Queued cancellation is durable; running cancellation persists intent and requires the fenced worker’s safe-boundary acknowledgement before recording completion or releasing resources.

`airk-store` tests cover restart persistence, exclusive lock handoff, monotonically increasing generations, stale completion, live-worker recovery, joining versus later work, conflicting keys, capacity, retention expiry, pause, and interrupted maintenance. These tests establish ledger behavior; they do not establish process supervision, publication safety, service-wide fairness or installed-platform qualification.

Registration requires existing canonical source and data directories, a validated collection ID and a digest binding all three. The kernel rejects data storage that contains sources. The registry rejects a second source root claiming the same data-root/collection destination. Source bytes and collection state are not opened by management operations. Windows and non-root Linux native process tests exercise these checks, registry contention, receipt persistence and unchanged source bytes.

Source locations must now be disjoint from every registered data root, the control namespace and verified installer-owned state/install directories, including in either ancestor direction. Shared data roots with different collection IDs remain supported. Registration and fenced additional-root updates validate the same bounded registry snapshot in an immediate transaction, so competing updates cannot both accept an unsafe overlap. Failed root observations retain their last known roots for this protection. Before index/reconcile/rebuild captures any source, the project owner validates its current root configuration against this ledger; a conflicting direct configuration change settles as `protected_source_boundary`, preserving the committed revision and originals.

Installer-private directories are adopted only when the bounded state ownership receipt and install layout agree on canonical install/state/channel identity. Previously proven private paths remain protected in the service ledger if a receipt later disappears. Raw development namespaces protect their control root without treating an arbitrary parent directory as private state. Windows comparisons use the OS's Unicode ordinal case rules, conservatively refusing case aliases; see [CompareStringOrdinal](https://learn.microsoft.com/en-us/windows/win32/api/stringapiset/nf-stringapiset-comparestringordinal). Directory availability and canonical identity checks remain the native/kernel adapter's responsibility. The registry reads only its own and installer ownership metadata.

The resource scheduler now issues an exact job-bound work grant before a worker may claim pending work. Stable pending-project cursor pages rotate across the full registry. Running cancellation uses a durable separate intent and settles only when the fenced worker acknowledges a safe boundary; `cancel_pending` remains queued-only, while `cancel` handles either state. Pause/resume is sent as generation/grant-scoped control for already running jobs. See [resource admission](service-resources.md).

Captured publication recovery is now admitted as a `recover` job. A project owner can start without replaying its publication on the activation handshake; failed captured recovery does not silently discard its journal or prevent explicit rebuild diagnosis. Recovery always selects the manifest's current slot, including after the initial slot has been retired.

Each successful operation attempts one bounded owned-retirement pass. Its separate cached `maintenance` observation records remaining incarnations, removed-file count, failure and observation time. Failure to retire old state does not turn an already committed rebuild into failure. Deferred retirement produces service-issued `maintain` jobs with persisted exponential backoff: at most seven deferred passes or three failed passes until a clean observation resets the allowance. Automatic acceptance and retry debit commit atomically; replaying the same accepted key consumes no extra attempt. Paused projects and already queued/running work consume no new retry attempts. Explicit cancellation of maintenance suppresses its automatic follow-up requests. Failed/exhausted retirement preserves its state and capacity for diagnosis and explicit retry. These jobs never delete unknown files or sources.

The `maintenance` control read uses only the bounded service ledger, including for closed projects; it reports cached observation time and whether automatic retry remains eligible. Service health remains independent of this read and every collection database. Native regression coverage holds an old request through replacement, observes deferred retirement, releases it, and waits for a service-granted automatic pass to finish. The durable backoff test covers restart, pause, queued work, cancellation and exhaustion. Detailed recovery receipts, full console presentation and the rest of the maintenance fault matrix remain integration work.

The `progress` metadata read now returns a bounded [fenced work snapshot](service-progress.md), separately from the latest durable job receipt. Actual retained-artifact, preparation, commit and verification boundaries advance counters; phase changes and heartbeat observations do not. Snapshots preserve unknown totals, retain their worker generation across restart, and freeze terminal timing. The worker excludes explicit pauses from its ten-minute no-progress deadline, requests safe-boundary cancellation, and exits after thirty more seconds if native work cannot drain.

## Independent source and semantic phases

The native service now uses source-only index/reconcile passes and source-only replacement builds. They publish lexical evidence, facts and authenticated pending semantic inputs without connecting to the inference helper. Source success names that publication; later helper failure has a separate vector-job receipt. Explicit legacy library indexing keeps its existing synchronous behavior until the adapter cutover.

A vector turn advances at most one 32-artifact batch with a 30-second soft budget checked at publication boundaries. Native helper request and input budgets still apply; this is not a hard publication-time limit. Success with remaining work requests another turn, returning resource admission between turns. It reads retained inputs and can finish while the original source root is offline. Failure stops automatic continuation until explicit retry. Cancel stops the current chain at a safe boundary; project pause preserves pending work and prevents further claims.

The existing 32 MiB registry now also retains one bounded continuation row per registered project, with independent source and semantic flags and a monotonic revision. These flags are outside the 1,024-job public queue. A worker saves the next phase under its fencing lease before acknowledging the current job. The supervisor selects bounded pages, prefers a requested source pass and atomically accepts a job plus clears only the observed flag. Queue saturation, stale revisions, other accepted project work, pause and request-epoch rotation leave unaccepted intent intact. There is no extension-owned continuation timer. Recovering a proven replacement-switch receipt also saves its semantic continuation in the same transaction, exactly once. Ordinary interrupted jobs retain their existing three-attempt recovery bound.

Trusted `model_setup` success requests a later source pass through the same ledger. Model setup does not publish source evidence itself. Source failures preserve independent older semantic work; a failed/canceled semantic phase requires explicit retry. Retired receipts do not discard unaccepted phase flags.

Native `embedding_status` reports the current opaque embedding-worker identity. Trusted `stop_embedding` requires that exact identity, optionally with `force: true`; the supervisor stops only its actual owned child and confirms native drain before success. A foreign/stale identity is rejected. Uncertain completion is reported explicitly, and project lexical retrieval and service health remain independent. Existing model sessions become unavailable after stopping; helper/worker restart controls are a separate lifecycle integration task. This management action is not an MCP tool.

Cancellation is rechecked in the final receipt transaction, including repair-plan cancellation. If it arrives after an atomic source/batch publication but before acknowledgement, that successful publication remains committed and its next-phase flag is cleared atomically. A later independent source request remains intact.
