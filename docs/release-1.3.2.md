# AIRK 1.3.2

This patch fixes missing progressive publications for initialized empty indexes and clarifies source indexing progress in the dashboard. It retains the 1.3.1 independent collection workers and bundled offline model. See [1.3.1](release-1.3.1.md) for those changes.

## Empty-index indexing progress

Version 1.3.2 fixes a gap in progressive source indexing: an initialized empty current index previously bypassed batching, and a queued full rebuild disabled it too. Such scans could prepare an entire corpus before their first committed-file observation, exposing them to the editor's ten-minute no-progress watchdog. Empty indexes now use bounded progressive publications, including when their model/detail configuration changes or a full rebuild is requested. The first batch targets 32 changed files; the final publication does not rewrite completed batches. Populated full or configuration-changing rebuilds retain their existing atomic publication boundary. This does not establish the cause of every long publication or qualify a recovery time bound for an already interrupted journal.

The dashboard places elapsed time and committed/processed counts beside indexing controls, adds a working indicator, identifies cached semantic readiness during a source scan, and describes source indexing before vector work. Native, extension and lockfile versions are synchronized at 1.3.2. Publication status is established by the release workflows. The reported Windows two-project setup passed manual acceptance with the local 1.3.2 VSIX; hosted qualification is recorded separately.

Before the version bump, local Windows validation on 2026-10-22 passed two new empty-index regressions covering ordinary indexing, full rebuilds, detail/model changes, semantic completion, zero-file discovery and repeated empty no-ops. The updated kernel unit suite (excluding the large-catalog measurement already covered by the baseline), ten scheduler integration tests and seventeen current-runtime tests passed; the existing runtime capacity qualification remained ignored. The complete workspace baseline passed earlier in the session, before the native follow-up edits; it is not a final-source full-workspace receipt. Extension validation passed 143 tests with six skips, Python contracts passed 124 tests with four skips, and final Clippy, formatting, repository/link and whitespace checks passed. The release executable's CLI smoke initialized an empty collection, requested a scheduled full rebuild and observed 32 files in the first publication, 35 at completion and exactly 35 changed artifacts. This establishes the small local regression, not recovery latency or acceptance on the reported collection.

## Upgrade and qualification

No additional format change or rebuild is required from 1.3.1. Existing interrupted publications still require journal recovery before indexing can continue; this fix does not establish a recovery time bound. Source files, collection IDs and saved settings are preserved.

The Windows x64 native helper and VSIX were rebuilt for 1.3.2 on 2026-10-22. The release CLI smoke verified the 1.3.2 identity, a 32-file first publication, 35 committed files at completion and 35 changed artifacts. The native ZIP and stable-channel VSIX passed the repository's package inventory, version and digest verification; they are unsigned local candidates and have not been published. The VSIX SHA-256 is `68e707aac29a076ba863c6812e11c9b1568f4c5d5b98d426d6aff38286e45292`.

Version-specific extension tests passed 143 tests with six skips; Python contracts ran 128 tests with four skips. The locked workspace build and complete 1.3.2 workspace test suite, including doctests, passed. This includes all 200 kernel integration tests, 157 store unit tests and the new empty-index regressions; sixteen existing native tests remained ignored. All-target workspace Clippy with warnings denied, formatting, repository/link checks and whitespace checks passed. On 2026-10-22, the reporter confirmed that installing the 1.3.2 Windows x64 VSIX resolved the indexing issue in the reported two-project VS Code setup. This is one manual acceptance observation, not a general performance or cross-platform qualification. Hosted CI and release workflow records remain authoritative for those checks and publication.
