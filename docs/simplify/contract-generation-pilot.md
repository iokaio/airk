# Contract-generation pilot (S1.2 golden capture and S1.3)

**Status:** Milestone S1 record, 9 November 2026. This page supports decision
D5 in the [simplification plan](../simplify-plan.md#9-decisions-for-the-user).
It records evidence; it does not adopt a generator. No wire shape, digest input
or persisted format changed (D8).

## What was built

| Artifact | Purpose |
|---|---|
| [`fixtures/wire/catalog_receipt.json`](../../fixtures/wire/catalog_receipt.json) | The control operation. Holds exact bytes for `ControlRequest` (`catalog_receipt`), `ControlResponse::CatalogReceipt` (receipt present and `null`), and the persisted `CatalogReceipt` payload (`index_operation_receipts.payload`). Also holds the `catalog_operation_id` digest vector, 12 reviewed malformed inputs and one accepted variant. |
| [`fixtures/wire/read_retry_decisions.json`](../../fixtures/wire/read_retry_decisions.json) | The semantic rule. 32 reviewed decision cases for "may this combined read be repeated once?". It is generated by [`read_retry_decisions.py`](../../fixtures/wire/read_retry_decisions.py), which holds the expectations independently of either implementation. |
| `crates/airk-core/src/wire_fixture_tests.rs` | Compares the Rust serialization with the catalog fixture. Exact bytes (P9) for persisted and digested values. Rejection and variant cases. |
| `read_retry.rs` test `shared_decision_cases_match_reviewed_fixture` | Runs native `validated_retry` over every decision case. |
| `packages/vscode/src/test/wireFixtures.test.ts` | Runs the hand-written TypeScript `singleRequiredMemberRetry` over the same cases, plus the extension catalog-receipt validators over the native bytes. |

**Capture procedure:**

1. The observed catalog bytes were rendered by the Rust test on its first run.
2. They were reviewed: field order, `null` versus absent, and exact integers
   above 2^53.
3. The `operation_id` vectors were recomputed with an independent Python
   implementation of `AIRK-DIGEST-1` framing. Both matched.
4. Only then was the capture committed.

The test never rewrites its fixture. On a mismatch it writes the observation
to a temporary file and fails.

**Container builds:** all three container inputs list both fixtures
(`.dockerignore`, `Dockerfile` and `scripts/container-inputs.json`).
`scripts/tests/test_container_inputs.py` verifies this.

## Findings from the fixtures (current behavior)

Every case matches between Rust and TypeScript except the divergences below.
Each divergence is recorded in the fixture and asserted as it behaves today.
None is fixed in S1.

| # | Divergence | Native (Rust) | Extension (TypeScript) | Risk |
|---|---|---|---|---|
| W1 | `grant_revision` or `catalog_revision` above 2^53 | Accepted (`CatalogRevision` is 1..=i64::MAX) | Refused (`Number.isSafeInteger`) | Conservative: no replay, a refused receipt. Unreachable at realistic revision counts. |
| W2 | Request-key `epoch` above 2^53 | Exact | `JSON.parse` rounds it, so an echoed key names a different epoch | The rounded key would cross the request. Epochs are counters, so this is unreachable in practice. Still unguarded. |
| W3 | `retry_after_ms: 25.0` (an integral float) | Refused (`as_u64`) | Accepted as `25` until the follow-up. **Fixed after the S1 review:** `readRetry.ts` now refuses non-integer number literals in the native text via `JSON.parse` source-text access, and the fixture case is no longer a divergence | Was permissive: TypeScript could authorize a replay that native refuses. Native never emits `25.0`. |
| W4 | `catalog_receipt` response with the `receipt` field absent | Read as `null` (serde treats a missing `Option` field as `None`) | Refused (`response.receipt !== null` takes the receipt branch) | Conservative. Shows that "absent versus `null`" is not specified in one place. |

W3 was the only permissive gap. After the S1 review the user approved the
fix (s1-review §10). The refusal applies wherever native text is available:
each member's `content[0].text` and the outer envelope text that
`readRetryDelay` parses.

## Generator comparison (pilot, outside the workspace)

**Pilot setup:**

- A standalone crate (its own `[workspace]` table) derived both tools on
  serde-faithful shadows of `RequestKey`, `CatalogReceipt`, `ControlMethod`
  (with one unit variant), `ControlRequest` and `ControlResponse`.
- It pinned the workspace lock's `serde 1.0.229`, `serde_json 1.0.151` and
  `schemars 1.2.2`, plus `ts-rs 11.1.0` (MIT), fetched for the pilot only.
- No pilot code, lockfile or dependency was added to the repository. The
  workspace graph and the cargo-vet/deny inputs are unchanged.

**First check, on the shadows themselves:**

- **Wire bytes:** the shadows reproduced **all** fixture bytes (receipts,
  requests, responses, absent receipt) through serde. Derives on serde types do
  not change serialization; serde still owns the wire bytes.
- **Rejections:** the shadows accepted **4 of the 12** native-rejected inputs:
  - uppercase identity;
  - short digest;
  - revision 0;
  - revision above i64::MAX.

  These rules live in `try_from` newtypes (`hex_identity!`, `CatalogRevision`),
  which neither generator sees.

| Property | A: schemars → JSON Schema → TS emitter | B: ts-rs |
|---|---|---|
| u64 above 2^53 | `integer`/`uint64` becomes `number` (lossy, matches today's `JSON.parse`) | `bigint`, which is **wrong** for values from `JSON.parse` unless a bigint-aware parser is adopted |
| `Option<T>` without a skip (`receipt`) | Optional (`receipt?: T \| null`), matching serde's lenient deserialization | Required (`receipt: T \| null`), matching serialization and the extension's actual check (W4) |
| `Option<T>` with `skip_serializing_if` | Optional | Optional |
| Externally tagged enum with a unit variant | `"status" \| { catalog_receipt: … }` | Same |
| Internally tagged response (`status`) | Discriminated `oneOf` with a `const` | Discriminated union |
| `deny_unknown_fields` | `additionalProperties: false` (a validator could enforce it) | Not expressible in TS types |
| Identity format, revision range | Absent unless annotated per type (`#[schemars(regex/range)]`) | Absent, and not expressible |
| Newtype names | Inlined as `string` (`transparent`) | Kept as aliases (`Incarnation = string`) |
| Runtime validation | Needs a JSON Schema validator in the extension (none is in `package-lock.json`, so a new npm dependency) | None; types only |
| Cost to adopt on real types | Core gains a direct `schemars` dependency and derives on contract types (schemars is already in the graph via rmcp) | Core gains a new proc-macro dependency and per-field attributes |

## Conclusions for D5 (recommendation; the decision is the user's)

1. **Neither tool can replace the hand-written extension validators.**
   - The rules that matter are invisible to generated types: identity format,
     revision range, cross-field authority and the read-retry decision.
   - On u64, ts-rs would introduce a false `bigint` type.
2. **Shared, reviewed fixtures caught real cross-language differences in S1;
   generated types did not.**
   - The fixtures found W1–W4.
   - Fixtures first: exact bytes for P9 and decision cases for semantic rules.
3. **If generation is adopted later, prefer schemars for input schemas.** The
   MCP surface already uses it at runtime. It must be paired with hand-written
   format annotations and checked against these fixtures. Do not adopt ts-rs
   for wire types while `JSON.parse` numbers are the runtime representation.
4. **Not covered by this pilot:**
   - `file_info` (the read-operation example): its response type lives in the
     kernel and its validator digest is private to `current/conditional.rs`.
     Capturing it needs either a seam that exposes the representation digest
     or a fixture through a real indexed collection. That is listed as an S2
     candidate, not done here.
   - Integer handling is covered for the control read only.

The pilot crate's source is reproduced below, so reviewers can repeat the
comparison in a scratch directory. It is not part of the repository build.

<details><summary>Pilot <code>Cargo.toml</code> and shadow types (abridged)</summary>

```toml
[package]
name = "contract-pilot"
edition = "2024"
publish = false
[workspace]
[dependencies]
serde = { version = "=1.0.229", features = ["derive"] }
serde_json = "=1.0.151"
schemars = "=1.2.2"
ts-rs = "11"   # resolved 11.1.0
```

```rust
#[derive(Serialize, Deserialize, JsonSchema, TS)] #[serde(transparent)] struct Incarnation(String);
#[derive(Serialize, Deserialize, JsonSchema, TS)] #[serde(transparent)] struct Sha256Digest(String);
#[derive(Serialize, Deserialize, JsonSchema, TS)] #[serde(deny_unknown_fields)]
struct RequestKey { namespace: Incarnation, epoch: u64, nonce: Incarnation }
#[derive(Serialize, Deserialize, JsonSchema, TS)] #[serde(deny_unknown_fields)]
struct CatalogReceipt { schema: u32, operation_id: Incarnation, caller: Incarnation, key: RequestKey,
    request_digest: Sha256Digest, catalog_revision: u64, authority_fence_required: bool }
#[derive(Serialize, Deserialize, JsonSchema, TS)] #[serde(rename_all = "snake_case", deny_unknown_fields)]
enum ControlMethod { Status, CatalogReceipt { caller: Incarnation, key: RequestKey } }
#[derive(Serialize, Deserialize, JsonSchema, TS)] #[serde(deny_unknown_fields)]
struct ControlRequest { protocol: u32,
    #[serde(default, skip_serializing_if = "Option::is_none")] expected_instance: Option<Incarnation>,
    method: ControlMethod }
#[derive(Serialize, Deserialize, JsonSchema, TS)]
#[serde(tag = "status", rename_all = "snake_case", deny_unknown_fields)]
enum ControlResponse { CatalogReceipt { receipt: Option<CatalogReceipt>,
    #[serde(default, skip_serializing_if = "Option::is_none")] #[ts(type = "unknown")] fence: Option<Value> } }
```

The pilot then:

1. round-trips every fixture byte string through these shadows;
2. counts the native-rejected inputs they refuse;
3. prints `schema_for!` output and a minimal schema-to-TS rendering, then
   `T::decl()` for ts-rs.
