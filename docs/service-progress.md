# Service job progress and stall handling

Native wait reasons travel separately as transient, exact-job metadata in worker status. Their sample age is independent of durable work counters. Setting or clearing a wait never resets phase or real-advancement clocks, and no wait field is added to persisted progress. See [console observations](service-console.md) for job/generation matching and paused queued jobs.

This records native progress behavior used by the default 1.4.0 extension/CLI service. The [completion checklist](service-implementation-checklist.md) retains the remaining lifecycle and qualification gates. Earlier dated fixture counts below remain development evidence.

`progress` reads one bounded cached observation per registered project from the service ledger. It never opens sources or an index database. The observation binds the job, grant, worker incarnation and fencing generation, with its service receipt time and the ledger's current job state. Reads include the project's current fencing generation so an older worker observation remains visibly older after restart. A terminal job receipt does not manufacture a completed progress report if the last available sample was partial. Missing observations remain unavailable.

The project owner records a final sample and sends bounded private-channel samples while working. The supervisor checks its exact current work grant before persisting a reply. Ledger writes reject pending/unclaimed work, foreign/stale worker generations, older jobs, old grants, decreasing cumulative counters and out-of-order samples. A recovered job begins a new attempt under a newer fencing generation; it does not append restarted counters to its predecessor. Each project has at most one 4 KiB observation, within the service ledger's existing 32 MiB ceiling. Retired job receipts cascade their cached progress.

The counters have specific meanings:

- `captured_files` counts eligible source artifacts reaching the retained-artifact admission callback after source capture, including verified reuse. Files that fail before admission are outside this count.
- `extracted_files` counts newly produced successful extraction payloads reaching that boundary; reused payloads do not increment it. Partial syntax is still a produced payload, not a claim of complete understanding.
- `prepared_changes` counts journaled source/deletion or semantic-input changes after durable preparation. `committed_changes` increments only after their durable commit. They are cumulative work items for this job, not unique paths or whole-corpus completion.
- `publications` counts completed current-index transactions, including metadata-only transactions. It does not claim manifest replacement has switched before validation.
- `verified_objects` counts successfully verified retained sources and extraction objects; incomplete/skipped/failed verification remains separately reported by its operation.
- Indexed-file counts, complete-inventory totals, completed semantic units and exact publication tokens appear only when those indexing observations exist. Unknown totals remain null. Coverage and extraction failures still require their independent index observations.

The finite phase enum describes the coordinator's current boundary, rather than every concurrent extraction thread. Observations include job elapsed time, current phase elapsed time and cumulative durations for at most eleven phases. Terminal timing freezes at actual completion. Explicit pause remains separate. A late control pulse cannot change a terminal observation.

Real work advances at successful capture/admission, extraction, durable preparation/commit and retained verification boundaries. Merely changing phase, taking a status sample or receiving a heartbeat does not reset the no-progress timer. The worker permits ten minutes without such advancement, excluding explicit pause. It then marks the observation stalled and requests safe-boundary cancellation with the structured `work_stalled` failure code. An atomic commit is not interrupted by that cancellation request. If native work cannot reach a safe boundary within another thirty seconds, the worker exits with code 76. The parent retains its work grant through confirmed process exit; interrupted-job recovery and finite retry limits still apply. Unix descendant cleanup and the full platform fault matrix remain tracked integration/qualification gates.

Tests cover phase/heartbeat independence, pause accounting, hard-stop deadline decisions, frozen terminal timing, monotonic/fenced durable samples, replay/restart and current receipt state without invented completion. Native integration verifies actual captured/extracted/committed counts and the publication token before continuing direct queries and replacement handoff. The service console will consume these observations in its own implementation stage.

## Per-file extraction failures and rebuilds (1.7.4)

A document rejected by a work budget (for example more than 1,024 attributes on one XML element) fails promptly during extraction. It never relies on the stall watchdog. Skip reports name the cause with `code: extraction_budget_exceeded`, and other per-file failures use `extraction_failed`. Coverage counts budget rejections in `extraction_budget_exceeded`, a subset of `extraction_failed`. Other files keep indexing, and an unchanged rejected file is rejected again on each scan without stalling the worker.

A replacement rebuild may now publish when its only incomplete measurement is per-file extraction failures: `current + extraction_failed == eligible`. Those failures stay visible in the refreshed coverage. Every other incomplete measurement still refuses the replacement and keeps the current index: stale or missing files, capacity-blocked or unreadable files, pending removals, an incomplete scan, an exhausted budget, or a pending source configuration. Before 1.7.4, a single persistently failing file blocked every rebuild.
