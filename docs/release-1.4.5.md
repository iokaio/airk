## Windows retained-reader and automatic-growth fixes

The ten-repeat concurrent publication campaign reproduced the earlier Windows failure on repetition seven, after six passes. The new static contexts identify replacement of a native ownership receipt. A minimal native test and a Rust regression then reproduce the cause deterministically: `MoveFileExW` refuses replacement while a reader retains the destination, even with read/write/delete sharing. The Windows durability adapter now clears the fresh temporary-file hint on its owned handle before the initial sync, uses Rust's atomic rename with its `FileRenameInfoEx` POSIX fallback, disarms cleanup of the vacated scratch name and syncs the exact renamed handle again. Read-only destinations remain refused; no general retry or ACL override is added. See [Microsoft's existing-handle rename semantics](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information). Native power-loss qualification remains separate.

The held-reader regression fails before the fix and passes afterward; it proves the retained handle reads the old receipt while a new open reads the complete replacement. The companion regression verifies cleared temporary attributes, read-only refusal and scratch cleanup. The corrected concurrent workload passes all ten serialized repetitions against unchanged test executable SHA-256 `99f98b430b0ddec8183d129523219ab6e21894c00069aba96649723869c23a93`. This campaign covers the metadata replacement fix, not the later capacity-observation refresh or a final release artifact.

A separate deterministic regression reproduces a read-open race with real 4 MiB automatic backend growth after the initial owner/grant observation. The cached database high-water could advance before its comparison with that older receipt. The reader now captures the admitted high-water, refreshes and revalidates owner/bootstrap/quota once when necessary, and compares against the captured value. - Catalog planning/proof code has a storage interface with a redb typed-table adapter while preserving existing catalog digest bytes. The catalog test now uses 192 frozen roots captured from an agreeing SQL/redb differential run, checks final contents independently and rejects omitted buckets.
