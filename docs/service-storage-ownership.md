# Service storage ownership

F13b adds separately dated native-edge and imported-assertion coverage. Logical certification checks canonical page digests and complete keyed membership against exact retained inputs before physical page continuation. Known empty native edges are proved from those inputs; missing optional projections stay incomplete. Authoritative analysis bytes are still checked when optional imported pages are absent. Component dates distinguish authoritative analysis, native facts, native edges and imported leaves; resumption cannot refresh an older component merely because another finished later.

Version-2 projection receipts keep one bounded path cursor. Compatible version-1 campaigns recheck the new component set while preserving original first-observation dates, start time and the independent baseline cursor/history. An interrupted audit retains the existing guard; a pre-failure completion proof is revoked with its owner. Verification detects and records damage; it does not authorize automatic repairs.

F13a adds optional source-bound scalar/native-fact coverage to explicit Verify. Logical certification compares the canonical retained facts and original ordinals; resumed physical turns check the declared resources. Missing compatible legacy projections report fixed incomplete coverage and cannot mint a whole-Verify completion proof. Baseline exceptional owner recovery checks its own required baseline components and does not consume or overwrite optional projection progress. The independently owned `integrity-projection.json` preserves original component dates and shares existing quota, relocation and purge ownership. A completed baseline is distinct from completed whole-projection coverage.

The 1.4.0 development service uses `collections-1.4`, a separate `.quota-1.4` policy/reservation/recovery ledger, namespace-local private staging, and `.lifecycle-1.4.lock`. Legacy `collections-1.2`, `.quota-1.2` and `.lifecycle.lock` remain independent. A collection name alone never authorizes another family's writer, durable allowance or cleanup. Stable and preview installations also retain their separately bound native state directories; this does not authorize two installations to share a collection.

The kernel selects quota ownership from the exact managed collection layout. The store enforces that binding before publication, maintenance, WAL admission and allowance retirement. Logical collection usage and policy exclude the other family's managed collection/control directories. Physical free-space admission still observes the actual volume, so independent policies cannot create disk space. Root inventory and reservations have their existing finite limits.

Service usage accounting and shared model-file accounting use service-owned ledgers. Recovery preserves durable allowances after process handles disappear. Legacy reservation cleanup and grant discovery cannot retire service allowances, even when both families have the same collection ID and grant identity. Private staging is created and reclaimed only inside the selected family's collection. Cross-family quota writers fail before creating a destination.

Legacy relocation refuses roots containing service-owned collections or quota metadata before writing a relocation intent. Service relocation, default CLI cutover and the complete platform qualification remain tracked by the [completion checklist](service-implementation-checklist.md). Existing development service databases whose WAL allowances were written to a legacy ledger are not migrated or silently adopted; they require an explicit fresh service rebuild. Sources and unknown state remain preserved.

## 1.8 integrity foundation

The unpublished 1.8.0 candidate provides an owned `integrity-observation.json` receipt through the collection metadata API. It binds registry namespace, project/worker ownership and the selected publication, and participates in existing quota, replacement, relocation, recovery and purge ownership. Retained-head metadata enrollment leaves physical audit `Unknown`. Up to 32 sticky damage records are retained; saturation refuses a new record instead of evicting earlier detections. A failed receipt write does not establish that detection was persisted.

Checked native writer adapters invalidate a writer-local mutation epoch before their changes. This is neither a durable mutation log nor protection against arbitrary raw edits or legacy SDK writers. The optional bounded privacy census borrows the live owner/writer and uses positive supported-platform handle evidence; a saved observation cannot recreate that live capability. Its API is not wired into startup or ordinary queries, and it does not certify indexed bytes. Unsupported evidence remains unavailable and existing strict reads remain in force. Current implementation and qualification are recorded in the [optimization plan](optimizations.md#f10a-integrity-foundation); historical platform results below do not qualify this foundation.

F10b adds explicit native owner admission under existing lifecycle, writer and manifest exclusion. Compatible metadata can enroll with physical audit Unknown. A private registry Clean record means that the exact owner drained, not that bytes were audited; Active persists before owner admission and survives failed settlement. Matching clean reopen uses existing bounded metadata, without creating missing ownership/selection files or reading exceptional recovery progress. The normal worker remains strict and does not arm this capability automatically. Its optional settlement adapter runs only after accepted jobs and LocalTools close finish.

Exceptional owner recovery uses a fresh worker/job/head/root/policy purpose and an independently quota-admitted `integrity-recovery.json` file, capped at 16 KiB. Its required-component proof is sealed and currently covers only the implemented baseline lexical/retained-input policy. Future projections must extend the fixed owning policy before relaxed reads. Restarting the recovery owner rechecks prior pages under a fresh purpose while preserving ordinary audit history; applicable damage remains sticky. Both owner-state transitions and physical recovery recheck durable damage inside their final transaction. Replacement, relocation, scratch cleanup and purge recognize the new file. Older binaries can refuse its cleanup; no transparent downgrade is claimed.

Windows eligibility requires supported local handles, current-user ownership and actual propagating grants limited to the current user/OWNER RIGHTS, SYSTEM and Administrators. An extra nonprivileged read grant refuses eligibility. Linux pins recheck the original path against the retained inode and the private root boundary at owning checkpoints; unsupported platforms remain strict. This machine's sandbox grants prevent positive untouched-root Windows qualification. Controlled lifecycle fixtures establish state behavior only; Linux and actual-process positive qualification remain pending.

F11a persists explicit service Verify progress in the same owning receipt, using 32-file/64-MiB retained-object turns. It preserves original component observation dates on resumption and resets affected progress when authenticated component identities change. Legacy lexical verification can exceed a turn's object allowance because that component is indivisible. The current worker keeps the accepted job grant across turns; automatic scheduling and clean per-turn handoff remain F11b work.

The existing registry atomically arms an audit guard when claiming direct Verify or an approved physical Repair. Actual complete lexical/retained-input verification, persisted progress and an exact-publication completion proof are required for successful settlement. A fresh canceled or fixed-incomplete audit may settle only with actual clean drain evidence; inherited uncertainty and applicable damage remain vetoes. Failure-only damage persistence uses the collection receipt and existing control store; a failed write proves no durability. Historical cursor completion is not fresh owner-session recovery after an interrupted owner, particularly when both damage writes failed. That recovery requires its own fresh required-component audit epoch before later fast reads can activate. F11a qualification is recorded in the [execution ledger](optimizations.md#f11a-durable-off-path-verify).
