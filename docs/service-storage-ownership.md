# Service storage ownership

The 1.4.0 development service uses `collections-1.4`, a separate `.quota-1.4` policy/reservation/recovery ledger, namespace-local private staging, and `.lifecycle-1.4.lock`. Legacy `collections-1.2`, `.quota-1.2` and `.lifecycle.lock` remain independent. A collection name alone never authorizes another family's writer, durable allowance or cleanup. Stable and preview installations also retain their separately bound native state directories; this does not authorize two installations to share a collection.

The kernel selects quota ownership from the exact managed collection layout. The store enforces that binding before publication, maintenance, WAL admission and allowance retirement. Logical collection usage and policy exclude the other family's managed collection/control directories. Physical free-space admission still observes the actual volume, so independent policies cannot create disk space. Root inventory and reservations have their existing finite limits.

Service usage accounting and shared model-file accounting use service-owned ledgers. Recovery preserves durable allowances after process handles disappear. Legacy reservation cleanup and grant discovery cannot retire service allowances, even when both families have the same collection ID and grant identity. Private staging is created and reclaimed only inside the selected family's collection. Cross-family quota writers fail before creating a destination.

Legacy relocation refuses roots containing service-owned collections or quota metadata before writing a relocation intent. Service relocation, default CLI cutover and the complete platform qualification remain tracked by the [completion checklist](service-implementation-checklist.md). Existing development service databases whose WAL allowances were written to a legacy ledger are not migrated or silently adopted; they require an explicit fresh service rebuild. Sources and unknown state remain preserved.
