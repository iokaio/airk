# CDN proposal for Arbiter release assets

*20 November 2026 · Proposal for review*

Put a pull CDN in front of the existing public AIRK release assets. **GitHub Releases remains the sole durable backing store.** AIRK would distribute the same ONNX graphs, weight parts and companion files through an AIRK-controlled download hostname, with the existing direct GitHub URLs as a fallback. Edge caches would fill on demand and could evict content. The ONNX Runtime implementation and provider plan continue on their current path.

The retained `models-1.8.201` catalog gives a concrete test baseline. It lists 44 parts across Focus, Context Compact and Context Large, totaling 24,130,010,313 bytes. The largest part is exactly 1 GiB. This older prerelease provides public pilot objects and a size reference. The actual release’s approved source map determines its inventory and traffic estimate. [Retained catalog](../../crates/airk-retrieval/src/arbiter/release-catalog.json) · [Candidate download history](../arbiter/knownissues.md#2-optional-models-download-from-one-github-prerelease-with-no-backup)

## Delivery design

1. **Publish once.** Upload reviewed assets through the existing GitHub release workflow. Use a fixed release tag and filename for each object. Prefer GitHub’s immutable releases where compatible with the release workflow and publish corrected bytes under new URLs. Keep the approved byte lengths and SHA-256 values in the compiled catalog. The CDN fills its cache from GitHub and needs no object bucket or upload job. [GitHub release limits](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases#storage-and-bandwidth-quotas) · [Immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)
2. **Cache the bytes behind the redirect.** Map an approved `/<release-tag>/<filename>` on the AIRK hostname to the corresponding fixed `iokaio/airk` GitHub Release asset. Admit only public, approved tag and filename pairs and read-only `GET` and `HEAD` requests. Follow a bounded number of HTTPS redirects inside the CDN, restricted to the existing GitHub release asset hosts and routes. The final bytes use the stable request path as the cache key. Reject viewer query strings and keep signed redirect URLs out of responses and logs. A full download must return HTTP 200, an exact `Content-Length` and identity encoding. Cache fills and responses should stream. Exclude redirects, error bodies and incomplete objects from the whole-object cache. If the CDN uses internal ranges, prove it validates and assembles them into the same full response. [GitHub release asset redirects](https://docs.github.com/en/rest/releases/assets#get-a-release-asset) · [Current native transport](../../crates/airk-service/src/service_runtime/arbiter/download.rs)
3. **Use the existing native fallback.** Start with logical assets for which every part already has a pinned GitHub source. Give each one a complete CDN-primary roster and a complete direct-GitHub backup roster for the same ordered part lengths and hashes. Publisher-hosted assets can keep their approved sources. Add one exact CDN host and path rule in Core and the native transport. Let source-class failures try the next complete roster under the existing per-part deadlines and cancellation rules. Keep part and joined-asset verification, transactional installation and activation in the native service. The current client retries whole assets, so byte-range resume can be evaluated separately. [Core source policy](../../crates/airk-core/src/arbiter/downloads.rs) · [Whole-asset fallback](../../crates/airk-service/src/service_runtime/arbiter/assets.rs)
4. **Preserve release authority.** Approve the exact revised source-map SHA through the current promotion path. Adding URLs changes the shipping profile and catalog digests even when every model byte is identical. Generate and check those identities through the Rust owners and verify that installed profiles and offline bundle projections resolve under the intended identities. The GitHub backup keeps its asset in the release upload projection. Exercise that behavior in the native and release-consumer tests. [Final distribution contract](../../crates/airk-service/src/service_runtime/arbiter/final_distribution/CONTRACT.md) · [Publication contract](../../crates/airk-retrieval/src/arbiter/publication/CONTRACT.md)

## CDN selection and cost

**Evaluate Gcore’s pull CDN first.** Its documentation describes following origin redirects, optimizing large downloads and serving cached content during origin failures. Those features match this design on paper. Before selecting it, prove that the intended account supports all three together on a real 1 GiB GitHub release part and can restrict upstream redirect destinations. Confirm any feature charges and terms for public model distribution. [Origin redirects](https://docs.gcore.com/cdn/cdn-resource-options/cache/set-up-a-cdn-resource-to-follow-origin-redirects) · [Large downloads](https://docs.gcore.com/cdn/cdn-resource-options/optimize-large-file-delivery) · [Serving stale responses](https://docs.gcore.com/cdn/cdn-resource-options/cache/always-online-provide-the-stale-cache-if-the-origin-is-unavailable)

Fastly is a second candidate if Gcore misses a requirement. Its segmented caching supports large objects and range reads, but the GitHub redirect handling would need explicit design and testing. Standard Cloudflare cache tiers cap objects at 512 MB, below the existing 1 GiB parts. Plain CloudFront has ample object capacity and passes origin redirects back to the viewer, so it would need additional origin handling to cache the bytes. [Fastly segmented caching](https://www.fastly.com/documentation/guides/full-site-delivery/caching/segmented-caching/) · [Cloudflare file limits](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/#cacheable-size-limits) · [CloudFront origin behavior](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RequestAndResponseBehaviorCustomOrigin.html)

Gcore’s published pay-as-you-go schedule starts with 1 TB of monthly delivery included, then €0.01/GB through 500 TB of monthly usage. Using the retained catalog as an illustration, 1,000 Compact downloads are about 6.90 TB or **€59** in base delivery charges, and 1,000 Large downloads are about 16.10 TB or **€151**. These are separate monthly scenarios using decimal units, before retries, prefetch, add-ons or tax. Budget from actual delivered bytes and use account spend alerts. [Gcore pricing schedule](https://gcore.com/developers/pay-as-you-go-cdn)

## Pilot and rollout decision

- **Prove a useful cache hit.** With an approved test hostname, use one small existing asset and one real 1 GiB part. Compare cold and warm requests with direct GitHub from two relevant regions. Record full SHA-256 and length, first-byte and total time, CDN cache outcome and origin bytes. Demonstrate that a warm download consumes no GitHub origin bytes. Check that the cache key survives upstream redirect URL rotation and that the CDN never exposes that URL.
- **Prove failures through Provision.** Use controlled fault injection for CDN timeout, truncation, corruption and origin failure. Confirm successful direct-GitHub fallback where eligible and no activation when both paths fail. Exercise real native installation, a retry with verified local assets, and a fresh cache miss during the simulated GitHub outage. Test revocation and purge, including any shielding tier. Serve stale only for a bounded window on transient upstream errors and only for still-approved artifacts.
- **Roll out after the transport evidence.** Run one full install of an approved GitHub-backed model before selecting CDN-first delivery. Adopt it if it measurably improves completion time or reliability for target users within the approved spend. Track full-install success, tail latency, fallback rate, delivered bytes, cache byte-hit ratio and origin errors. For rollback, retain direct GitHub in shipped catalogs and return to GitHub-first in the next approved catalog. Purge affected objects and disable their routes if content is revoked.

Cached objects can survive a short GitHub outage while they remain available at the edge or shield. A cold or evicted part still needs GitHub, and a complete model needs every part. This improves delivery and short-outage tolerance while preserving one durable copy. Full cold-install independence requires another durable source.
