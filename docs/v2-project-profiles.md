# Project profiles and repairs revision 1

D9 extends the extraction registry with `project-facts/1` and changes affected PHP, Ruby and SQL profiles to `repair-facts/1`. Unrelated profile identities remain stable. No grammar dependency changes are required: Starlark uses the bounded Python syntax subset, Gradle Kotlin uses the existing Kotlin grammar, and SQL dialects use the existing SQL grammar plus explicitly labelled structural procedure recognition.

Project profiles cover Bazel targets/loads/dependencies, Gradle plugins/tasks/modules/configurations, Kubernetes resources/references, OpenAPI operations/schema references, GitLab jobs/dependencies, selected manifests and instruction-document cues. They preserve written references without claiming evaluated builds, resolved bindings or external schema retrieval. Structural overlays do not create code continuity fingerprints. Existing Kotlin declaration continuity remains available independently of build overlays.

Schema recognition examines at most 4096 captured bytes. Ordered JSON/JSONC/YAML/TOML views retain original spans and duplicate keys, with 100,000-node and 128-depth ceilings. OpenAPI reference traversal is bounded to 1024 edges, depth 16 and 100,000 steps; external references and cycles remain explicit. Incomplete or unrecognized schema prefixes retain generic extraction. Parser/schema flavor and instruction filename family enter effective profile identity. Instruction cues are untrusted document evidence and are excluded from document continuity matching; their content never configures execution.

Policy version 2 adds explicit captured header context. Only declared eligible regular files under registered roots are read, subject to discovery/read limits and a 128 KiB per-configuration bound. Selection hashes the actual captured bytes and indexes those same bytes. At most 16 configurations are admitted. Explicit path/scoped overrides precede header context. Only relative `.h` entries with explicit C/C++ argument markers qualify; missing, ambiguous or unsupported context retains the C default with a diagnostic. Version 1 policies remain readable and cannot use the new selector. See [policy details](extraction-policy.md).

PHP/Ruby repairs preserve exact receiver/import/mixin spellings and existing declaration identities. PostgreSQL/MySQL require explicit profile selection; generic SQL does not infer a dialect. Bounded procedure recognition emits structural evidence without continuity fingerprints. Unsupported vendor/control-flow/delimiter syntax remains partial. Oracle and SQL Server work remains in phase 11.
