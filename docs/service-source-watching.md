# Service-owned saved-source reconciliation

This describes implemented native behavior through the 1.5.4 development candidate. The default extension and CLI use service-owned scheduling; the old editor scheduler is retired from those paths. See the [completion checklist](service-implementation-checklist.md) for remaining qualification.

Version 1.5.4 creates the traversal diagnostics table through a transactional registry format-6-to-7 startup migration. Existing format-6 installations without this table upgrade normally; fresh 1.5.3 installations with its exact earlier schema retain their observations. Saved format-6 reads do not migrate metadata. Missing tables in completed format 7 and conflicting earlier table definitions remain explicit errors.

In 1.5.3, **Management › Projects** and **Management › Indexing** expose **Unreadable directories** from bounded watcher metadata. A root walk still stops at its first directory failure; this is an observed list, not an exhaustive inventory. It retains at most eight paths within an 8 KiB serialized observation, with explicit truncation, error categories and observation time. Access failures still report `root_unavailable` and periodic fallback; traversal and ignore behavior are unchanged. Entries clear only after that root is fully traversed, usually on the next ten-second plan after access is restored. An interrupted or budget-limited traversal cannot prove recovery. Paths remain scoped to their project and configuration epoch; they are not source content or evidence of indexing completion.

The service ledger retains these observations across watcher/service restarts. The bounded process log records `source_traversal_unavailable` only on a project's transition to unreadable-directory failures and `source_traversal_recovered` when they clear. Unchanged retries refresh metadata without repeating log events. Logs contain project identity, not directory paths; the scoped Management list holds the paths. Unknown backend availability does not clear retained failures. Changed root configuration discards obsolete diagnostics rather than reassigning them to new roots.

`configure_watch` enables saved-source monitoring for a registered project. Registrations begin in manual mode. The service retains this choice, requested/completed source-intent revisions, last reconciliation time, configuration epoch and bounded retry state in its ledger. Closed editor windows do not own this work. [Fenced source freshness](service-freshness.md) combines these durable intents with source-job outcomes and forwards bounded cached observations to workers independently of index readiness. Pause preserves changes and prevents new claims; resume admits them under ordinary service resource grants.

Enabled monitoring retains an on-demand service through quiet periods, including while indexing is paused or the watcher is unavailable. Disabling every project's monitoring permits ordinary idle shutdown after outstanding work and watcher notices drain. The coordinator must complete a registration scan before declaring no background intent, and its cached idle observation must be current. Configuration commits wake a fresh scan; revision checks prevent an older in-flight scan from authorizing exit. Accepted metadata operations retain their own idle charge through actual execution, including when the caller times out or disconnects.

One supervised `source-worker` owns native directory notifications for enabled projects. Its private bounded channel contains registration metadata, configuration digests, observations and source-change notices. Source-directory enumeration and potentially stalled filesystem calls run in this child, outside the service control plane. Initialization and activation precede watching. A process-lifetime OS lease excludes successors while a predecessor survives; Windows Job Objects contain the child. Shutdown drains, then kills and reaps an unresponsive owned watcher before returning capacity.

The watcher examines directory metadata and uses nonrecursive registrations: at most 8,192 directories and 16 MiB of planned/pending path bytes per project; 32,768 directories and 64 MiB of planned/pending path bytes shared; 262,144 directory entries per project per refresh; depth 64; 1,024 projects and 8 MiB of encoded bindings. A project has its original root and at most 16 additional roots. Paths must be absolute; linked/reparse/aliased directories are refused. Existing AIRK ignore hints and the project's data-root exclusion apply. Unavailable roots or exhausted limits produce periodic-fallback observations. One missing root does not invalidate another root's notification coverage. Traversal retains continuation across turns of at most 512 operations/50 ms, and native registration/removal proceeds in batches of at most 64 calls. Specific failure codes distinguish project/global directory and path-byte limits, scan-entry, depth and path-length bounds; the older `root_limit` remains for binding capacity. The watcher RSS guard scales with detected memory from 128 to 768 MiB, matching native resource reservations; reaching it can still cause bounded fallback on constrained hosts. Existing metadata exclusions remain in force. These are notification hints, not complete source-coverage claims.

Planning advances at most 512 steps or 50 ms per polling turn, with ten-second and topology-change refreshes. A syscall can exceed that budget; separate heartbeat and RSS supervision protect control responsiveness. The service reserves 1/64 detected memory for this process, clamped to 128–768 MiB, plus 32 MiB for the main service. Missing heartbeat for 15 seconds or RSS above the watcher allowance triggers termination/reaping. Three failures open a service-lifetime restart circuit with exponential delays; a service restart currently resets it. An unknown predecessor retains its reservation and reports incomplete telemetry.

Events coalesce after two quiet seconds or thirty seconds of continuous changes. A 256-batch notification queue, overflow flag and five-minute full reconciliation provide a backstop. Overflow marks every enabled scope dirty. Each project has one in-flight notice, retransmitted after one second until acknowledged. Rotating delivery prevents early projects hiding later work. The ledger atomically saves the source revision and watcher/configuration/sequence receipt before acknowledgement, suppressing retransmissions across service restart. Configuration epochs fence stale notices. Changes after a job's captured revision remain pending after completion.

Automatic reconciliation accepts at most three durable requests per desired revision with persisted backoff. Each request retains interrupted-job recovery of up to three claims: at most nine interrupted execution attempts, not three total executions. Pause, queued/running work and exact key replay consume no extra request attempt. Cancellation suppresses automatic follow-up for the captured revision; newer notices remain eligible. Exhaustion preserves desired work for diagnosis and explicit retry. Confirmed child startup failure can settle pending work only under exclusive unadmitted project ownership, with no surviving worker or ambiguous running job. Resource pressure and restart backoff leave work pending.

`watch` returns cached project observations, source-intent revisions and last successful pass time. `completed_revision` acknowledges the captured reconciliation pass; it is neither a publication token nor proof of successful extraction of every artifact or unchanged live files. `source_status` returns independent watcher availability, PID, counts, observation age, circuit and predecessor-drain state. Notification coverage and indexing readiness remain separate.

Validation covers durable pause/cancellation and retry exhaustion, captured versus later revisions, configuration fencing, duplicate receipts after restart, conservative root-cache failures, startup-settlement ownership, fair notice delivery and directory admission bounds. Native coverage enables watching, observes nested changes without editor events, pauses/resumes, queries committed evidence, restarts after an offline saved change, and verifies source preservation and lease release. Installed-editor and macOS qualification, console presentation and default extension cutover remain open.

At service startup the source coordinator waits for the metadata owner’s first registry bootstrap attempt to complete. The initial wake releases that gate; dropping an unreleased coordinator closes it without opening the registry. This avoids concurrent cold schema creation while preserving independent health and explicit metadata failures. Existing control deadlines and registry validation remain in force.
