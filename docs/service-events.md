# Retained service events and explicit retry

This is the development contract for the [1.4 native service](airkservice-architecture.md), now the default extension/CLI backend at version 1.4.0. The event reader and retry action are native management operations; the retrieval-only MCP tools expose neither. Final artifact/platform qualification remains separate.

The private service ledger keeps at most 1,024 events, each bounded to 1 KiB, alongside its existing 32 MiB database ceiling. Registration, pause/resume, job acceptance and state changes, cancellation requests, explicit retries and watch enablement commit their events in the same transaction. Rolled-back changes leave no event or retention loss. Replaying an accepted request does not create duplicate events. Terminal events survive rotation of the original job receipt, until the event's own retention boundary is reached.

Events contain sequence, observation time, project/job identities, job kind, fencing generation, attempt count and bounded failure codes where applicable. They contain no source content, paths, query text, model inputs, credentials or arbitrary exception messages. These are observations of service operations; they do not establish source freshness, index-current coverage or publication success beyond the named job receipt.

The `events` control method accepts an optional registered project filter, optional cursor and a limit of 1–32. A page is capped at 48 KiB. The first read returns retained entries in sequence order and discloses whether an older prefix has rotated away. Continuation pins the ledger namespace, filter and maximum sequence observed by the first page. New events are excluded from that snapshot. Restart preserves the ledger namespace and valid continuations.

Finish every `next` page before saving `tail` for the next poll. A tail position starts a new bounded observation after the completed snapshot. Rotation past an unread position returns `event_cursor_expired`; restart the retained log and show the gap. Changed filters or namespaces return `event_scope_changed`; future/malformed positions and invalid limits have independent codes. A complete retained page sequence is not a complete lifetime history. Native management can use `airk service rpc --runtime-dir <directory> --request-file <json>`; the file contains a `ControlMethod`, for example:

```json
{"events":{"project":null,"cursor":null,"limit":32}}
```

The `retry` control method requires the original failed/canceled job ID, caller identity and a fresh request key from the existing `request_epoch` method. It preserves the original receipt, joins matching pending work or creates a new job with zero attempts. It leaves pause and watch enablement unchanged. Source retries reset the bounded automatic retry/cancellation policy for the current desired source revision; maintenance retries reset its finite automatic follow-up allowance. Other work kinds retain their normal execution/recovery rules. Retry does not discard a pending publication journal or authorize source deletion.

The retry key binds the original job as well as the accepted operation. Mixing it with ordinary enqueue or another original job returns `KeyConflict`. Replaying an accepted retry returns that job's current receipt, including later cancellation; it never resets later policy again. Its bounded origin receipt survives rotation of the old failure while the accepted request is retained. Unknown old request epochs expire explicitly. Running, pending and successful jobs cannot be retried through this action. Capacity rotation protects the referenced failure until retry acceptance; active jobs remain protected by existing queue rules.

The native log and retry path are intended for the trusted service console. Console rendering, exported diagnostic bundles, service-wide failure events and complete repair-plan integration remain separate implementation work. No VSIX or installed-platform qualification is established by these contracts.
