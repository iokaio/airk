# Embedding cache packs

AIRK stores positive embedding results in collection-local immutable binary packs. Exact input keys still bind the complete embedding descriptor and input bytes; packing does not change the numerical pipeline or round float values. Successful no-vector results are reused only within the current build's bounded input registry.

The current derived format requires a full index rebuild. There is no reader or converter for earlier per-vector JSON cache objects. `airk index --full` preserves source files and saved collection configuration while rebuilding managed derived state.

## Integrity and publication

A receipt-authenticated version-two sidecar lists only records used by its publication and the packs containing them. Its pipeline and dimensions must match the inventory and retained model metadata. Each pack has a fixed header, a sorted key index, and fixed-size records containing the original key, numerical checksum and raw `f32` bits. The authenticated index binds each record's digest and ordinal. A lookup verifies the header/index and the selected record before returning a vector; file size or modification time is never authentication.

Writes append to private reservation-owned staging. Sealing writes the index, syncs the pack and verifies its entire contents. Finalization promotes owned packs without overwriting an existing object. An existing digest path must verify before reuse. Publication references finalized packs; interrupted private work is reclaimed through the reservation protocol. Full rebuild bypasses cache lookup and recomputes vectors, but verifies exact equality before reusing an existing packed result, including signed-zero bits.

Packs are limited to 16 MiB and 4,096 records. A manifest admits at most 64 packs, 65,536 live references and 16 MiB of serialized metadata. The adapter retains at most 4 MiB of decoded indexes and eight file handles including transient work; it permits at most 256 MiB of application reads per build. These independent limits fail explicitly rather than expanding without a bound. A pack with fewer than half its records live is compacted; exceeding the pack count triggers compaction of the live set. Compaction authenticates and copies only live records and charges replacement bytes to quota before writing. Old readers can still retain older packs until their ownership ends. The cumulative read budget includes ordinary lookups, compaction rereads and new-pack verification; a fragmented corpus can exhaust it even when a warm lookup-only build fits. Such a build fails without replacing the committed index. For example, roughly 65,000 distinct 384-dimensional vectors occupy about 105 MiB of records; three passes can exceed 256 MiB. This is a capacity limitation, not a qualified workload or an invitation to remove the bound.

Ordinary reuse authenticates targeted records without hashing every reused pack in finalization. Maintenance verifies complete owned packs, once per unique digest within a pass and within its verification budget, before reclaiming unowned objects. This also detects corruption in unused records of a partially live pack. The current receipt, pending publication and active-reader ownership protocol remains in force until the single-current-index implementation replaces it.

## Measurements

Index reports distinguish application file opens, read/write bytes, record/index/full-pack verification bytes, syncs, decoded-index hits and peak allocation, packs written/reused, and compacted records. Record and full-pack verification byte counters overlap each other and are subsets of application reads, not additional physical I/O. Packs written counts private packs sealed, including compaction; packs reused counts final owned packs that were not newly sealed. The S4 exact-input registry already avoids duplicate cache lookups; the pack index cache saves repeated index decoding across different keys.

`embedding_cache_store_us` measures individual stores. `embedding_cache_finalize_us` includes sealing, verification, compaction and promotion. Compare their combined cost when evaluating the format change. Cache counters cover the adapter through finalization; later publication verification and automatic maintenance have separate costs included in total wall time. They are not device I/O or process RSS measurements. See the [implementation and qualification ledger](indexingenhancements.md) for measured results and limits.
