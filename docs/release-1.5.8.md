## Update and installation behavior

- The extension captures its loaded version once. At activation, extension-list changes and window focus it compares that version with its own installed metadata exposed by VS Code.
- A detected difference produces one **Reload to finish update** action. Explorer replaces the old working screens with the installed/running versions and the same action. The status bar retains the action after dismissal. Repeated observations do not repeat the toast. Reload happens only after a user click.
- While that update is pending, the older host stops further runtime installation attempts and withdraws new MCP definitions. It does not cancel accepted native jobs or discard registrations, settings or indexes.
- Runtime progress says **Installing AIRK runtime**, **Updating AIRK runtime** or **Checking AIRK installation**, with the loaded version and actual stages. It does not call project indexing installation or setup.
- Successful activation ends quietly. AIRK output records that the runtime and interface are ready; Management displays the independent indexing progress. The previous completion popup with MCP Servers, Reload Window and Show Details is removed.
- Connection/terminal cleanup problems retain their underlying output details and present one **Review details** action. Repeated automatic observations of the same installation warning are deduplicated. Explicit repair can present it again.
- Connecting initially displays **Loading projects** and explains that saved registrations are being checked. It does not report a project as unregistered while the initial connection is pending. The interface's running version is available on the AIRK brand tooltip and About.

Agent sessions have their own connection lifetime. Management > Agents retains the client-specific guidance. This candidate does not silently restart external sessions or terminate VS Code to refresh them.

## Queued repair admission and troubleshooting

A local regression reproduces pending maintenance requests whose plan has finished or whose ownership link is missing. The scheduler cannot claim them, yet the source watcher sees pending work and defers new reconciliation. Bounded native housekeeping now records those obsolete pending requests as failed with `maintenance_request_obsolete`, preserving their original IDs/receipts and allowing otherwise eligible source work to proceed. It does not replay a finished approval, mark source revisions indexed, reset failure budgets or override active/paused plans. Admission also checks that the owning plan item is still queued/running, rather than admitting a terminal item.

The console records a queued maintenance request's owning plan, phase and gate, including plan pause separately from project pause. These fields also enter captured diagnostic reports. This reproduces a possible failure state matching part of the remote report; it does not prove which plan owns Bookbuilder's queued repair or the original cause on that machine.

Overview and Management share automatic service observations every two seconds while visible, with one request sequence at a time and reconnect backoff to 30 seconds. Published/semantic status refreshes automatically with a five-second throttle, plus publication-change checks even if the publication token is unchanged. Active repair plan rows refresh with their headers; completed plans stop unnecessary row reads. Normal Overview/Management screens no longer require a Refresh status button. A manual Check status now remains in Service for troubleshooting, with a check time, substantive change/no-change result and clear disconnection feedback. The header shows the latest service-check age. Refresh reads service observations; it does not implicitly repair or reindex. Queued work without a native explanation says that no blocking reason was reported and offers diagnostics rather than implying progress. A prior completed sample is collapsed under its previous job result.

Copy details on project health, progress, Activity, semantic status, Service, Storage and Recovery exports labeled cached metadata through the host clipboard. Copies include request IDs, observation times and available worker/gate/failure details, remain bounded to 64 KiB, and trigger no jobs or source reads. Displayed paths/names can be present, as the button tooltip explains; the separate full diagnostic report retains its existing default redaction.

The Recovery preview now puts a plain-language project/action summary and Start repair at the top. Its stages distinguish inspection, awaiting approval, queued work, active repair and completion. Fallback approval appears only when a loaded plan actually requires it, and its consent is tied to that exact plan/preview. The webview sends the plan ID and digest it displayed; a changed preview requires review again. Accepted repair submission gets explicit feedback. Routine native recovery is independent of this advanced reviewed workflow.

## Limits and validation

VS Code owns VSIX installation and extension-host replacement. The detection above depends on metadata and lifecycle events exposed by the public VS Code API. It does not inspect private editor installation directories or guarantee that every pending replacement is exposed before a reload. New code cannot retrofit this guidance into an already running 1.5.6/1.5.7 instance. These changes take effect once 1.5.8 has loaded; later updates can use them. The first upgrade may still require VS Code's own reload control.

Quiet completed-installation reopen still ensures that the verified on-demand service is running; it does not reinstall the CLI or repeat runtime retirement. Runtime activation replaces the console observation client so an old service incarnation cannot retain the UI pipe. Before a service response, both Overview and Management show loading/connecting rather than claim that no project is registered. Compact Windows JSON connection files are edited using the document's actual EOL mode, preserving exact save/concurrency guards.

The existing completed-installation receipt remains separate from project preparation and initial indexing. An interrupted or failed first indexing attempt keeps its native job/recovery outcome; it does not invalidate a completed runtime installation. Source/runtime recovery behavior and remaining Bookbuilder diagnostic uncertainty are documented in the 1.5.7 record.
