# AIRK split: implementation and release plan

Prepared and reconciled with `feat/split` on 13 November 2026 through `860dc4e6`. This plan incorporates the complete [Codex review](codex-review.md), the [Admin UX review and per-screen designs](codex-admin-review.md), the [combined Admin/extension proposal](codex-admin-extension-combined.md), the implemented U103–U109 baseline and the additional product requirements below. §1.1 distinguishes committed implementation and retained Windows build/check evidence from remaining repairs, UI migration, model/platform qualification and release publication.

## 1. Outcome, boundary and planning ledger

Release a matched AIRK Service/`airkctl` pair and the separate universal VS Code extension with:

1. Every review defect repaired and its regression retained; the review's unresolved observations and accepted omissions explicitly closed or brought back for a release-scope decision.
2. Preserve the implemented U105/U106 service, CLI, MCP and Explorer open-agent paths plus U107–U109 behavior, close their remaining recovery/parity and client-surface gaps, and qualify actual clients (§6).
3. **One shared AIRK presentation in VS Code and a standalone browser**, replacing independently maintained Explorer/Admin screens as their surviving workflows qualify. Retain a small VS Code host for editor integration, scope, trust and startup guidance; preserve Explorer's richer evidence/review/strategy workflows and the separate Workbench unless explicitly migrated. Support a remembered host choice, task-based Help and compact layouts with less scrolling. This expands the earlier “Admin inside Explorer” requirement; it does not reduce the extension to a passive iframe.
4. Extension download actions, description and README pointing to `https://airk.ioka.io/index.html`, backed by the verified GitHub release catalog.
5. Working Windows, macOS and Linux installers, including an exact `--silent` entry point that installs with documented defaults without terminal interactions.
6. A verified ZIP for each supported platform/architecture containing the runnable service pair, required assets/notices and platform-specific manual setup instructions; no installer or VS Code is required to use it.
7. Static online help at `https://airk.ioka.io/help/html.index`, generated from the help shipped in the product and covering extension users and CLI-only users.
8. The [Arbiter concept](../arbiter/concept.md), with the purpose clarified in §9: local AI gathers relevant evidence from the index and provides fuller contextual answers for agents and Workbench users, reducing the follow-up turns needed to satisfy a user's prompt or instructions. Deliver improved bundled MiniLM INT8 retrieval plus an optional, default-off, per-index Arbiter with two smaller and two larger qualified model choices, running inside the existing service.
9. When a user splits an index, both resulting indexes automatically become members of an index set named after the original index. Include this set and both memberships in the split's reviewed outcome and completion checks (§7.3.1).
10. Qualify the existing independent index-set deletion path against the full preservation/recovery matrix, implementing only missing behavior or coverage (§7.3.2). Member indexes remain intact; a separate retirement operation has not been established.
11. During extension setup/first use, when the service is confirmed not installed and the host supports installation, offer **Download and install automatically**, **Install manually**, and **Not now**. The automated option discovers the official compatible service installer from `iokaio/airk` GitHub releases, verifies it and runs its headless `--silent` entry point. It requires the user's choice; extension installation/activation alone is not consent (§8.5).

The release is complete only when the approved release workflow and publication verification succeed. Packaging alone is a candidate milestone. If a requested capability cannot qualify, report the specific blocker; do not silently remove it from the acceptance criteria or label a partial candidate the completed release.

## 3. Entry gate and decisions

### 3.1 Preserve the implemented U105–U109 authority and read contracts

All seven U105 steps now have committed implementations (§1.1). Use their existing source, tests and retained evidence as the starting point; remaining work is the specific repair/qualification backlog, not another implementation of those steps. The [open-access specification](open-agent-access.md) has a U109-amended goal but retains older paragraphs; use the current native decision code and recorded amendments when reconciling stale wording.

Retain these U105/U106 invariants from [open-agent-access.md](open-agent-access.md):

- Old grant-bound connections continue to work. A predecessor refuses a ledger containing an open record. Ledgers without open records and catalog objects without descriptions retain their prior serialized bytes/digests.
- New/migrated open connections start with `agent_choice: off`. Omitted selectors read the stored default scope; explicit selectors may narrow to a nonempty subset of its resolved indexes, after set expansion. Outside indexes refuse `agent_scope_choice_disabled` with the outside members named. Off still hides `list_indexes` from `tools/list` and refuses direct invocation; an unset default refuses `agent_default_scope_unset`. Preserve these U109 rules in both schemas and execution.
- Names resolve by ID, then exact name, then unique case-insensitive name; ambiguity/unknown names refuse. Inputs allow at most 32 index selectors and 32 set selectors, subject to the existing resolved-selection limit. A named index reads all enabled sources; a set expands its members as whole indexes. Choice-on permits every index owned by that OS user; workspace defaults are not an access-control boundary in this mode. Direct local-owner selectors are separate from a connection's choice-off authority.
- Defaults are service-owned, revision checked and effective on the next call without credential-generation changes, reconnects or agent-file rewrites. Nonces remain bounded, leased by connection/resolved scope/catalog revision, expire after the specified 300-second idle interval, and are revoked on the relevant defaults/revision/revocation changes.
- Descriptions remain optional, limited to 1 KiB with the specified control-character rules; absent descriptions are generated for display, never eagerly persisted. Description edits can invalidate catalog selections and must exercise the repaired reselection paths.
- `list_indexes` returns bounded revision-bound index/set pages with names, descriptions, source roots and catalog-only readiness; that field is not proof of indexing/semantic readiness. `limit_per_index` allocates the requested result count per member; the product must fit the explicit overall `limit` or its derived default and the existing 100-result maximum. Bytes, deadlines and verification budgets stay shared. Member reads run under bounded query concurrency and return in canonical order; names are display metadata and elapsed times are timing, not provenance identities. Omitting the new field preserves prior budget/cursor encodings.
- Open HTTPS connections follow current catalog issuance without requiring reenrollment on a catalog revision move. Revocation, pending fences, shutdown and current per-call authority still apply; grant-bound connections retain their captured fence. Tool visibility is refreshed by a fresh `tools/list` or reconnect; no `notifications/tools/list_changed` is currently emitted. Defaults changes take effect on the next call independently of that cached visibility.

Preserve existing mixed-index/set, source-expansion, deduplication, empty/invalid-scope, revision, publication/continuation, partial-failure, budget and isolation coverage. Three actual CLI/pipe/HTTPS combined-read regressions have retained passing evidence (§1.1); they do not establish complete W4/A2/native/installed-client parity. Add only missing cases needed by a consumer or a review finding.

## 9. Arbiter implementation and model preparation

**The primary purpose of training is to make AIRK answer questions about indexed files with more complete, useful context.** Local AI should interpret the information needed for a user's prompt or set of instructions, help gather additional relevant evidence from the index, and organize a robust contextual response. A more capable AI agent can use that response to achieve the user's goal with fewer follow-up turns and retrieval calls. Workbench users should receive useful answers about their files through the same capability, without manually assembling a sequence of low-level MCP results. Arbiter has no code-generation objective and does not edit files or perform the user's coding task.

| Consumer | Required product outcome |
| --- | --- |
| A more capable AI assistant or coding agent | A task-specific context response containing the pertinent implementation, definitions, documented constraints, configuration, examples, tests and exceptions that indexed evidence supports. Gather complementary evidence so the agent can reason or act with fewer requests for missing context. The receiving agent remains responsible for its actions and code generation. |
| A person using Workbench | A source-grounded contextual answer to questions such as “Where is this behavior defined and tested?”, “What constraints apply to these files?” or “Which documents explain this configuration?”. Present connected, cited facts and excerpts, qualifications and missing information, with source navigation and access to full evidence. These are information tasks, including non-code documents, rather than a raw tool-response viewer. |

Improved embeddings, routing and relevance scores support these outcomes. Training and qualification must measure the usefulness and completeness of the delivered contextual response and the reduction in follow-up work; better isolated classifier accuracy or smaller packets alone does not complete the feature.

The [concept](../arbiter/concept.md) supplies the model, isolation and lifetime requirements. This user clarification makes **bounded gathering of additional indexed evidence** part of this release plan; it is not left as a future optional expansion. Land its own reviewed contract in A3 before implementation, preserving the concept's canonical reads, source grounding, budgets and authority boundaries. Its old `airk-cli` service-owner wording must follow the live extracted owners: inference lifetime in `airk-inference`, composition in `airk-service`, runtime/model execution in `airk-retrieval`, contracts in Core, persistence in Store and canonical reads in kernel/frontend/MCP. Do not recreate a monolith or extract a new crate.

### 9.0 Context gathering and response flow

1. Accept the question or information need from the user's prompt/instructions, its authorized index scope and a total work budget. Resolve targets against current indexed evidence and select a supported native retrieval recipe. Instructions describe what information is needed; they do not grant new scope, mutation authority or permission to execute commands.
2. Retrieve an initial bounded evidence set through canonical indexed reads. Use improved MiniLM to find useful passages even when the question's wording differs from the files. Preserve lexical/exact lookup behavior and original source/publication identities.
3. Use the qualified local Arbiter to assess relevance, evidence roles and the information still needed for the question. Choose additional reads from explicit supported operations and verified targets: for example, expand the defining context, retrieve a cited constraint, find related tests/examples, or gather a relevant document section. The service validates and performs those reads. Merely reranking the initial hit list is insufficient for this requirement.
4. Stop when the reviewed recipe's required evidence is covered, no justified next read is available, uncertainty requires clarification, or the fixed read/round/fan-out/byte/token/deadline budget is reached. “Sufficient” is a task-relative assessed state with reasons, not proof that every relevant fact was found. Duplicate/no-progress reads terminate expansion; stale or refused reads remain visible. Model decisions cannot increase the original budget or authorize arbitrary tool execution. This is a finite native retrieval workflow, with no general-purpose agent loop or external agent control.
5. Assemble a contextual answer with organized source-backed facts and intact excerpts, relevant constraints and exceptions, citations, relationships supported by the index, and explicit gaps/ambiguities. Workbench displays this answer directly; agents receive the equivalent context for their own reasoning. The answer's organization and explanations identify the evidence supporting them. Model judgments about relevance/roles remain distinguishable from source facts; unsupported conclusions are not presented as facts.

Use the proposed packet as the evidence-bearing basis of this response. Keep full canonical results available under normal authorization/lifetime rules. Add the composed contextual operation through the reviewed native contract and expose equivalent supported inputs/results in CLI, MCP and Workbench; low-level direct reads remain available with their existing semantics. The user-visible gain comes from gathering and organizing evidence around the question, not from withholding data from the raw interfaces.

### 9.1 Fixed acceptance and model catalog

### 9.3 Data, evaluation and typed advice

Follow the concept's acquisition → baseline → train → export → calibrate/freeze → untouched evaluation → integration sequence. Pin experiment inputs, seeds, hardware, training resources, exported identities and reproducibility limits. Keep training requirements separate from end-user inference requirements.

**What the models are trained for:**

| Training target | Examples and expected behavior |
| --- | --- |
| Question-to-evidence retrieval — MiniLM | Pair real questions/instructions with relevant indexed passages and hard negatives. Include code, prose, configuration, tests and document formats. Retrieve the contract or exception needed to understand a behavior, even if another passage is a closer lexical match. |
| Context relevance and complementary coverage — Arbiter | Score evidence for the user's information need and required roles; select useful complementary records over redundant hits. Evaluate sets of records as well as individual passages. Preserve controlling constraints, counterevidence and exceptions within the budget. |
| Gathering missing context — Arbiter | Label intermediate retrieved sets, remaining information gaps and justified next reads among verified native choices. Examples require gathering a definition plus its context, related tests/examples or documentation across permitted files. Reward reads that close a real gap; stop on adequate coverage, no progress, unsupported requests or exhausted budgets. |
| Organizing a grounded answer — Arbiter plus native presentation | Classify the role and contribution of retrieved evidence so the service can present coherent cited facts/excerpts and supported relationships for Workbench or an agent. Preserve ambiguity and qualify interpretations; every source claim remains traceable. |
| Applicability and uncertainty — Arbiter | Identify unresolved targets, insufficient/stale evidence, unsupported questions and no-valid-next-read cases. Return a specific gap or clarification need instead of inventing context. Routing/recipe selection supports these information goals. |

Training is directed at retrieval and contextual answering, with no code-generation loss, patch prediction or command-execution objective. A user's coding goal determines what context is useful; it does not turn Arbiter into the agent that implements that goal. Optional models may qualify without new weight training if unchanged artifacts meet these AIRK-specific gates after evaluation/calibration; any adaptation is driven by measured contextual-answer gaps. MiniLM still requires the actual encoder-training experiment.

Examples record the original prompt/instructions, intended information need, task/version, repository/revision, authorized scope, candidate/source identities, required evidence roles, independent sufficient-evidence sets, complementary records, distractors, contradictions/exceptions, intermediate read observations, allowed next-read choices, stop/abstention reasons and a cited expected response rubric. Include tasks for both agent preparation and direct Workbench use, with non-code files represented. Judge completeness and usefulness of the evidence set; similarity-only positives can reward redundant context that omits the critical constraint. Gold labels are independently adjudicated, not derived from the implementation or merely from which files a later patch changed.

Record language, annotation authority, licenses and split lineage. Split by repository/fork, issue family, symbol family and paraphrase origin before mining/synthesis. Keep train/development/calibration/policy-selection/final evaluation disjoint; hold out whole families and audit benchmark contamination. Include ambiguous/no-valid choices, stale publications, partial extraction, lexical distractors, negation and instructions inside evidence. Public retrieval datasets do not establish AIRK authorization or context-sufficiency labels. Add separately versioned task/decision contracts and independent cases in A3 where bounded next-read or context-gap judgments exceed them; do not silently overload a fixed head or existing wire shape. Qualify tasks individually and disclose unsupported tasks, but every promoted model must contribute to the primary contextual-response use case. Do not substitute ordinary decoder logits for trained pointer/head scores or call relative softmax a calibrated probability.

**Primary qualification is measured at the question and goal level:**

1. **Assistant goal completion and turns.** Compare ordinary raw-MCP retrieval, deterministic composed retrieval and Arbiter-assisted contextual responses on the same held-out prompts/instructions, authorized corpus/revision, capable-agent model/version, tool access, total budget and goal rubric. Allow the ordinary baseline its normal follow-up reads; do not handicap it to a single hit list. Count agent turns, retrieval calls, clarification turns and internal Arbiter reads separately. Measure successful goal completion, missing critical evidence, unsupported claims, citation fidelity, total latency and token/byte cost. Fewer turns count as an improvement only with the frozen quality/coverage floors maintained; moving unbounded work inside one call is not a win.

3. **Native exported-model effect.** Measure both MiniLM INT8 exports and each optional model's actual native artifact. Separate encoder gains from Arbiter's additional gathering/organization gains; keep the semantic baseline fixed when comparing optional models. Retain general-document/language, resource and uncertainty regressions.

Hold the downstream agent and rubric fixed, report stochastic variation and task-family results, and limit claims to tested populations. Downstream task execution belongs to an authorized isolated evaluation harness or the user's agent, never the installed Arbiter service. ## 11. Validation ladder and release gates

### 11.1 One correction cycle per completed package

1. Read complete affected flow/contracts/callers/tests and retained failures. Record hypotheses, invariants, persistence/concurrency/ownership boundaries, exact parser inputs and uncertainty before execution.
2. Add known sibling regressions together and run one scoped diagnostic batch to confirm the analyzed failure class. A passing hypothesis is not a reproduced defect. Add the smallest observation seam if evidence is insufficient.
3. Finish production, caller, fixture and regression changes together. Review the complete diff and input roster, then freeze inputs. Do not compile after each small edit.
4. Run one ordered affected validation batch, stop on failure and collect complete diagnostics. Classify production defects, harness errors and missing prerequisites before preparing a coherent next correction. No assertion weakening, deadline widening or retries until green.
5. Reuse unchanged artifacts/evidence under their original identities. Harness/docs/frontend-only changes do not justify a native rebuild. Two failures of a T2/T3 component stop further runs: record wrong assumption/missing cheap seam and return the blocker before a third attempt.
