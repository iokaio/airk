### Repeatable local commit cycle

1. **Select:** verify branch/worktree and the next phase's prerequisites. Read the current source/contracts/tests, list the exact intended files and acceptance cases, and distinguish implemented behavior from experiments. Preserve unrelated user edits; stage explicit paths/hunks only.
2. **Reproduce and measure:** use an isolated fixture or named real corpus as appropriate; record actual initial failures and work counts. Do not turn latency aspirations into brittle ordinary unit-test deadlines or warm a first-response measurement with diagnostics.
3. **Implement:** make one coherent change. For storage/integrity work, include its writer, recovery, retention and reader implications together. Keep optional quality work off ordinary queries. If the scope grows, split/update this plan before expanding the patch.
4. **Test:** run the focused row gate first, resolve the complete shared cause of failures, then run the applicable commit gate below. Record commands, pass/fail/ignored/unavailable counts and actual timing/counters. Do not relabel skipped or unavailable validation as passing.
5. **Review:** a separate agent reviews the complete phase diff and validation evidence; the primary also reviews the combined diff. Check related callers, managed/platform paths, docs and rollback behavior. Fix findings and rerun checks justified by the changes. Do not run expensive hosted CI as a debugging loop.
6. **Commit locally:** update affected current documentation, including candidate release notes, and verify README/index/Marketplace text agree with implemented behavior and the source version. Use the configured authorized human identity with `git commit -s`. Verify the actual `Signed-off-by: Tyler Jensen <tyler@tsjensen.com>` trailer. Do not invent agent sign-offs, amend earlier user commits, push, open a PR or publish.
7. **Checkpoint the plan:** after the implementation commit succeeds, record its hash, completed scope, tests, measurements, review, limitations and next phase in the ledger. Commit that small documentation checkpoint locally as well, so a restart has a committed handoff. The checkpoint records the preceding implementation hash; no self-referential hash or history rewrite is needed.
8. **Repeat:** begin the next ready phase without asking again for already-authorized local implementation/testing/commits. A failed gate keeps that phase open. A blocked optional experiment does not prevent independent required work; record the precise unresolved decision and finish the unaffected scope.

## Findings and limits

The reproduced failure is a deadline mismatch: the unified `status` wrapper allows two seconds for the whole backend call, including authenticated installation readiness, registration resolution, brokerage and the index observation. The installed service and published index can be healthy while that preparation exceeds the deadline. `diagnostics` shares preparation but does not have this two-second wrapper. The native scalar status implementation is substantially cheaper once connected.

This is not evidence that every reported timeout has the same cause. Source review also found two-second registry waits, two-second optional usage-lock waits, and status waiting behind another evidence exchange. These can independently consume the same deadline. They need isolated measurements rather than attribution from the error code alone.

### Four verification passes on an ordinary unmanaged launch

The current source-bound route can perform these complete verification passes before the first native tool completes:

1. Universal shortcut or delegated stable launcher: `selected` before executing the engine.
2. MCP construction: `root_mcp_control` -> `installed_metadata_control` -> `selected`, before initialize is answered.
3. First tool: `RuntimeReadiness::ensure` -> `installed_control` -> `selected`.
4. That same readiness operation: `ensure_running` -> `selected` again, followed by authenticated service health.

Each `selected` calls `verify_runtime`: hash all manifest files, rehash main/helper for the executable-pair receipt, traverse the complete topology and hash each present role copy. For the measured installation, that is approximately:

```text
248,244,233 manifest bytes
+ 176,640,512 main + 55,317,504 helper, checked again for the pair
+ 3 x 176,640,512 distinct role-file bytes
= 1,010,123,785 logical hash bytes per full pass
x 4 passes = 4,040,495,140 bytes, about 3.76 GiB
```

This is source-derived logical SHA-256 input, not measured physical disk reads or an instrumented count of every installed launch. It excludes launcher self/equality hashes, extra main-image hashes and filesystem metadata work. Managed pins and repair/compatibility routes must be measured separately.

Use `T_hash = B / R` as a falsifiable serial cost model, where `B` is logical bytes hashed and `R` is measured aggregate native hashing throughput. The sensitivity table uses assumed decimal GB/s, not claimed SHA-NI performance:

| Assumed throughput | One 1,010,123,785-byte pass | Four-pass total |
|---|---:|---:|
| 0.5 GB/s | 2.02 s | 8.08 s |
| 1 GB/s | 1.01 s | 4.04 s |
| 2 GB/s | 0.51 s | 2.02 s |

The two Python manifest-only samples imply about 1.00-1.02 GB/s for that interpreter/backend and access pattern. They do not establish native SHA throughput, physical I/O or native CPU seconds. The four passes occupy initialization and first-tool windows, not all the status timer. Instrument native thread CPU, wall time, concurrent verification and bytes per stage before comparing the model to the observations. The locked `sha2` backend already supports x86 runtime hardware dispatch; verify actual build/CPU dispatch instead of treating SHA-NI as a missing feature. [Versioned RustCrypto backend](https://raw.githubusercontent.com/RustCrypto/hashes/sha2-v0.10.9/sha2/src/sha256/x86.rs).

## Cache design policy

Every proposed cache must have a reviewable specification before implementation:

1. **Owner and exact key:** include authorized root/project, registry/collection incarnation, publication/model/configuration/schema identity as applicable, canonical effective arguments and representation options if caching representation. Queries use the exact input consumed by the current versioned preprocessing; do not invent new text normalization for hit rate.
2. **Authority fence:** a hit still needs current authorization, removal/lifecycle checks and the current-head/integrity authority specified by the chosen policy. Strict mode requires equivalent physical-integrity evidence; the target private-owner profile uses publication/owner certification and separately disclosed audits. A token, TTL, file timestamp, watcher event or SQLite counter alone is not a universal integrity proof. Resolve fences and read/head selection atomically enough to reject a hit racing replacement; do not quietly substitute one assurance profile for the other.
3. **Bounds:** declare entry count, logical bytes, allocation/handle limits, TTL/max observation age, in-flight fills and CPU budget. Charge the aggregate against existing process/service memory policy; caches do not create extra capacity. No unbounded negative or error cache.
4. **Invalidation and failure:** specify publication/registry replacement, removal, configuration/policy changes, filesystem replacement, expiry, schema changes, partial pages, worker restart, permission failures, overflow and unsupported filesystems. Unknown validation forces a fresh authenticated path or explicit failure. Never serve an expired token as historical fallback.
5. **Observation versus immutable evidence:** immutable numeric vectors/decoded content may be reusable longer than mutable health/freshness. Refresh dynamic fields independently. A whole status invalidated only by publication head would miss source queues, pause/failure and freshness expiry.
6. **Client-local rendering/accounting:** cache logical observations or explicitly key representation; render omission receipts, full/terse choices and caller observations separately. Preserve exact validators/byte limits. Count actual native submissions, coalesced waiters and cache hits distinctly; define one usage observation at the existing outer-request boundary without inventing forwards or replaying a submitted read.
7. **Disclosure/privacy:** reused observation/evidence needs origin, age and cache-hit diagnostics where useful; preserve current `cached`, `cache_age_ms`, `observed_unix_ms`. Adding fields to public replies is an intentional schema/help compatibility decision, not required for internal statement/page reuse. Query/result caches start memory-only; no query/source text in persistent metrics or keys written to logs.
8. **Lifecycle:** a cached object must not retain an idle snapshot, transaction, object gate or undeletable database handle. Pooled connection experiments have an explicit purge/rebuild/relocation drain protocol. No half-read transport or uncertain outcome may become a cached success.

## Outcomes and measurement contract

The first outcome is fast access to an **existing authenticated publication**. Opening Explorer must not make a saved index wait for fresh source reconciliation, semantic completion, every workspace project, agent-file migration, shell setup or full diagnostics. First installation, upgrades, incompatible formats, pending recovery and unregistered roots remain distinct paths with real prerequisites.

The second outcome is an interface that promptly shows what is available. Render the shell immediately; show saved observations with their age while confirming the connection; enable reads only after the selected scope/publication is authenticated. Separate connection progress, published text availability, source updates and semantic readiness. A service health response or a remembered count alone must never become a green ready state.

Add opt-in, content-free monotonic timing at the outer launch/extension boundary before optimizing. Current usage spans start after admission and snapshot selection, and recording finishes after elapsed time is calculated; they cannot explain end-to-end latency on their own. Capture these stages independently:

- launcher process creation/routing, full verification pass count, hash calls and bytes, path/topology checks;
- installation-lock wait and hold, lifecycle settlement, health verification and unnecessary receipt writes;
- extension activation, discovery, registration lookup, launch-spec publication and first UI render;
- registry opens/pages/busy waits, brokerage, direct authentication, worker startup and inner session creation;
- cache hit/miss, backend-mutex wait, native admission, snapshot selection, scalar status and serialization;
- usage open/resource sampling/baseline/record waits, completed native submissions after waiter cancellation;
- first lexical result, first usable semantic result, UI confirmation, background polls and Workbench saves.

Keep reports path-free and query/source-free. Report physical I/O as unknown unless measured by the OS; logical bytes hashed are not disk traffic. Record build identity, CPU/core limits, memory, storage class, filesystem-cache assumptions, corpus counts, active projects and whether the service was already running. Count native submissions separately from client retries. Do not add diagnostic probes to ordinary status to collect these measurements.

Proposed local acceptance targets below are engineering goals, not current guarantees. Validate against comparable before/after builds on the same fixtures; adjust documented targets only with recorded evidence.

## Single-user deployment options

The user confirms that the current user is the only account that ever accesses these index files and directs that deep data-quality checks move outside fast MCP retrieval. AIRK is already a local per-user service; no multi-tenant database or cloud permission layer was found to remove. That deployment fact supports reducing redundant same-user ownership checks and reconsidering hostile out-of-band mutation detection on private derived state. It does not remove simultaneous Codex/Claude/Explorer connections, background writers, worker crashes, stale publications, cleanup or accidental corruption.

**O37. Make private service ownership the target retrieval model.** Inventory each check by the failure it protects against, then choose the least repeated work consistent with the agreed detection contract. The recommended target for this confirmed deployment is a trusted-private-index profile with deep verification owned by publication and maintenance, rather than repeated on every user/agent read. Keep current behavior until the profile and migration are implemented and qualified; this document does not claim the change is already safe or complete. Retain a separately defined strict audit/diagnostic path and suitable handling of roots that do not satisfy private-owner assumptions.

Private eligibility needs positive platform ownership/access evidence plus the bound data-root and worker lease; default location and existing privacy-warning APIs are insufficient. Reuse appropriate native checks without silently rewriting custom-root permissions or claiming a descriptor check certifies every descendant. ## Second pass: data reduction recommendations for human review

Reviewed October 30, 2026. These are recommendations, not implemented changes or approval to discard existing data. The strongest opportunities are repeated copies of useful evidence, data for unopened UI sections, and complete catalogs returned to callers that need one section. Removing those costs can improve response latency, available evidence within a byte budget, agent context use, session size and UI responsiveness. It does not require returning fewer relevant matches or weakening the meaning of a result.

Distinguish three decisions: avoiding construction of an unchanged representation; changing the default wire/UI representation while keeping all useful information available; and omitting stored evidence or future capabilities. The tool-specific return-preparation notes address the first. The recommendations here identify representation and storage decisions for human review. Any new representation needs its own compatibility, pagination, byte-accounting and validator review. Reducing wire bytes alone does not prove less disk I/O, CPU, model context or elapsed time.

### Existing reductions and a small response-size check

AIRK already defaults to terse output, omits unchanged client-local freshness/readiness/indexing observations, shares provenance, emits one current publication token with local references, and supports compact fact pages with file/provenance tables. Search already defaults to focused snippets, and `parse` already offers an evidence-only view. Preserve these; do not count them as new savings. Sources: [response policy](../crates/airk-mcp/src/response.rs), [minimal facts](../crates/airk-core/src/discovery_minimal.rs), [plan output](../crates/airk-kernel/src/workbench.rs).

### R01. Store and return plan evidence once

`locations()` in [the plan runner](../crates/airk-kernel/src/workbench.rs) constructs `{citation, text, fact:<complete original record>}`. Execution also keeps the native result in `steps[].result`. For a text hit, its text and citation therefore occur in the raw step result, the evidence row and the nested `fact`. [Workbench state](../packages/vscode/src/workbenchView.ts) adds another derived card containing the text. These copies do not provide four distinct pieces of evidence. Moreover, `bounded_result()` removes visible evidence rows before removing the retained raw step bodies, so duplication can consume the budget while useful cards disappear.

Recommend a versioned canonical record table with step-to-record references and one copy of each excerpt/citation/provenance record. Keep step arguments, status, errors, budget use, continuations, interpretation qualifiers and effective plan/digest. Retain non-citation raw step metadata as canonical data too; an excerpt table alone cannot reproduce every result. A normal evidence view can use these records directly; raw/export views can reconstruct the complete supported representation from the same retained data. Preserve distinct facts at the same location and their producer/basis: equal citation text alone is not proof that two facts are interchangeable. This is deterministic representation work, not AI summarization.

Do not merely switch Workbench to the existing `output.view:"evidence"`. That option clears raw results only after execution, and [continuation discovery](../packages/vscode/src/workbenchRender.ts) currently obtains cursors from `report.result`. Move required cursor/selector/validator/coverage information into the compact step contract first. Raw JSON export must remain lossless; fetching current evidence later cannot recreate a saved publication that has expired. Measure unique evidence bytes versus total envelope bytes, copies/allocations, visible cards retained at the same budget, and exact export/continuation parity (O19/O23/O38; T12).

### R02. Send Workbench the data needed to display the current view

[Workbench state](../packages/vscode/src/workbenchView.ts) sends the whole session, including envelopes, alongside derived cards and continuations. [The webview](../packages/vscode/src/workbenchWebview/main.tsx) also formats plan JSON and source details inside collapsed `<details>` elements; those expressions run while the details are closed. JSON and Markdown main views already render conditionally, so that is not a missing optimization.

Keep one authoritative bounded session in the host. Send turn summaries, visible cards, continuation handles and active-view data; request immutable turn details or exact JSON/Markdown only when opened/copied/exported. Render closed details only after expansion. A view handle must bind session/turn/revision and fail explicitly if evicted; do not reread the live index as a substitute for saved evidence. Pair this with O23 deltas so a saving indicator does not resend every excerpt.

For persistence, an explicit request plan and returned effective plan can also overlap substantially ([session writes](../packages/vscode/src/workbenchSessions.ts)). Consider a versioned shared representation only where exact equality is proven. Preserve entered text, recipe parameters, resolved arguments, changes made by the user and rerun semantics; the requested and executed plans are not generally identical. Measure postMessage bytes, closed-details formatting time, session bytes and restored/exported content before choosing any migration.

### R03. Deliver each successful Explorer search result once

[The controller](../packages/vscode/src/explorerController.ts), in `search.run`, posts a full `search.session` notification and then returns the same view through the ordinary request response. [The Search screen](../packages/vscode/src/explorerWebview/search.tsx) awaits completion but discards that response data; [the application](../packages/vscode/src/explorerWebview/app.tsx) uses the session notification.

Use one canonical full-result delivery and a small correlated completion acknowledgement. Keep busy/error notifications, selection epochs, superseded-request rejection, restored state and every hit/citation. Audit other consumers before changing the internal response contract. Acceptance: exactly one full successful result per search, unchanged displayed hits and errors, and lower serialized/postMessage bytes. This is a particularly direct reduction with no relevance tradeoff.

### R04. Keep unopened reports and offscreen management data out of routine UI messages

[`managementView`](../packages/vscode/src/explorerManagement.ts) includes a saved diagnostic preview whenever it exists, even on another Management tab. [Diagnostic previews](../packages/vscode/src/serviceConsoleView.ts) can approach 256 KiB. Only the Logs pane displays the report, but subsequent state updates can repeatedly carry it. The same view also builds service/runtime/resource/inference data and every project's formatted activity, work, storage and configuration sections together.

Retain the captured report once under an immutable host-owned revision. Send an availability/age/redaction/truncation summary outside the report view, and deliver the body once or on explicit open/copy/save. Send shared action eligibility and the visible Management section, loading another section when selected. Keep new failures and blocking action reasons visible regardless of tab. Do not silently regenerate a captured report or lose its observation time, redaction choice, stale-report notice or exact export.

The [UI assistance status](../packages/vscode/src/explorerAssistance/tools.ts) also repeats static routes, destinations, tool names and help notes alongside changing attachment data. Internal compact observations may reference an exact catalog revision; explicit full diagnostics should remain self-contained. Measure report-body bytes resent per poll, offscreen formatting time and complete current details after tab switches (O16/O23/O24/O40).

### R05. Return the capability or diagnostic section that was requested

[`capabilities`](../crates/airk-mcp/src/lib.rs) always constructs the Workbench operation/schema catalog and extensive static guidance, even for an exact adapter with `rich:false`. Workbench Forms uses only `payload.workbench.operations`. Recommend explicit section selection for adapters/formats, operations, limits and explanations; preserve a full inspection mode. Static sections can be obtained once by exact catalog identity rather than attached to every filtered inquiry. This changes the public contract/default only after review; it is separate from caching the identical current response (T01/O19).

Similarly, optional diagnostic sections can avoid gathering, formatting and sending unrelated process, job, index or editor detail. Full `diagnostics` remains available and self-contained. Preserve each section's observation age/source, identity mismatch, unavailable reason and partial-coverage state; a missing unrequested section must not imply healthy. Share repeated static explanations or identities only through an explicit resolvable representation. Measure avoided work as well as returned bytes; dropping fields after all probes run saves little preparation time (T05).

### R06. Project useful terse readiness and omit only truly absent values

General first/changed evidence replies serialize [full readiness records](../crates/airk-core/src/readiness.rs), including version, selection/pipeline digests, detailed work units and ready timestamps. [The response layer](../crates/airk-mcp/src/response.rs) later omits unchanged records, but does not make those initial records smaller. Recommend a terse summary with availability/state, effective retrieval policy, useful coverage counts and real failure/partial reasons. Keep detailed identities and timing in full output or explicit diagnostics. The scalar status implementation already demonstrates this principle.

Also review absent-value fields: [`MinimalFact.signature`](../crates/airk-core/src/discovery_minimal.rs) can serialize `null` per row; rich code/document records contain other null/empty values, and successful [conditional reads](../crates/airk-core/src/evidence.rs) can include `reason:null`. Use schema-defined omission only when it has exactly the same meaning, respecting required versus optional fields. Unknown is not false, absent coverage is not complete, and an empty result is not an unexecuted query. Keep failure/candidate/truncation state and all conditional-read outcomes explicit.

Do not weaken the substantive state used for omission receipts: model, policy, coverage and failure changes must still be observable even if detailed hashes move out of terse display. Review validator identity and byte accounting rather than silently changing them. Measure first response, progress, model replacement, failure and unchanged-repeat cases independently.

### R07. Share file identity within search/reference hit pages

Each [hit citation](../crates/airk-core/src/lib.rs) repeats its path and source hash; source-line citations also repeat start/end in `location.Lines`. Minimal facts already use bounded page-local file/provenance tables. Evaluate the same approach for multi-hit search, reference and excerpt pages: exact file identity once, line spans per hit, and full original document/mapped locations where necessary.

Keep responses independently interpretable: references resolve within the same page, not by remembering a previous connection. Preserve full source hashes, exact publication and original PDF/page/block/slide/table/region coordinates. Upgrade Explorer, Workbench, exports, budgets and citation readers together under a versioned representation. Compare many hits in one file with one hit per file; a table can make small heterogeneous replies larger. Do not shorten hashes, replace original coordinates with guessed source lines or change hit ranking to save metadata.

### R08. Remove repeated generic discovery/help prose where clients can still use tools correctly

Tool descriptions and response-mode argument descriptions repeat generic audit guidance already present in [server instructions](../crates/airk-mcp/src/remote.rs). Shorten redundant prose while keeping each tool's distinguishing semantics, required arguments, scope rules, bounds and interpretation limits. Deferred discovery may show a tool without initialization instructions, so a completely context-free description is not acceptable. Do not remove tools or strict schema constraints merely to reduce the catalog. Retaining callable compatibility aliases while emphasizing canonical arguments is a separate client-compatibility decision.

[UI help](../packages/vscode/src/explorerAssistance/tools.ts) full responses include summary, extracted steps and a body containing overlapping prose. Consider a versioned full-body view with metadata, while retaining existing focused summary/steps selectors. `get_template` includes operator contracts that help an agent use the template correctly; retain the self-contained default. A compact catalog-reference option is useful only when a caller explicitly knows that exact catalog. Measure tools/list bytes, actual client model-context use, help completion and argument-error rates; do not assume one byte equals one token.

### R09. Treat duplicate MCP encodings as a compatibility question

[`unified::success`/`failure`](../crates/airk-mcp/src/unified.rs) put the same JSON body into text and `structuredContent`; ordinary native [rendering](../crates/airk-mcp/src/lib.rs) is text-only, so this is not a duplicate in every tool response. The [MCP 2025-06-18 tool-result specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content) recommends a serialized text copy alongside structured content for backward compatibility. AIRK clients consume both forms in different paths.

First reuse body construction/serialization without changing the protocol. Remove a duplicate wire form only for an explicitly supported client path whose consumers and output-schema requirements are proven compatible; otherwise keep both. Do not infer client support from its product name or presume both forms enter the model context. Measure native logical bytes, outer protocol bytes and client-visible context separately. This is lower priority than the confirmed internal duplicate copies in R01–R04.

### R10. Reference identical retained UTF-8 source/extraction bodies

[Extraction payloads](../crates/airk-core/src/extraction.rs) contain full extracted text, while [retention](../crates/airk-store/src/blobs.rs) separately stores captured source bytes and the serialized extraction object. For an adapter proving exact UTF-8 equality, a versioned immutable body reference could replace the second inline text copy and reconstruct the same logical extraction.

Keep the captured source object. A live workspace read cannot replace immutable indexed evidence, crash recovery or source-bound validation. Binary documents, normalized extraction, composite regions and different encodings need their own treatment. Content-addressed cross-path source/payload reuse already exists, compact inventories already omit full facts/chunks, and `LocalChunk` already stores spans rather than another chunk-text string. This proposal targets the remaining body duplication, not those existing optimizations.

Measure equal-body bytes and actual compressed sizes first. Require format migration/rebuild policy, reference-aware retention/repair, bounded reads, original-location/citation parity and unchanged logical validator semantics. Combine with O38 span access so a small excerpt does not require reconstructing the entire logical object on every query.

### R11. Store lexical file metadata once per file

[`current_lexical_docs`](../crates/airk-store/src/current/lexical.rs) repeats path and serialized citation/source hash for each chunk. Normalize file identity separately from per-chunk ordinals and locations, then materialize only admitted candidates through bounded joins/lookups. Keep stable chunk identities/order, original coordinates, replacement/deletion/replay semantics and publication authentication under O37/O39.

FTS already uses external content, `detail=none` and `columnsize=0`. Its retained terms participate in incremental deletion/replay; they are not disposable duplicate text. Do not remove the lexical index or terms without an equivalent update/search design. Measure metadata bytes per file/chunk, write amplification, candidate lookup cost and migration size; avoid a smaller format that makes every result perform expensive random reads.

### R12. Avoid generating facts and attributes the selected profile discards

[`detail::select`](../crates/airk-ingest/src/detail.rs) removes unsupported detail after extraction, and [continuity preparation](../crates/airk-ingest/src/continuity/mod.rs) can compute semantic boundaries before that filtering. Pass the published detail policy into producers so unneeded fact families and rich attributes are never constructed, provided they are not inputs to required definitions, relationships, semantic boundaries, continuity or embeddings. Search Only already has some producer short-circuits; audit actual remaining paths.

Preserve every fact and call occurrence currently promised by Agent Lean. This is not a recommendation to reduce that level's capabilities or silently exclude generated/vendor files. Reconstructing a rich string from a retained span is appropriate only when exact equivalence is proven; signatures, written types and mapped document facts are not always one verbatim contiguous span. Measure generated-versus-published records, allocation/CPU by producer and unchanged fact/relationship/semantic output before enabling suppression.

### R13. Stop producing unused source-comparison measurements

Every artifact upsert currently [loads retained evidence for `SourceContextSize::measure`](../crates/airk-store/src/current/metadata.rs). [That measurement](../crates/airk-core/src/usage.rs) builds hit representations and serializes them twice to account for nested MCP escaping. The persisted measurements are small; avoiding their input reads and temporary data is the main potential win.

Audit whether usage-disabled or comparison-disabled configurations need these rows at all. Prefer exact counting from already-loaded publication inputs, a streaming equivalent of the existing escaped-byte formula, or explicit background preparation when comparisons are enabled. Missing measurements must mean unavailable comparison, never invented savings. Preserve useful ordinary aggregate diagnostics and revision binding. Enabling the feature later must not trigger a full collection scan inside the next MCP query. Measure publication read bytes/CPU and whether the user actually requests the comparison (O13/O39).

### R14. Keep compression and capability reductions as separate experiments

[Bounded LZ4 compression](../crates/airk-store/src/compression.rs) with Off/Automatic/Space modes already exists; [the default is Off](../crates/airk-core/src/compression.rs). Benchmark Automatic for large source/extraction objects before designing another format. This reduces physical representation size without removing useful information, but decompression and whole-object amplification can hurt small reads. Apply any rewrite through controlled maintenance, measuring both size and query/restore latency.

A deliberately text-only collection could potentially omit semantic-only projections and create them later from retained inputs in an admitted background job. That is a capability/readiness tradeoff, not proven superfluous data: existing detail profiles deliberately preserve semantic boundaries independently of visible facts. Keep it opt-in and separately reviewed, with explicit future-enable cost, pipeline identity and coverage. Do not drop embeddings, original document mappings, captured inputs, recovery journals, provider provenance or stored evidence just because the current question does not display them. Existing vector selection exclusions and embedding-pack compaction already remove some unnecessary work/data.

### Acceptance and review order for data reduction

Start with R03 and the duplicated transport/display portions of R02/R04; then design R01 with continuation/export parity and R05's selective construction. These have concrete consumers that currently discard or repeat data. Evaluate R06–R09 against actual agent clients before changing default schemas. R10–R13 need writer/storage/producer qualification; R14 needs separate performance and product decisions.

For each accepted recommendation, record the old field/copy, its actual consumers, the new source of authority, default/full behavior, compatibility/migration and what remains available on demand. Measure construction, serialization, wire bytes, unique evidence bytes, allocations, UI formatting and persisted size separately. Compare exact citations, hashes, publication, validators, ordering, cursors, error/coverage/truncation behavior, exported/restored evidence and task completion. Test multi-file documents, imported assertions, ambiguous/moved files, partial pages, failed steps and small byte budgets. Reductions must not achieve a smaller response by concealing missing evidence or making a useful detail impossible to recover.
