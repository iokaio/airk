AIRK language support: next priorities

Research date: 27 October 2026 · AIRK 1.5.3 development source · recommendations only; no new language adapters implemented in this fix.

Recommended first batch: GDScript, VBA and MATLAB. AIRK already covers the major language families in the usage rankings. Its strongest remaining additions are specific ecosystem gaps. “Missing” below means no dedicated built-in structured extraction adapter; readable UTF-8 may still be indexed and searched through text fallback.

What the repository already implements

I checked the live adapter registry and selection paths. Dart, Scala, Elixir, R, Objective-C/Objective-C++, Perl, Groovy, Nix, Zig, Julia, Clojure, OCaml, Haskell, Erlang, F#, Fortran, COBOL, Delphi, Apex, Solidity and hardware/GPU dialects already have adapters. HCL, Dockerfile, Protobuf, GraphQL, build files and several embedded document formats are also represented.

The older additional-languages plan reflects earlier coverage and now lists implemented languages as missing. It should be treated as historical planning. Current component documents and code are more precise about limitations.

Existing Python syntax coverage means MicroPython is not automatically a wholly missing language. VB.NET does not cover VBA or VB6; Clojure does not cover Common Lisp or Emacs Lisp. Bash parsing does not establish every shell dialect. Grammar registration alone does not establish complete extraction or compiler-resolved references.

Admission requirements for a future language change

Each addition should include deterministic file/profile selection, bounded syntax or structural facts, original source spans and citations, explicit partial/error coverage, fixtures for comments/strings and malformed input, reuse/invalidation tests, and verified dependency licensing and native build compatibility. Keep language runtimes and source execution outside indexing. The first batch is a proposal for a separate change after semantic indexing has been accepted locally.
