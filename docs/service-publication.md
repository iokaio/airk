# Service publication and bounded readers

Native work now admits current-index reader and writer connections through a thread-scoped, at-most-thirty-second retry budget for typed current-store opening contention. The caller retains its grant and writer ownership, checks pause/cancel/lease boundaries, and reports a sampled publication wait. Only connection opening is retried; captures, caller transactions and committed publications are never replayed. Query threads keep immediate typed rejection and exact-request retry hints. Permanent I/O, permissions and corruption remain terminal. Final continuation/readiness observation uses the same bounded admission before acknowledging the job.

Historical October 25 format-140 mechanism evidence: a four-project source-publication/query regression exposed SQLite `BUSY_RECOVERY` during connection opening. Real locked-reader and locked-writer tests now pass, including finite admission, checkpoint cancellation, preserved revision identity and query-thread isolation. The original unretained native load failure and partial-readiness timeout are not assigned an exact cause; retained reruns pass, and the new exact-pair/final-source campaigns remain in progress.

The native 1.4 worker uses `collections-1.4/<collection>/incarnations/<identity>` and redb format 150 in 1.4.5. The SQLite boundary requires ownership-checked fresh setup and full indexing; no legacy database reader is retained. An owned `active.json` manifest selects its active incarnation. Default 1.4 clients use this namespace; separately installed 1.3 clients retain their old namespace. The separate owner/header version makes new state incompatible with older readers even if they are pointed at its directory. This is a rebuild boundary, not migration.

Manifest ownership now permits a bounded 100 ms wait for a short metadata handoff. Only actual OS lock contention is retried; a longer wait returns the typed `SelectionContention` marker with a 25 ms retry interval. I/O failures and invalid/aliased ownership files remain failures. Replacement-build ownership stays nonblocking, and reads do not wait for the duration of a build. The [read retry contract](service-retrieval.md) describes the structured MCP retry hint.

Service, project and manifest ownership guards explicitly unlock before closing. On Unix this prevents a descriptor inherited by a concurrent fork from extending a released owner's lock until that child executes. The regression duplicates the open-file description, proves the replacement can acquire after guard release while the duplicate remains open, and proves closing the old duplicate cannot release the replacement's lock. Lock names and unknown files remain in place.

## Ordinary publication

The collection's OS writer lock permits one publication coordinator. Shared redb snapshots preserve committed reads while bounded captured changes are prepared and applied. Authenticated lexical, catalog and DiskANN records and the new head commit coherently. Preparation captures authenticated afterimages rather than retaining a transaction across process lifetime.

Prepared and Applying are distinct durable intentions. Both preserve the prior committed head and evidence until target verification and atomic installation succeed. Recovery verifies retained source/model identities and uses captured inputs, never changed live sources. A later request selects the latest committed head; obsolete revision tokens fail explicitly. Cursors do not retain snapshots between requests.

Lexical pages, posting blocks, document/citation records and forward lists are authenticated under the selected publication. There are no SQL physical seals, FTS shadow rows or legacy rollback caches. Snapshot verification and writer-base reuse remain bound to the exact publication identity.

## Disk and request admission

The owning writer establishes a durable lifetime grant bound to the root, collection, incarnation and authenticated file identity. Database growth extends the grant and owner ceiling before the backend can extend the file. Actual logical length and admitted unused allowance are separate observations; dropping a handle or job reservation does not discard a valid lifetime grant. Root, collection and job capacity remain enforced.

Before Applying, the writer exercises the captured installation under an ephemeral savepoint, verifies the target, samples allocator high-water including metadata padding, and restores the exact Prepared roots. A durable replay-admission receipt binds the descriptor and funded ceiling. Restart replay retains that allowance without requiring a new job reservation. Failed backend I/O can require existing readers to drain before the same owned handle reopens; typed pressure is not reported as successful recovery. See [the storage plan](storagekv/storagekv-design.md).

Each service read owns a redb snapshot and a shared OS object-protection lease. Ordinary commits can proceed, while deletion and manual compaction require exclusive ownership and defer or reject while readers remain. Captured scan work and pending journals retain separate ownership. Expiry does not release an OS lease: its actual holder must finish or exit.

Service snapshots expire after 120 seconds; materialization and bounded query-work checks reject expired or canceled work. A direct query exceeding 125 seconds exits its lock-bearing project worker rather than assuming future cancellation stopped native work. Only confirmed process reap returns its allowances. Storage I/O is not guaranteed to be preemptible in place.

## Replacement handoff and retirement

An activated worker creates an owner receipt binding the canonical source root, data root and collection. A durable initial-slot receipt precedes directory creation. Each slot has its own incarnation identity; the database owner must match it. The collection writer lock remains outside all resettable slots and serializes configuration changes and publication across incarnations.

A rebuild records an owned intent before creating a unique sibling slot. It copies only bounded, owner-validated saved source/extraction/vector/compression/scan configuration. Model input files remain in their configured data root. Usage policy and its ledger stay at the logical collection directory and survive the handoff. Both old and replacement databases, retained objects and grants count toward quota. Insufficient headroom fails while preserving the last readable index; there is no implicit offline deletion fallback.

Kernel validation checks the replacement's retained inputs in revision-bound pages, measured source coverage and unchanged saved configuration. The store authenticates its lexical pages/postings, bounded complete graph and map, fresh incarnation, settled publication and expected prior head. This work, quota inventory, metadata serialization and synchronization finish before request selection is excluded. The short final lock rechecks the selection manifest and atomically replaces its pointer. Windows never needs to rename a live database directory.

Each native MCP request selects its incarnation and acquires an OS object lease while manifest handoff is excluded. Idle sessions cache no such lease. An already admitted request may finish against the old incarnation; a later call, including one on the same direct connection, selects the replacement. Scoped tokens expire against its new head. A helper loading retained model objects holds object protection as well; a cached retained model keeps that protection until its actual model handle is dropped. Timer expiry never authorizes removal beneath a live holder.

The selection manifest records the rebuild job ID and exact committed token. After process death, an activated replacement worker reconciles a matching older running job with that receipt before conservative generic recovery. A pre-switch abandoned candidate is classified for retirement without opening its unfinished database; a completed switch stays selected. Bounded owned metadata scratch can be discarded under the recovery locks. No unactivated child reads project state.

Retirement retains at most eight old/canceled slots and refuses additional rebuild admission when that bound is reached. The store's retirement operation obtains the stable writer and exclusive old-object lease, validates the complete deletion set, removes at most 4,096 known files per pass, and releases old incarnation grants only after removal is proven. Unknown files, aliases, foreign owners and live readers preserve the directory and capacity for explicit follow-up. A receipt survives partial removal and the gap between deletion and grant retirement. Native console/automatic maintenance reporting remains part of the control/UI integration.
