# Service publication and bounded readers

The opt-in service worker uses `collections-1.4/<collection>/incarnations/<identity>` and SQLite format 140. An owned manifest selects its active incarnation. Default 1.3.x clients continue to select their existing namespace. The separate owner/header version makes new state incompatible with older readers even if they are pointed at its directory. This is a rebuild boundary, not migration.

Manifest ownership now permits a bounded 100 ms wait for a short metadata handoff. Only actual OS lock contention is retried; a longer wait returns the typed `SelectionContention` marker with a 25 ms retry interval. I/O failures and invalid/aliased ownership files remain failures. Replacement-build ownership stays nonblocking, and reads do not wait for the duration of a build. Structured MCP retry-hint serialization remains part of Phase 7 cutover.

Service, project and manifest ownership guards explicitly unlock before closing. On Unix this prevents a descriptor inherited by a concurrent fork from extending a released owner's lock until that child executes. The regression duplicates the open-file description, proves the replacement can acquire after guard release while the duplicate remains open, and proves closing the old duplicate cannot release the replacement's lock. Lock names and unknown files remain in place.

## Ordinary publication

The collection's OS writer lock permits one publication coordinator. Its request gate is shared while it prepares and replays bounded captured changes. SQLite WAL provides committed snapshots to concurrent readers; lexical rows and their physical seal, authenticated map records, DiskANN graph rows and the new head commit in one transaction. Preparation still computes a target seal, rolls back and captures replay inputs. Moving that work outside reader exclusion does not remove its cost or establish a latency result.

Prepared and Applying are durable intentions. In format 140 they leave the prior committed head and all of its evidence intact; a reader can use that snapshot until the coherent new head commits. Startup treats either intention as recovery work. Recovery uses authenticated captured inputs rather than changed live source. A later request selects the latest head; a supplied obsolete revision fails explicitly. No cursor retains a snapshot between requests.

Main-file cache witnesses cannot authorize WAL reuse. Service reads hash the physical FTS shadow rows through their pinned SQL snapshot, including overlay content, and compare the authenticated lexical manifest. The legacy rollback cache remains limited to its existing format. Within one publication, tracked row changes can reuse the already verified writer base.

## Disk and request admission

Before the first SQLite open, including recovery, the owning writer creates or adopts a durable quota grant bound to the source root, collection and incarnation. It covers the admitted main-file capacity, 64 MiB WAL, 128 KiB SHM and 192 KiB allocation slack. The logical quota report conservatively includes full outstanding allowances alongside measured file lengths; it is not an OS filesystem quota. The allowance survives handle drop and process exit. Ready/orphan transaction cleanup must preserve this lifetime allowance. Capacity growth reserves the larger lifetime bound before publishing the new owner capacity. Existing databases with missing allowances fail closed.

The explicitly selected native VFS checks WAL writes, growth truncation and preallocation hints before delegating to the platform, disables chunk rounding, and checks SHM region mapping before allocation. It leaves SQLite's process default unchanged and shares at most eight immutable limit registrations. Full/busy outcomes preserve the last committed snapshot and require retry after reader/checkpoint pressure is relieved. File checks reject oversized, linked or redirected sidecars and any rollback sidecar before SQLite opens them. Checkpoint growth remains covered by the main-file allowance.

Every format-140 SQLite reader/writer enables and verifies `SQLITE_FCNTL_PERSIST_WAL` before issuing statements. Final close still checkpoints, but retains the already admitted WAL/SHM names instead of unlinking them underneath another opener's file validation. SQLite's [file-lifecycle contract](https://www.sqlite.org/walformat.html#file_lifecycles) documents this distinction. The main/WAL/SHM limits and hard-link/reparse checks are unchanged; owned retirement remains responsible for removing these files. Legacy rollback-mode connections are unchanged.

Each service read owns both its SQL transaction and a shared OS object-protection lease. Admission and reclamation exclusion use the same gate. Ordinary commits can proceed, but object deletion requires exclusive ownership and defers while any old or current read remains. Captured scan work and pending journals retain their existing separate ownership. Expiry does not release the OS lease. Its actual holder must finish or exit before reclamation proceeds.

Service snapshots expire after 120 seconds; checks around materialization and SQLite progress callbacks reject expired work. A direct query exceeding 125 seconds exits its lock-bearing project worker rather than pretending that cancellation of an async future stopped native work. Only the supervisor's confirmed process reap returns its allowances. This is a finite failure boundary, not a guarantee that storage I/O can be preempted safely in place.

## Replacement handoff and retirement

An activated worker creates an owner receipt binding the canonical source root, data root and collection. A durable initial-slot receipt precedes directory creation. Each slot has its own incarnation identity; the database owner must match it. The collection writer lock remains outside all resettable slots and serializes configuration changes and publication across incarnations.

A rebuild records an owned intent before creating a unique sibling slot. It copies only bounded, owner-validated saved source/extraction/vector/compression/scan configuration. Model input files remain in their configured data root. Usage policy and its ledger stay at the logical collection directory and survive the handoff. Both old and replacement databases, retained objects, WAL/SHM and grants count toward quota. Insufficient headroom fails while preserving the last readable index; there is no implicit offline deletion fallback.

Kernel validation checks the replacement's retained inputs in revision-bound pages, measured source coverage and unchanged saved configuration. The store authenticates its FTS shadow rows, bounded complete graph and map, fresh incarnation, settled publication and expected prior head. This work, quota inventory, metadata serialization and synchronization finish before request selection is excluded. The short final lock rechecks the selection manifest and atomically replaces its pointer. Windows never needs to rename a live database directory.

Each native MCP request selects its incarnation and acquires an OS object lease while manifest handoff is excluded. Idle sessions cache no such lease. An already admitted request may finish against the old incarnation; a later call, including one on the same direct connection, selects the replacement. Scoped tokens expire against its new head. A helper loading retained model objects holds object protection as well; a cached retained model keeps that protection until its actual model handle is dropped. Timer expiry never authorizes removal beneath a live holder.

The selection manifest records the rebuild job ID and exact committed token. After process death, an activated replacement worker reconciles a matching older running job with that receipt before conservative generic recovery. A pre-switch abandoned candidate is classified for retirement without opening its unfinished database; a completed switch stays selected. Bounded owned metadata scratch can be discarded under the recovery locks. No unactivated child reads project state.

Retirement retains at most eight old/canceled slots and refuses additional rebuild admission when that bound is reached. The store's retirement operation obtains the stable writer and exclusive old-object lease, validates the complete deletion set, removes at most 4,096 known files per pass, and releases old incarnation grants only after removal is proven. Unknown files, aliases, foreign owners and live readers preserve the directory and capacity for explicit follow-up. A receipt survives partial removal and the gap between deletion and grant retirement. Native console/automatic maintenance reporting remains part of the control/UI integration.
