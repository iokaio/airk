# Current-index storage foundation

> Historical 1.2.0 foundation record. Version 1.3.0 replaces the Tantivy adapter and its private lexical forks with FTS5 in the current SQLite transaction (format 126). See [current operation](current-index-runtime.md) and the [replacement rationale](index-sharding-review.md#decision-replace-tantivy-with-sqlite-fts5). The stage descriptions below retain their original implementation context.

This records the storage foundation developed in S7 and integrated into production in S8 of the [indexing optimization plan](indexingenhancements.md). The normal kernel, CLI and MCP routes now use it. See [the current runtime contract](current-index-runtime.md) for the complete 1.2 behavior and rebuild boundary. These APIs do not read or convert an older index. Earlier format numbers below describe development steps; the adopted database format is `user_version=120`.

## Ownership and data

`airk-core::graph_storage` defines bounded record/proof contracts. `airk-retrieval::vector::mutable` runs the pinned DiskANN insertion and search algorithms. `airk-store::current` owns persistent records, authentication, gates, capacity admission and replay. SQLite is the local record provider and transaction boundary; it does not perform vector similarity search. DiskANN remains the vector engine.

The authoritative `current.sqlite3` has one current head, graph records, graph authentication nodes and at most one pending transaction. A head binds the collection, original source root, fresh incarnation, commit sequence, graph instance/specification, allocation/live counts, graph root, catalog root, lexical commit and selected lexical directory sequence. A sequence identifies current evidence; it is not a retained searchable generation. Equality is the only relationship exposed by `CurrentToken`.

The S8 catalog step adds a proof-checked keyed map anchored by the head's catalog root. Keys hash the scope, a fixed namespace and the complete identity. The first 16 hash bits select a bucket of at most 128 sorted full keys and 512 KiB of exact values. A 16-level sparse tree authenticates the whole bucket, including membership and absence. Complete enumerations traverse nonempty branches from the trusted root with independent node, entry and byte limits; missing child rows or buckets fail the read. Artifact records contain compact captured retained references. Readers authenticate those records and still verify their referenced source/payload objects before presenting their content as evidence. The format is rebuild-only (`user_version=101`); no reader converts the preceding isolated foundation format.

A catalog-only artifact change can commit its bucket paths and new head in one rollback-journaled SQL transaction under the exclusive gate. It verifies captured retained inputs, charges a durable recovery allowance, advances the sequence on add/edit/delete and leaves an unchanged record as a no-op. A crashed SQL transaction rolls back or commits atomically; an orphan allowance remains until the owning Ready writer retires it. The combined catalog, lexical and graph path is described below. The runtime uses the combined transaction below.

A bounded, poison-on-error map plan now overlays touched buckets and branch hashes in memory. It proves each planned key against the evolving root without modifying the committed SQL tree, then predicts the exact root for a multi-key update. The catalog-only writer compares that prediction with its transactional SQL replay before advancing the head. The combined S8 journal stages and replays ordered artifact, vector, occurrence and fact-index operations against the same prediction.

The current journal stages ordered map afterimages alongside captured inputs and sealed graph afterimages. A pending descriptor binds the count, bytes and digest of the map rows, and the prepared head binds their predicted root. Applying verifies the staged rows before it changes visibility. Final replay updates graph records, map buckets and authentication nodes in the same SQLite transaction, requires the exact predicted root, then advances the one current head. Aborting an unapplied preparation removes staged map rows. The map replay step used rebuild-only `user_version=102`; later lexical binding and reader steps advance the format below. Typed fact postings and the changed-artifact runtime route use this transaction; retained occurrence-body verification is described below.

The S8 mapping contract has an exact embedding-key binding to one physical graph ID and at most 2,048 sorted unique occurrence IDs. The graph scope digest binds graph instance and specification, and current reads check the authenticated graph record's key and live state. An ANN candidate must resolve by its physical ID; a live candidate with no binding fails instead of disappearing from results. Each occurrence ID addresses an authenticated pointer with path, source/payload hashes, the retained extraction-object digest and required chunk/span membership. Preparation verifies those spans against the captured extraction. Pointer reads confirm the current artifact's source hash; `CurrentRead::occurrence_hit` also re-resolves the exact pointer, verifies retained extraction/source bytes and reconstructs its original citation body. Unicode, contiguous membership and native/mapped location boundaries are enforced. A stale or modified pointer fails, and synthetic embedding context is never returned as evidence. The neutral core renderer shares one mapping budget across units of the same artifact. Production search uses these checks under one request gate.

The isolated current lexical adapter uses a new Tantivy schema without corpus-global ordinals. A document ID hashes its exact artifact path and local chunk number; replacing one artifact deletes only that path's documents, leaving unrelated IDs and documents in place. Mutations use the charged directory and synchronize the committed directory before returning. The runtime binds the resulting immutable segments and metadata to the current head, captures replay inputs and verifies candidate completeness. Engine merges and compaction can still rewrite older segments and must be measured and quota-admitted.

A bounded lexical manifest lists the exact active Tantivy segment files and `meta.json`, with lengths and SHA-256 digests. Its canonical digest is bound to `CurrentHead.lexical_commit` in the isolated current store. After an update, capture can reuse a previous trusted digest only for a retained immutable segment name of the same length; mutable `meta.json` is always rehashed. A reader's full verification checks every listed file, the current schema and Tantivy's active-file set, rejecting missing or same-size corrupt files. The kernel verifies these files on each fresh reader. This remains potentially O(index size); no constant total query or update I/O claim is made. S10 owns further measured caching improvements.

An isolated private lexical fork can now hard-link the verified base's active immutable segment files into a sibling staging directory, copy `meta.json`, regenerate Tantivy's managed-file inventory, and run the changed-path update there. The base remains readable and unchanged if staging fails. A private manifest is checked against newly written files and the inherited verification ticket before the candidate can be committed. It requires same-filesystem hardlinks and conservatively charges the full logical base size as temporary headroom even though the unchanged segment payloads are not copied. This makes update time depend on file count, changed documents and any Tantivy merge, but near-quota updates may still be denied until hardlink-aware accounting is qualified. The runtime recovers the selected fork and reclaims unreferenced forks under the exclusive gate. Cross-platform and power-loss qualification remain open.

The store now binds the exact lexical manifest bytes to the current head. Sequence-zero initialization is followed by an idempotent, exact-token manifest attachment; lexical reads reject a missing attachment. A replacement manifest is captured in Prepared and checked in Applying and final replay. Graph records, keyed map rows, lexical manifest bytes and the new head commit in one SQL transaction. The store checks byte bounds and the head digest; retrieval must decode the canonical Tantivy manifest and verify its physical files and active set. A cross-crate test exercises the private fork and graph insertion through that transaction. The isolated format is rebuild-only `user_version=103`; the adopted runtime uses the combined transaction.

An authenticated, request-scoped lexical reader now decodes the head-bound manifest and verifies all active files before it opens Tantivy. Conjunctive term and escaped path-prefix clauses return at most the requested candidate count plus one lookahead; a stable digest-prefix sort key replaces corpus-global ordinals. Each returned document is checked against its path/local stable ID and stored citation. The kernel compares candidates with the current catalog and retained chunks under the same read gate before presenting them as evidence. The Tantivy schema is rebuild-only `current-lexical-2`, and the isolated database format is `user_version=104`. Full file verification per new reader remains potentially O(index size); caching improvements belong to S10, and cross-platform qualification remains open.

A public changed-artifact preparation method derives the target catalog root from sorted, unique upserts and deletes. It captures verified retained upsert metadata and the replacement lexical manifest with the sealed graph under one durable intent; the SQL commit still swaps their map, graph, manifest and head rows together. The owner must authenticate the private Tantivy candidate before calling it. The occurrence-aware variant also stages new vector bindings and exact citations. Typed fact postings and all normal runtime routes use this publication boundary.

The kernel now has an isolated lexical materializer that holds one `CurrentRead` while checking each Tantivy candidate against the authenticated current artifact record, retained extraction and original source object. It binds the candidate set's lexical digest to that read head and requires exact local chunk text and coordinates, source hash, stable identity and query-term membership before enforcing the response text budget. It caps aggregate validation reads and returns the exact `CurrentToken`; budget exhaustion is an error, not a complete response. A cross-crate test covers a real retained artifact, an old lexical digest, tampered candidate payload and truncated text. Normal CLI/MCP search uses this materializer and returns the versioned current token.

The head now selects a physical immutable Tantivy directory by `lexical_sequence`, with `lexical-0` at bootstrap. A transaction capturing a replacement manifest must select its target sequence; graph-only updates retain the previous selection. Pending replay checks that relation before Applying, and current tokens bind it under head digest domain 2. This isolated format is rebuild-only `user_version=120`. Startup verifies the selected directory; cleanup removes only unreferenced old/orphan forks after the reader gate drains.

The isolated kernel reader now derives the selected directory from the pinned head, decodes its committed manifest and verifies active files before opening Tantivy. The store has explicit Ready-only lexical reclamation under the exclusive gate: it first checks the selected manifest and owned directory, bounds root entries, candidate directories and flat file entries, then removes only unselected `lexical-N` forks and interrupted `.current-lexical-*` staging directories. Missing selected state, pending work, symlinks or nested candidates stop cleanup before deletion. A Windows cross-crate test removes old hardlink forks and confirms the selected fork remains searchable. Startup recovery and post-commit GC use these checks. Qualification on other platforms remains open.

An isolated restart coordinator now opens the exact owner-captured database capacity under the writer lock and exclusive gate. Ready verifies its selected fork. Prepared verifies the private target and captured inputs before advancing, or aborts to the verified old head if it can still safely abandon the uncommitted intent. Applying rechecks the target and replays; missing or corrupt target files leave reads unavailable instead of substituting an old revision. A cross-crate test exercises valid and missing forks in both phases. Normal startup calls this coordinator. Store fault tests and forced process exits at Prepared/Applying cover the Windows recovery boundary, including recovery through the shipped CLI and MCP.

The current mapping format now includes a path-local occurrence index. Its authenticated value holds an exact source hash and count; occurrence IDs derive from collection scope, path, source hash and ordinal. Changed-artifact preparation can retire only that path's pointers, update shared vector memberships and require an exact matching graph live/tombstone state. The read helper checks each pointer's ordinal against the index and current catalog source. The occurrence-aware preparation method attaches new or shared graph nodes with their exact captured spans; the reader verifies and materializes their retained bodies. The production updater uses this mapping.

Physical graph IDs append monotonically. ID zero is a non-live DiskANN search seed; an empty store initially has no allocated records, and the retrieval provider creates that seed. Each other ID retains its original exact embedding key. Deletion marks a node non-live while leaving its edges available for traversal. Resurrection of the same key preserves its ID. The provider filters non-live nodes before returning hits and refills within one shared read/candidate budget. A budget-limited result explicitly reports `partial`.

## Bounded integrity and preparation

Every committed graph record is authenticated through a 32-level sparse Merkle tree. Leaves bind the complete graph scope, physical ID, exact embedding key, live bit and exact fixed-size record bytes. Branches bind their position and children; canonical empty subtrees are scope/height-specific. Allocation/live counts belong to the trusted head. A checksum stored beside a mutable record alone would not protect against replacing the record and its checksum together.

DiskANN prepares updates in a private quota-backed SQLite overlay. Base reads verify committed proofs; private dirty records have scoped checksums. Repeated neighbor writes coalesce to one final afterimage per ID. Sealing propagates only those final records through their authentication paths, bounds the streamed descriptor, and drops the base read handle. It does not buffer or copy the complete graph. Any failed mutation, read limit or panic poisons the candidate. A poisoned candidate cannot be published.

The low-level default overlay ceiling is 256 MiB and one million dirty records. Production indexing selects a quota-backed capacity of one quarter of its remaining preparation allowance, up to the 4 GiB hard ceiling. Graph operations and cumulative logical reads are saturating diagnostic counters without transaction-wide cutoffs: repeated neighbor visits do not themselves grow resident memory or retained storage. Logical read counters include proof bytes and are not measurements of physical device traffic. Per-insert/search read budgets, exact record validation and quota-backed SQLite capacity remain enforced. S10 evaluates caching after this correctness baseline. See [runtime capacity](current-index-runtime.md) for coordinated file, mapping and cache allowances.

## Readers, writers and recovery

The lock order is lifecycle guard, collection writer, current-index gate, then quota ledger. Gate files live outside resettable collection directories. A request owns a shared gate and its SQLite read transaction until all providers and response evidence have been released. The writer needs an exclusive gate. Idle caches retain no current read handles. Public routes and usage calculations hold their current request context through evidence materialization.

The durable phases are:

| Phase | Read behavior | Recovery action |
| --- | --- | --- |
| Ready | Read the current head | Clean up unowned maintenance allowances if necessary |
| Prepared | Read the unchanged base head | Validate captured inputs and afterimages, then apply or explicitly abort |
| Applying | Report recovery required | Replay captured component changes and finish the exact target |

Preparation stores ordered, bounded retained-input references and the exact graph afterimages before entering Applying. Recovery verifies retained source/payload/model identities and never substitutes live source or reruns a partially completed DiskANN insertion. Graph rows, authentication nodes and the new head commit in one SQL transaction. Repeating a completed commit cannot allocate new IDs. A cleanup failure after Ready is a maintenance error on a successful commit, not a claim that publication failed.

Initialization has a separate bounded owner header and captured bootstrap marker. An interrupted bootstrap can resume only its exact empty/unversioned database or exact committed initial head. An arbitrary database error is never interpreted as an empty collection. Ownership and sidecar bounds are checked before SQLite may recover a hot journal. The runtime adds a captured bootstrap recipe for lexical/configuration initialization, recovers physical forks and coordinates reset and cleanup with the same gates.

## Capacity and durability

Authoritative SQLite uses 4 KiB pages, `journal_mode=DELETE`, `synchronous=EXTRA`, no automatic vacuum, and a fixed admitted database ceiling. The exclusive gate permits this simple journal mode. EXTRA includes the directory synchronization associated with deleting a rollback journal; see [SQLite synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous). Statement failures abort the entire transaction. Savepoints, attached databases, virtual tables and triggers are prohibited so they cannot introduce an unaccounted second journal.

Before each write phase, admission includes remaining main-file growth and a conservative rollback-journal bound `P × (4096 + 8 + 2S) + 4S`, where P is the original page count and S is the effective sector size. The bound is tied to the pinned SQLite pager implementation; it is not a portable formula for arbitrary database settings. P is recomputed after Prepared, including before an abort. S is read through SQLite's VFS file pointer and normalized using the pinned pager's rules. Changing the SQLite version or journal restrictions requires requalification. The S8 capacity step permits monotonic ceiling growth while Ready: it reserves the larger allowance, synchronizes the new owner bound, reopens SQLite with the new page limit, and then retires the unused allowance. If the writer dies before or after that owner change, the next writer sees the exact old or new bound and explicitly retires the orphan. The runtime chooses power-of-two growth increments under quota; a large ceiling causes correspondingly large conservative reservations on later writes.

Recovery allowances are separate from disposable staging reservations. Their bounded metadata survives process exit and generic dead-lease cleanup. Only the owning writer, after examining the current journal outside the quota ledger, may release them. Existing files and the outstanding allowance are both counted conservatively. A failed next-phase admission leaves Prepared readable. Hot-journal files and their original-page/sector headers must fit the admitted capacity before SQLite opens them; [SQLite's recovery protocol](https://www.sqlite.org/lockingv3.html#dealing_with_hot_journals) explains why this check precedes a database query.

Metadata replacement synchronizes the file and, on Unix, its parent directory. On Windows it closes the temporary handle and uses [`MoveFileExW` with write-through](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw). Process-death tests qualify the exercised Windows and Linux container behavior. They do not establish power-loss durability on every filesystem or macOS qualification.

## S8 runtime adoption

The 1.2 runtime uses authenticated per-artifact catalog and exact-key/live-occurrence mappings, incremental Tantivy commits, captured replay, admitted database growth, request-scoped readers, retained-input ownership and bounded reclamation. Historical reads, checkpoints and rollback are unsupported. Old exact tokens and cursors expire explicitly. The fresh `collections-1.2` namespace never adopts 1.1 indexes or per-collection settings; sources and externally selected workspace/storage paths remain unchanged. Implementation and qualification limits are recorded in [the runtime contract](current-index-runtime.md).

## Current native discovery

Artifact transactions also maintain authenticated file/fact/relationship path postings. Selectors are domain-separated digests; each selector uses 256 fixed path-hash shards, each bounded to 4,096 paths and the map value byte limit. A reader authenticates every shard to establish a complete candidate set or absence. Changes rewrite only affected shards, with transaction byte/key ceilings; no mixed-map corpus scan is required. The current format is rebuild-only.

Native fact pages and relationship queries materialize candidates through verified retained extraction and original source bytes under the same current read gate. Fact cursors bind revision, filters and representation, preserve deterministic source order, and can advance over files with no matching facts. Evidence-work limits are independent of response-size limits. Relationship traversal reports truncation when work or response budgets are exhausted. Public discovery also merges authenticated imported producer assertions after checking their captured source/build bindings.

## Current update coordinator

The kernel `CurrentUpdater` now composes sorted captured artifact changes, the existing bounded embedding executor, exact-key reuse, path citation retirement/attachment, mutable DiskANN updates, a verified Tantivy fork and current-journal publication. The collection writer lock spans planning and publication; preparation readers drop before the exclusive publication gate. Post-commit lexical cleanup failures are maintenance failures on a successful commit. Process-exit tests cover both Prepared and Applying, including recovery after later live source edits.

Applied collection configuration and aggregate counters can travel in the same authenticated map transaction. Counters use changed-artifact deltas. Configuration changes require replacement of all current artifacts; selected detail and captured model assets must agree. Explicit bootstrap configuration initialization and owner-header scope discovery do not read old catalogs or migrate old collections. The runtime owns imported evidence, source/extraction/metadata/model/cache objects and bounded reclamation. Representative production latency and relevance qualification belongs to S11.

## Current query adapter

`current::search_current` holds one shared gate through exact-token validation, lexical/vector selection, reciprocal-rank fusion and retained citation rendering. Lexical and semantic votes share path/local-chunk identities; multi-chunk semantic bodies are emitted once. Semantic search uses the model objects named by authenticated collection configuration. Missing models fail explicitly, including hybrid requests; the adapter does not silently fall back. Expired tokens fail before inference. No current gate or engine reader remains in an idle cache.

Unfiltered queries use mutable DiskANN with live-node refill. Path-scoped queries authenticate file postings, path occurrence counts, pointers and key bindings, then compare distances within at most 4,096 graph nodes from at most 4,096 matching paths. Work is additionally capped at 16,384 pointers, 65,536 members, 64 MiB of pointer encoding and 256 MiB of retained evidence reads. Candidate omissions set truncation; malformed mappings and corrupt evidence fail. Output text is truncated only after fusion. Production search uses this adapter. Representative latency/relevance qualification belongs to S11.
