# Local ingestion and setup boundaries

Version 1.1.4 strengthens the F05, F09 and F10 boundaries from the [review](airkimprovements.md). These mechanisms protect local source reads and bound the built-in PDF worker; explicitly provisioned providers remain trusted executables.

## Source handles

Discovery metadata does not authorize the later read. Ingest opens the source through a dedicated read-only traversal. Unix uses directory-relative `openat` with `O_NOFOLLOW` for every component and compares opened file identity and change metadata. Windows opens non-reparse directory handles that deny deletion/rename, then opens the source with read sharing only, denying concurrent writes and deletion while it is held. File identity comes from the open handle. Both paths reject redirected ancestors and non-files, enforce byte budgets, and verify that the pathname still identifies the held file after reading. Detected changes fail the scan with its previous publication retained.

These checks cover path replacement, symlinks/reparse points and ordinary concurrent edits. They do not establish protection from a privileged actor changing mounts, a hostile filesystem implementation, or malicious in-place writes that evade the operating system's metadata observations. Unix permits ordinary concurrent writers and detects changes through metadata; it does not claim a transactional filesystem snapshot. Network filesystems remain unqualified.

## Process startup and PDF extraction

On Windows, providers start suspended without a console window. AIRK configures and assigns a kill-on-close job before resuming the initial thread. Any startup failure terminates and reaps the suspended process. On Unix, each child has a private process group. Timeout/output failures terminate the contained processes before pipe readers are joined.

The PDF adapter copies admitted bytes into a private temporary directory and starts the current AIRK executable in a hidden worker mode. No original source path is passed to that worker. The CLI dispatches it before constructing the async runtime, through the kernel into ingest, preserving dependency direction. A library host using PDF extraction must call `airk_ingest::pdf_worker::dispatch()` at startup too; lack of dispatch fails extraction and never falls back to an unbounded in-process parser.

The worker has a 15-second wall deadline, a 10-second CPU allowance, and a 512 MiB process memory limit. Windows also limits job memory and active processes to one. Unix uses `RLIMIT_AS` and `RLIMIT_CPU`; its address-space limit measures virtual memory, while the Windows job limit measures committed memory. These limits are not equivalent RSS measurements. Output pipes are capped, parsed output is at most 64 MiB of JSON, and accepted text remains at most 32 MiB. The parsed page tree is checked against 512 pages before rendering content streams; page text is bounded as it is written. PDF parsing and decompression themselves occur inside the worker limits. A bad page now fails extraction instead of silently accepting earlier pages. The `pdf-isolated/1` profile identity forces existing PDFs through the new adapter on their next index pass.

Malformed input, page/output limits, timeout, worker allocation failure or worker failure become the existing per-file extraction failure observation. PDF page-tree and inherited-parent traversal reject cycles, more than 64 levels, or more than 4,096 tree nodes before rendering. Aggregate discovery/read/corpus capacity failures remain pass-wide and retain the previous generation; parent-side worker infrastructure storage/memory exhaustion also fails the pass. No remote extraction service, shell-selected executable, or new dependency is introduced. Private worker files are removed after the process and descendants exit.

## Shell profile writes

CLI setup refuses symlinked or multiply linked profiles, redirected directory ancestors, non-files, invalid UTF-8 and profiles exceeding 1 MiB including the addition. Existing profiles are opened without truncation and appended through the verified handle, with exclusive creation for absent files and no-follow opening where Node exposes it. Handle identity, link count, size and timestamps are checked against the path immediately before appending. Other startup commands and login-profile selection are retained. Refused files report manual setup instructions; successful shell profiles remain idempotent.

Node does not expose a portable directory-relative write/locking primitive here. The helper therefore does not claim protection against an adversary creating a hard link to the held file in the final interval after validation. Its checks reject observed replacements and avoid reopening a checked path for writing.

## Validation scope

Windows tests cover source junction rejection, held-source write/rename denial, PDF page mapping through both the library worker fixture and distributed CLI, malformed PDF rejection, excessive-page preflight, deep/cyclic page trees, bounded text writing, memory allocation rejection, immediate descendant termination, process timeouts and pipe limits. An original compressed fixture expands below 128 KiB of stream bytes into 33 MiB of text and is rejected within the 15-second worker deadline (the complete local test, including fixture creation, took 16.2 seconds). Extension tests cover hard links, oversized profiles, redirected ancestors, deterministic replacement between inspection/open, ordinary profile preservation/idempotency and the isolated Windows PATH script. Unix-specific handle replacement and native shell tests run on their respective CI platforms. A local Windows result does not qualify Linux/macOS enforcement, installed-editor workflows, network filesystems or a broad adversarial PDF corpus.
