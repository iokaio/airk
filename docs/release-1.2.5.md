# AIRK 1.2.5 candidate — not released

> Historical local candidate record, superseded by the [1.3.0 candidate](release-1.3.0.md). The 1.2.5 binaries and validation below describe their named local build only.

Native, extension and lockfile versions were synchronized at 1.2.5 for this candidate. It was built for local review, but no release or Marketplace listing was published for 1.2.5.

## Release summary

- **Earlier evidence during indexing:** MCP can start before the first source scan finishes. Committed lexical passages and facts become searchable while discovery continues; vector work follows through bounded background batches. Results still identify incomplete discovery and semantic coverage.
- **More reliable updates:** known saved paths use scoped indexing, rebuild requests survive a busy writer, and a queued request waits for its own revision-bound completion report. The editor clears stale waits when a collection binding changes and shows coverage as pending until a new inventory is measured.
- **Storage upgrade:** SQLite FTS5 replaces Tantivy lexical storage alongside DiskANN. A recognized older 1.2 collection is rebuilt from saved source files when the extension next indexes it; native CLI users run `airk index --full`. The rebuild preserves original files, collection ID and saved settings, but replaces the old derived index.
- **MCP and model setup:** search returns focused snippets by default, optional terse replies retain citation identity, and the unsupported `airk_history` tool is removed. New model setup uses the helper's CPU capability report and shared catalog; automatic selection remains FP32 MiniLM.

The follow-up's guarded lexical cache changes warm-read integrity verification as [documented separately](indexing-follow-up-2026-10-21.md#lexical-cache-integrity-contract). No end-to-end speedup, installed-editor acceptance or other-platform qualification is claimed for the final follow-up. The validation history below identifies which candidate each result covered.

## MCP evidence and tool catalog

The former `airk_history` tool is retired because AIRK 1.2 retains only one current index, so the endpoint could return only an unsupported error. The source catalog has fifteen read-only MCP tools. The published 1.2.4 helper still has sixteen, including that unsupported endpoint. Historical evidence and checkpoints remain unsupported. Existing clients with an explicit `airk_history` allowlist entry must remove it when adopting the new helper.

Search now returns a focused excerpt of at most 768 UTF-8 bytes per hit by default; `full_chunks: true` requests the complete indexed chunk subject to the existing byte budget. Snippet citations keep the source hash and adjust indexed line coordinates. A cut sets truncation, and `airk_read_file` or `airk_context` expands selected evidence. Search remains approximate across mixed code and documents. A related style guide or book passage does not establish an application's configuration; scope a known project with `path_prefix` and inspect the implementation.

Set `AIRK_MCP_RESPONSE_MODE=terse` on an MCP worker to replace repeated full publication/readiness/indexing blocks in evidence replies with a compact coverage summary and exact publication token. The default full envelope remains available. Status, capabilities and change validation retain their detailed reporting. Terse output still includes citations, hashes, validators and truncation; it does not prove live-source freshness.

MCP runs four evidence and two control requests at once, with up to sixteen additional requests waiting for a permit for five seconds. Queued requests are cancelled without consuming worker capacity. A full queue or timeout returns a retryable error. The control pool remains separate.

VS Code MCP definition resolution and the helper check no longer wait for a full initial index. The helper check can verify its handshake and fifteen tools before the first publication, reporting indexing as pending; search becomes available as soon as a base batch is committed. The dashboard shows processed and committed file counts, elapsed time, and whether published evidence can already be served. A scan with no native progress for ten minutes is stopped with a recoverable error; the existing one-hour total cap remains. A scheduled semantic batch has a twenty-minute cap, retains earlier committed evidence, and can be retried through Diagnose & Repair or Resume after the cause is addressed. These bounds do not make a slow scan faster, and a single observation cannot prove a process is stuck.

The semantic dashboard now keeps the published completed-file percentage visible while a batch runs, with an animated working indicator and live elapsed time. Native preparation and computation-stage observations update the activity label before the batch commits. Only the durable commit advances the completed count; the batch cutoff appears as a warning after three minutes of work.

`known_hash` now fails explicitly when a present indexed source has a different hash. `airk_references` selects candidate chunks from the current authenticated lexical index before verifying exact-case whole identifiers in retained source. It remains bounded and textual: strings, comments and declarations can match; a truncated result does not prove complete impact coverage. In this 1.2.5 candidate, Agent Lean and Rich Structure omitted generic call occurrences, so relationship results could be empty even where callers existed. The later [1.3.0 candidate](release-1.3.0.md) changes that profile behavior; relationship results still cannot establish a complete resolved caller graph.

## Large-workspace indexing

Known changed paths now support direct `index --paths`, durable `index --scheduled --paths` and `schedule enqueue --paths` requests, including additional-root aliases. Editor/native watcher hints coalesce by revision and survive events during an active pass. Confirmed hinted removals may retire that exact path; directory, ignore/configuration and incomplete-inventory hints require complete reconciliation. Each admitted source is hashed. Untouched bindings retain their indexed hashes and do not become claims of live freshness.

Unchanged-source reuse checks retained object presence/type/length without decoding unused copies. Byte authentication remains at consumption and explicit verification. Scoped updates avoid unrelated source traversal; compact artifact comparisons avoid repeated JSON serialization. Ordered reuse results no longer empty the extraction pool.

The editor submits settled requests without a duplicate native debounce, uses a 1 s minimum interval by default, and leaves coverage inventories to explicit/periodic observation. Accepted periodic stale coverage queues reconciliation subject to mode and pause. Scheduled CLI semantic runs reuse a model across up to eight 32-file batches with a 60 s soft budget, yielding between commits for source work or pause and sweeping unreferenced objects once per drain. Returned readiness avoids a post-run status process; returned timings are logged and recorded in native usage. Status/change freshness includes the last scheduled source-pass timings, scope and complete inventory timestamp. See the [dated review and qualification record](indexing-speed-review-2026-10-21.md); broader speedup claims require its measurement gate.

Progressive source publication no longer runs a semantic batch inline after every base batch. Source discovery continues while pending semantic work is persisted; the existing scheduler processes it after the source scan. Lexical search and facts remain available from committed batches. On a cold scan, vector evidence starts after discovery; on compatible updates, unchanged vectors remain available and changed inputs lose incompatible vectors at publication.

The initial source batch targets 32 changed files or two seconds of scanning. Later count targets grow after every publication up to 4,096 files, with the existing 64 MiB source-byte trigger. The interval between publications adapts to four times the preceding publication duration, bounded to 2-30 seconds of scanning. This reduces repeated transaction overhead when publication is expensive. Capture and publication can exceed that interval; it is not a wall-clock deadline. No physical shards, tool-triggered refresh or index history are added.

These changes address observed large-workspace delays without requiring another large-corpus benchmark before implementation. Correctness checks cover early lexical availability, deferred inference, subsequent semantic completion, bounded cadence, pause and retained-input recovery. End-to-end speedup has not been measured.

## Queued indexing and late completion

A 240-second scheduler join timeout previously appeared as an indexing failure in the editor even though the request remained queued and could complete in another worker. It now returns the typed `scheduled_index_pending` outcome with the requested scheduler revision. VS Code continues with `schedule wait <revision> --progress`, which joins that same request without enqueueing another scan or clearing pause/failure state. The dashboard identifies the queue wait. After at most three native joins, the extension displays still queued, releases its busy slot and revisits the same request after 30 seconds. Pause prevents continuation. Each helper invocation retains its execution and idle limits; closing the workspace or losing trust prevents another join.

Diagnostics recognize the specific earlier wait failure as superseded only when the native queue reports all requested revisions completed, no running or blocked request, and a completion timestamp after that failure. Current native failures still take precedence. Partial retained-input verification remains partial; a ready scheduler is not proof of every retained object. The original editor observation and event remain visible.

## Dependency review

SQLite FTS5 replaces Tantivy for lexical retrieval in the 1.2.5 source candidate, while retaining DiskANN. The [decision and rationale](index-sharding-review.md#decision-replace-tantivy-with-sqlite-fts5) explain the query fit, separate segment-publication costs, intended SQLite transaction integration, tradeoffs and rebuild requirements. FTS5 lives in the current SQLite database, with captured replay and one atomic lexical/map/graph/head commit. Tantivy and the retired 1.1 retrieval adapters are removed from Cargo dependencies. Database format 126 requires a full rebuild when upgrading from earlier 1.2 builds. Extension indexing detects recognized older formats and starts that rebuild automatically; CLI users run `index --full`. The existing collection ID and saved settings are preserved; see the [upgrade instructions](current-index-runtime.md#upgrading-a-tantivy-collection). Local FTS5 correctness checks are recorded below; package and platform qualification remain separate, and no performance improvement from the replacement is claimed.

[Issue #32](https://github.com/iokaio/airk/issues/32)'s request to replace the Git-sourced SQLite dependency was reviewed on 2026-10-21. The latest published `rusqlite` 0.40.2 / `libsqlite3-sys` 0.38.2 pair still bundles SQLite 3.53.2, which lacks the Windows extended-local-path WAL locking fix required by AIRK. The exact upstream commit containing SQLite 3.53.3 remains pinned pending a fixed registry release. This is an outstanding dependency-source limitation, not a completed fix. See the [dependency notice](../THIRD_PARTY_NOTICES.md) for provenance and the replacement gate.

## Review corrections (2026-10-21)

The format-126 candidate removes full text from FTS5 citation payloads and replaces hex terms with prefixed raw tokens (underscores preserved). Publication verifies its base once, then rehashes touched row groups during preparation/replay, with separate scans of SQLite's `WITHOUT ROWID` tables. Semantic/resource-only updates reuse that verified base within their transaction. Full base verification still scales with corpus size; a measured end-to-end speedup is not claimed.

Snippets are focused before the total response budget, terse rendering preserves usage attribution, and references load/charge each retained path once. Progress is collection-bound. Extension joins are bounded, queued work yields to other collections, structured errors tolerate intervening warnings, and a successful child exit wins an idle-timer race. Pause stays retryable, and failure-reporting capacity is reserved before scanning. Retained-repair counts accumulate across the bounded retry.

FTS5 BM25 and indexed path-column ranking remain deferred: this change preserves AND matching, exact prefix scope and stable identity ordering. Ranking changes need separate relevance qualification across mixed content. The full rebuild also removes retained copies/extractions/captured models, preserving original files and settings. Local format-125 candidates require rebuilding too. The prior qualification paragraphs above do not qualify this review candidate; checks for format 126 are recorded after completion below.

### Seven-item follow-up (2026-10-21)

The [follow-up review](indexing-follow-up-2026-10-21.md) implements durable rebuild enqueueing during active writes, stale editor wait cleanup, guarded lexical snapshots across requests/publications, typed late-completion diagnostics, consistent catalog validators, revision-bound bounded report history and explicit pending-rescan coverage with revision-based retry suppression. CPU capability/catalog changes are included; automatic INT8 remains future work. Contributor instructions now require a human DCO sign-off on every commit.

The lexical cache changes the previous full-physical-hash-per-request contract: warm reuse relies on filesystem identity/change witnesses and SQLite's change counter, with a Windows local-volume notification guard, thirty-second maximum age and full-verification fallback. Explicit integrity diagnostics bypass it. See the review for silent-corruption limits, bounded resource use and one-shot CLI behavior. No speedup or cross-platform qualification is claimed for these changes.
