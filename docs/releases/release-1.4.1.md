# AIRK 1.4.1 upgrade candidate

Installation and upgrades now display a VS Code progress notification with the current stage: version and payload checks, staging, native activation, agent connection updates, workspace setup and cleanup. Progress uses actual stages without an invented percentage. A connected-client preflight pauses the upgrade with a visible Retry Update action; success and failure remain explicit. VS Code owns the earlier VSIX installation UI, before AIRK can activate.

For Windows on-demand installations, activation now checks whether the owned stable launcher can be replaced before publishing an activation intent or draining the working service. A connected client that holds the launcher blocks the update at this preflight boundary. The extension shows MCP Servers, Retry Update and Show Details, and keeps the preceding service running. After clients disconnect, Retry Update performs the fenced activation and cleanup. The native owner drain polls every 100 ms with a 45-second deadline after shutdown acknowledgment; executable verification and control/setup work are additional steps. External MCP clients are not killed by this drain. Verified OS-managed login services retain their existing owned stop/maintenance path because that manager can itself hold the launcher; that platform/lifecycle matrix remains separately qualified.

October 25, 2026. This branch synchronizes the native workspace, all local crate lock entries, extension and npm lock entries at **1.4.1**. It is unpublished. Native runtime paths retain the compatible `service-1.4` family; project registrations, selected data locations and watching preferences are preserved. The [versioning process](../versioning.md) defines local candidate, CI, Marketplace and GitHub version agreement. Publication must use this checked-in version and tested main artifacts, not relabel the earlier 1.4.0 binaries.

The candidate includes the earlier service cutover, help/status diagnostics, automatic onboarding and executable-retirement work recorded in the [historical 1.4.0 notes](release-1.4.0.md). It adds a distinct installed extension version so VS Code can stage the update beside the previous extension directory instead of attempting a same-version replacement.

Existing recognized workspace Codex, Claude Code and GitHub Copilot connections are refreshed to the installed stable launcher and registered native binding. Other servers, environment, approval and disabled settings are preserved; missing entries do not enable agents. Unsupported/custom configurations and unsaved changes remain for explicit review. Installation exposes MCP Servers, Reload Window and Show Details, and warns about incomplete connection/cleanup work. External agents still need their own reconnection; changing configuration does not replace running clients.

The native installer stages an independently approved executable pair outside the extension directory, verifies and activates the replacement through the fenced service lifecycle, and retires the predecessor after success. Source/index data remains separate. Locked external clients can defer old payload cleanup and require reconnection and repair. Failed activation must retain the prior working selection.

An offline source-version check now runs in CI before packaging. Later Marketplace dispatch must request `1.4.1`; GitHub release uses `v1.4.1`. Release-time bump automation is a fallback, not another increment for this change. Main CI, signing, release rehearsals and publication remain separate authorized steps.

Local validation for this candidate is limited to installer/version-agreement checks at the user's request. The running-upgrade harness installs the previous VSIX into a private profile, retains MCP clients, installs the new VSIX while the prior editor is active, reloads, verifies that connected clients produce a visible preflight warning without draining the preceding service or creating activation/launcher-repair intents, disconnects those fixture clients, retries, verifies unchanged project binding/data location, and checks the new runtime versions and restart notification. Final results and unexecuted scenarios are recorded after the run. Full suites and native macOS/Linux upgrade qualification have not run for 1.4.1.
