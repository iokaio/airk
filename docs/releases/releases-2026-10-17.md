# AIRK 1.1.0–1.1.2: October 17, 2026 release summary

The three stable GitHub releases published on **October 17, 2026 in America/Denver (MDT, UTC−06:00)** combine workstation indexing, collection controls, storage efficiency and coding-agent setup. **1.1.2 is the latest of these releases** and includes the earlier changes. AIRK remains a local retrieval kernel: agents supply reasoning, source workspaces remain authoritative, and collection isolation, cited revision identity and bounded failure reporting remain in force.

## Build and release delivery

Starting with 1.1.1, new release tags match the package version without a build suffix; older tags remain valid. Publication checks prevent duplicate or mixed-version uploads. When both distribution destinations already contain a complete version, the workflow can prepare a draft next-patch PR subject to repository/organization permissions and human review; it does not bypass protected main or invent a contributor sign-off.

Extension publication can reuse the exact reviewed rehearsal packages after authenticating their commit, attempt, artifact IDs and hashes. Docker dependency-cache fallback can reuse a compatible configuration across manifest/version changes while Cargo still verifies the locked graph. Missing or incompatible artifacts fail explicitly. The 1.1.2 VSIX includes the pinned MIT-licensed `jsonc-parser` runtime and original license for targeted configuration edits. ## Workstation indexing and evidence detail

Automatic eligible-source sizing uses one eighth of detected machine memory, capped at **2 GiB**, with a **512 MiB** fallback when detection is unavailable. The largest automatic profile permits 256 MiB raw files, 4 GiB extracted text per collection, 100,000 extracted files, one million discovery entries and 8 GiB pass reads. **Extracted text remains capped at 32 MiB per file**; raw admission is not a promise that every admitted file can be extracted.

UTF-8 sources above 4 MiB and within the text ceiling retain complete searchable text and original line locations with explicit partial status, without structured parsing. Larger text is skipped with a reason. The shared inventory ceiling is now 512 MiB, including continuity metadata. These byte ceilings are not measured memory or runtime guarantees, and native parsers are not forcibly preempted.

Coverage reports source/extracted totals and the largest eligible files. When a collection budget is exhausted, the extension can offer a reviewed increase within native ceilings and retry once. Existing explicit policies, per-file bounds and disk quotas remain authoritative; failures preserve the previous publication. See [ingestion limits](../ingestion-limits.md).

| Index detail | Retained native evidence |
|---|---|
| Essential | Searchable text and exact citations |
| Balanced | Essential plus adapter-supported declarations, signatures, imports, structural/document facts and declaration continuity |
| Detailed | Full adapter-supported evidence, including individual calls and document-unit continuity |

New collections default to Balanced. Existing collections and older saved policies retain Detailed until changed. The dashboard distinguishes configured detail from published detail; a successful rebuild applies the new selection. Reduced detail is disclosed in MCP responses, and absent optional facts do not prove absent source behavior. Provider imports and history settings remain separate. See [extraction policy](../extraction-policy.md).

## Dashboard, storage and recovery

The Activity Bar dashboard brings collection cards, measured coverage, indexing controls, pause/resume, evidence detail, helper verification and setup into one panel. Storage selection holds new jobs and waits for active indexing to settle. Cancellation preserves the existing location and pause preference; changing folders leaves old indexes in place and requires agent configuration refresh.

Default quotas are **100 GiB per collection** and **500 GiB per storage root**. They are logical-byte ceilings, not reservations of that much disk space, and saved policies are preserved. Retention can target **1–9 searchable generations** (active plus zero to eight predecessors). New collections target active-only automatic retention; legacy collections without a policy remain manual. Live readers, checkpoints and selected history can protect additional data.

Automatic cleanup can run before/after publication and continue during quiet editor intervals. A changed retention target makes cleanup due without another publication. Capacity failures stop automatic indexing loops; resolving the cause and explicitly resuming or indexing is required. Concurrent writer contention stays queued, transient Windows deletion races receive bounded handling, and physical admission leaves additional headroom. See [storage quotas](../storage-quotas.md), [retention](../retention.md) and [extension behavior](../vscode-extension.md).

Immutable SQLite catalogs now share file/producer values and store binary source hashes while preserving complete public evidence. Publication can reuse unchanged native rows; a bounded cache reuses semantic validation while still authenticating current component bytes. This reduces repeated work without trusting timestamps or pinning obsolete generations. Lexical and catalog construction still perform generation-wide work.

The 1.1.1 follow-up fix journals prepared-publication ownership before immutable rename. After process death, recovery preserves committed receipts and authenticates uncommitted data, the expected head and reader exclusion before detaching owned data. This permits an immediate same-revision retry without adopting unknown directories or deleting committed evidence. See [operations and recovery](../operations.md#recovery).

## Coding-agent connections

**Connect Coding Agent** and **Manage Agent Connections** open the same agent picker and persistent guide. The guide keeps workspace, collection, storage, configuration, reload instructions and verification together.

- **Codex:** explicitly create a missing project `.codex/config.toml`; preserve existing TOML for manual merging.
- **Claude Code, Gemini CLI and Antigravity:** install a project JSON entry while preserving comments, unrelated servers and approval policy. Conflicts, invalid files, unsaved edits and redirected paths require review.
- **VS Code / Copilot:** explicitly enable AIRK registration and open separate MCP controls; the user completes client start/trust prompts.
- **Other clients and remote hosts:** use the guide's manual configuration route appropriate to the selected client and host.

Opening the guide does not force indexing. **Check AIRK helper** updates the selected collection and checks its native MCP handshake; the agent must separately discover its tools. Ask the agent to run `airk_status`, `airk_capabilities` and a known-phrase search, then verify collection identity and citations. Refresh generated configuration after helper or storage changes. See [agent integration](../agent-integration.md).

## Upgrade guidance

Install the 1.1.2 package matching the platform. Preserve collection IDs, source roots and storage bindings. Review saved ingestion limits, detail, quota and retention settings: new defaults do not silently replace explicit policies. Choose a new detail level or restore automatic limits deliberately, allowing time and temporary space for rebuilding.

Refresh client configuration to use the selected helper, root, data directory and collection, then reconnect. Existing Codex settings require a manual merge; JSON installation preserves other settings. A healthy helper or running server in VS Code does not establish another agent's connection.

The larger objects introduced in 1.1.0 may exceed 1.0.0 reader limits. A packaged Windows 1.1.0 → 1.1.1 helper upgrade was tested, but that does not establish installed-editor rollback or every upgrade path. Use isolated or backed-up state for rollback qualification. Sources are not rewritten by indexing.

## Recorded evidence and remaining limits

The [October 17 Windows comparison](../scale-qualification.md#final-windows-enhancement-comparison-2026-10-17) measured frozen AIRK and application workspaces at all three detail levels. Relative to its detail-level baseline, Balanced logical storage fell **12.2% / 23.3%**, Detailed fell **28.3% / 24.9%**, and repeated exact-symbol calls were **4.3–6.3 times faster**. Peak memory was approximately unchanged. These are individual workload observations with no embedding model, not production vector-search or maximum-capacity qualification.

Six controlled updates reused all unchanged files, completed cleanup and passed citation/isolation checks. The [Windows installed-editor tests](../windows-local-build.md#installed-extension-and-two-window-qualification) covered trust, multi-root and shared/independent collections across windows. Native process-death tests cover publication boundaries and retry protection. The 1.1.2 guide has automated configuration-preservation and renderer checks; those do not establish every installed agent's connection.

The version-specific [1.1.0](release-1.1.0.md), [1.1.1](release-1.1.1.md) and [1.1.2](release-1.1.2.md) records retain their development checks and open acceptance items. Cross-platform build/signing records do not establish every editor, remote-host, oldest-OS, upgrade/rollback or power-loss scenario. Larger-than-memory performance, production semantic quality, complete language resolution and billed token savings remain unqualified. Dependency-notice review gaps remain documented in [third-party notices](../../THIRD_PARTY_NOTICES.md).
