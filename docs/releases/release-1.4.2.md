# AIRK 1.4.2 resource-policy candidate

October 25, 2026. Unpublished Windows x64 local candidate. Native workspace, local crate lock entries, extension manifest and npm lock entries are synchronized at **1.4.2**. The compatible `service-1.4` namespace and existing project registrations, source/index storage, watch preferences and explicit resource overrides are preserved. No publication or normal-profile installation is performed by this build.

Balanced automatic memory uses 25% of effective machine RAM, bounded to 2–32 GiB and never exceeding a known machine/cgroup ceiling. Responsive uses 12.5%, bounded to 2–8 GiB; Throughput uses 50%, bounded to 2–64 GiB. Unknown capacity uses the conservative fallback. Background work protects resident headroom for up to four query workers where the configured budget supports them. Extraction remains at most sixteen default shared threads and four per job; inference remains one worker per grant. Running work retains its charges through cancellation, deadlines and lowered policy until acknowledged completion or confirmed exit. Available-memory admission uses machine-scaled low/high thresholds rather than repeatedly admitting at a single low watermark.

Balanced source-byte pacing is 64 MiB/s per grant, bounded by a 256 MiB/s aggregate reservation across active grants. This paces admitted source bytes between bounded artifacts, not physical disk I/O or atomic publication. Console observations distinguish reserved memory, actual RSS, protected query headroom and aggregate pacing capacity. Existing overrides are preserved and grants remain subject to the shared ceiling. Remaining pacing capacity below the minimum valid 1 MiB/s grant defers admission, including byte-level custom overrides.

Native source watching raises directory admission to 8,192 per project and 32,768 shared, planned/pending path bytes to 16 MiB per project and 64 MiB shared, traversal entries to 262,144 per project per reconciliation, and depth to 64. Traversal continues in bounded turns; native registration/removal yields after 64 calls. Existing exclusions, source/data boundaries and linked/reparse/alias rejection remain. Specific failure codes identify the exhausted bound. A machine-scaled 128–768 MiB watcher memory reservation/guard accounts for larger native registration capacity; constrained hosts and OS watcher limits may still require periodic fallback. The supervisor validates heartbeat counts against the same shared directory constant, so valid counts above 512 no longer trigger watcher restart. These limits are finite metadata bounds, not a guarantee of complete watch coverage.

Storage quotas remain 256 GiB per collection and 500 GiB shared. New job failure codes distinguish root, collection and per-operation reservation quotas from physical headroom, filesystem-full and SQLite-full failures. They retain bounded maintenance retry behavior and do not expose raw exceptions or paths. Earlier `storage_pressure` receipts remain historical and cannot be retrospectively attributed.
