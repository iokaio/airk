# AIRK UI review and unification plan

23 November 2026 · Design for review · Source baseline `f37d31b8`

## Product decision

Explorer is the complete AIRK interface inside VS Code. Every capability available in the standalone Admin console has a first-party Explorer workflow, subject to the same authorization and platform capabilities. Use the existing extension-host connection to `airkctl` for privileged operations. Render the workflow inline with Explorer navigation, theme, focus behavior, and feedback.

Place exactly one **Open Admin Console** button in the top-level Explorer header. It opens the standalone console in the default browser on explicit activation. The header button is the sole browser entry point in Explorer. Remove Simple Browser hosting, the destination chooser, the preference for where to open Admin, and all task-level Admin buttons and redirects. An unsupported or failed operation stays on its Explorer screen with its reason and recovery action. Standalone Admin remains independently useful for users outside VS Code.

Workbench remains an editor-side evidence workspace. Its management action navigates within Explorer to the relevant resource or setup task. Its composer, transcripts and saved sessions stay in Workbench.

## Review basis

Static review of maintained UI source, host bridges, shared components, operation catalogs, related contracts and test entry points. Findings describe source behavior and likely UX consequences. Installed appearance, keyboard behavior, platform support and end-to-end journeys still need validation. The operation contracts and current handlers are authoritative for availability. For example, the Admin guide describes macOS peer proof as absent while current source contains a macOS implementation. The presence of that implementation alone establishes no installed support. ### How the surfaces fit today

| Surface | Current design | Consequence |
| --- | --- | --- |
| Explorer | Bundled Preact webview, typed extension-host messages, editor-aware workflows and a partial native Admin integration | The same destination can expose a shared Admin view, retained Explorer controls and an external browser action |
| Browser Admin | Standalone Preact app over local HTTPS with its own launch, session, navigation and operation adapter | Broad functionality and a strong service boundary, with operator and discovery tasks competing for attention |
| Workbench | Separate VS Code webview with a composer, transcript, evidence tools and scoped session storage | Fast repeated evidence work, with important scope and history controls largely behind icons and popovers |

The current shared management renderer is already bundled into Explorer. It mounts the Admin `App` in embedded mode and adopts a native session. Explorer's CSP blocks frames by default. The separate legacy handoff can still invoke `simpleBrowser.show` or launch the external browser. Fix both seams: replace handoffs with native Explorer routes and give management views an Explorer-owned shell. Keep shared workflow components where they fit. ## Standalone Admin review

| Area | What works | Friction and recommendation |
| --- | --- | --- |
| Entry and shell | Single-use launch, authenticated local session, explicit sign-out, offline Help and named destinations | Expiry or restart interrupts the operator and the rail gives evidence and administration comparable weight. Group navigation under **Manage**, **Investigate** and **Help**. Keep service status and sign-out in the header. Show a dedicated expired, restarting or unreachable state with the supported re-entry instructions and the state of any in-flight action. |
| Overview and Index Library | Full catalog, reviewed setup and mutations, folder picker, progress, sets, sources, grants and retirement evidence | The library carries many unrelated forms and is the heaviest management workspace. Start with a searchable list of indexes and sets, use stable object links and breadcrumbs, and open dedicated setup, split and retirement flows with review and result steps. Show display names prominently and immutable IDs in details. |
| Activity, Logs and Usage | Jobs, requests and recovery evidence, complete results, log access and usage reports | Operators must move between related views and inspect technical payloads to see what happened. Lead with a filterable timeline carrying time, target, status and next action. Link a job to its request and relevant logs. Keep report scope, period, estimates and exclusions visible. Offer complete receipts and exports from details. |
| Service, Storage, Recovery and models | Resource facts, lifecycle actions, storage review, recovery plans and standalone model workflow | Broad diagnostic and maintenance controls compete on the same page. Lead with service status and current issue, then use focused views for Runtime, Models, Storage and Recovery. Put high-impact controls at the point of need, show affected targets and service-generated impact before applying, and show operation receipts afterward. Derive model labels and choices from supported runtime capabilities as the Answer model design evolves. |
| Agents and trust | Endpoint and ownership details, verification, manual client snippets, trust guidance and revocation | Manual configuration has considerable technical detail. Start with a client picker and a clear status per client, then show the applicable connect, verify, repair or revoke action. Put complete snippets and exact commands in advanced details. Explain whether the change affects this client, an index grant or the service. |
| Search, evidence, review, strategies and Help | Guided investigations, catalog-backed tools, bounded scope, native metadata, complete exports and bundled help | Several destinations share the Search route and a tool parameter, which makes them feel like modes of one form. Give guided workflows stable browser routes with back/forward behavior and retain the existing bookmarked/launch aliases. Start with task prompts, preserve current input on return, and use plain-language labels for budgets, truncation and historical results. |

Use a labeled desktop sidebar and an accessible drawer at narrow widths. Establish a common page pattern with title, target, current state, task action and detail area. Use responsive tables with row labels and real empty, refused and loading states. Keep error summaries reachable from the keyboard and return focus after dialogs close. Use consistent spacing, semantic severity tokens, visible focus and readable long paths. Keep raw JSON and exact receipts accessible on demand. Maintain browser history and test direct links for signed-out and expired sessions. ## Workbench review

| Area | What works | Friction and recommendation |
| --- | --- | --- |
| Entry and composer | Compact composer, slash commands, recipes, guided evidence options, tool forms and cancellation | First-time users compete with project, history, settings and evidence-options icons. Add a persistent labeled **Search in** affordance and a compact scope line at the composer. Expose the most common evidence actions directly when space permits. Describe the effect of Stop accurately when an admitted native read may finish. |
| Scope and readiness | Explicit indexes and sets, independently observed readiness, host-owned scope identity and stale response fencing | Project identity, selected read scope and publication state each answer a different question. Show their current values near the composer and bind each turn to its recorded scope. On a setup blocker, open the matching Explorer task and return to the original draft for review. |
| Transcript and source evidence | Source cards, editor navigation, context expansion, provenance, raw response, exports and explicit omissions | Long evidence and multiple diagnostic sections can crowd out the result. Render a concise answer or evidence summary, a visible incomplete/refused state, source cards, then a receipt expander. Keep verified saved-byte observations dated and distinguish them from live editor state. Keep all original export fields. |
| History and persistence | Rename, fork, copy/export, scope-specific saved histories, persistence settings and save recovery | History, save policy and destructive actions cluster in small popovers. Show whether inputs and results are saved beside the session title. Put bulk deletion behind an explicit review naming the project scope. Keep compact history browsing and give the popover a predictable focus order. |
| Editor and Explorer integration | Host-validated source opens, refresh review and an existing Management action | Management currently starts a separate navigational journey. Link to Explorer with an approved resource identifier and the reason for the task. Provide a return action that restores the existing Workbench draft and scope without submitting the request. Keep persisted and forked turns historical until current authority is established. |

Reuse scoped selection presentation, outcome labels, provenance details and source actions across evidence surfaces. Preserve Workbench's compact layout, session lifecycle and user-controlled persistence. Test narrow-width popovers, keyboard navigation, interrupted requests, stale authority and saving independently. During implementation, expand it to one row per action, with the exact operation, supported platforms, permission and session requirements, review/receipt behavior, and the corresponding Explorer test. Cover empty, failed and uncertain paths. A copied command remains available wherever Admin already exposes one. Any new effect behind a button requires an existing approved native path or a separately reviewed contract decision.

### Example journeys

1. **Create an index for the current folder.** From Explorer Overview, choose **Create index**. Review the name, roots, storage location and watching, then review the service draft and apply. Land on Index Details with indexing progress and an explicit **Use in this window** scope action.
2. **Recover a failed job.** Follow an Activity link to the exact request and index. Inspect the original receipt or recovery plan, review the next permitted effect and see the resulting state in the same Explorer view. Restart and unknown outcomes retain the exact next action and original identity.
3. **Repair a Workbench scope.** Follow the empty-state setup action to Explorer, review and apply a scope, then return to the draft. The composer displays the resulting effective scope before the user submits.
4. **Open the standalone console.** Select the header button. The default browser opens through the existing one-use browser launch path. Explorer stays on its current view and keeps its local state.

## Architecture and lifecycle

- **Explorer owns the shell.** Route to management components with typed destination and object identifiers. Reuse shared operations, form rules, labels, scope and evidence projections, and workflow components that fit both surfaces. Split Admin's route/session shell from reusable tasks. Use VS Code theme tokens and host-specific layout in Explorer. Give the browser its own navigation, theme and responsive presentation. Keep Workbench's composer and transcript independent.
- **Use the existing authority chain.** Explorer webview → validated messages → trusted extension host → open, verified `airkctl` session → owner pipe → native Admin entry → canonical handler. Browser Admin → local HTTPS adapter → the same canonical operation handler. Preserve server-owned permissions, request identity, operation allowlists, trust, service-instance and generation fences, and browser peer/session controls. Keep launch/session secrets off editor messages and out of UI logs and persisted state. Keep transport contracts and generated bindings under their existing owners.
- **Keep workflow state by scope and origin.** Treat DRAFT, PREPARED, APPLYING, KNOWN OUTCOME and UNKNOWN OUTCOME as distinct display states. Preserve preparation custody across view changes when the original native session remains valid. After close, revocation or service replacement, discard stale authority, retain eligible historical observations, and use the original request recovery path where available. Automatic reconnection may resume reads under current authority. Apply stays an explicit, reviewed user action.
- **Retain native result semantics.** Carry original revision, scope and publication identity through every renderer, copy and export. Keep provenance, denial, partial/omitted data, paging, retries and readiness separate. Respect native budgets, chunk ordering, cancellation and original deadlines. Tests compare complete equivalent results over both real transports.
- **Remove the legacy pathways after parity.** Convert all app, journey, status and guidance callers to Explorer routes. Remove task-level `admin.open` messages, the embedded whole-app variant and the retained parallel screens after equivalent workflows are verified. Converge `airk.openAdmin` on the explicit external-browser launch action if the compatibility command remains. Keep the external launch gesture only in the Explorer header and standalone entry points. Scope browser-launch failure feedback to the header action.

**Release conditions**

- Explorer has exactly one browser-launch button at the top. Activating it uses the default browser. An automated UI audit and installed journeys establish zero frame/Simple Browser hosting and zero implicit browser launches across management, onboarding, recovery, alerts and Workbench.
- Every inventoried Admin capability has an Explorer route with equivalent useful inputs, effects, outputs and diagnosis. Unsupported operations remain discoverable with a reason and any existing recovery path. Capability visibility and authorization are tested separately.
- Test complete inputs and responses on the installed extension-host owner-pipe route and standalone HTTPS route. Compare full receipts and exports, normalizing only documented transport identities and timing. Include role/trust refusals, stale scope, chunked responses, lost acknowledgments and no replay of uncertain mutations.
- Validate keyboard-only use, screen reader announcements and focus return, narrow editor panes, browser mobile widths, zoom, light/dark/high-contrast themes and long paths. Test loading, empty, refused, stale, partial and offline states separately.
- In usability review, have participants create an index, resolve an unhealthy source, locate a failed request and verify an agent without directions. Try the same operational tasks in both Explorer and browser Admin. Record whether each task was completed, where users hesitated and where a browser switch occurred. Explorer tasks require zero browser switches.
- Self-review for this design checked current source seams, route mappings and the native contract. Runtime and usability checks belong to implementation. Repository and Markdown checks apply to this document.
