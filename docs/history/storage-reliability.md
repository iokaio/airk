# Storage reliability and embedded engine review

October 25, 2026. This is an incident analysis and recommendation, not a claim that all listed improvements are implemented. The 1.4.3 source fix is described in the [release record](releases/release-1.4.3.md).

## Failure and immediate correction

The installed 1.4.2 runtime admitted large publications against growing main-database capacities but retained a fixed 64 MiB WAL and 128 KiB shared-memory limit. Its VFS returns SQLite FULL before writing beyond either bound. A publication can therefore fail despite ample physical disk space and unused main-database capacity. Once its durable phase reaches Applying, retrying the same captured replay under the same limit can repeatedly fail. Read-only inspection found this state in both active projects. This is an AIRK admission-policy defect; these observations do not establish SQLite corruption or an upstream engine defect.

Version 1.4.3 derives WAL capacity from two admitted database images plus frame headers, rounded up to a power-of-two tier with a 64 MiB floor. It derives shared-memory capacity from the corresponding WAL-index region count, with a 128 KiB floor. Both remain finite, enforced before writes/mappings, and included in the durable lifetime quota allowance before opening the writer, including recovery. For a 1 GiB admitted main image the rounded WAL allowance is 4 GiB; these are logical reservations, not preallocated files or resident memory. Existing quota settings remain authoritative and may refuse the larger reservation.

Retained reads can use the preceding smaller allowance only while all files fit those preceding limits, with the preceding VFS budget. The next writer enlarges the durable allowance before replay. Growth admission uses SQLite's logical page count rather than the main-file length, which excludes uncheckpointed WAL pages. Original sources, collection identity, pending replay inputs and the old committed revision remain preserved. Restart the old runtime when installing the new candidate; simultaneous old/new engine access is not an upgrade mechanism.

The integrated large-publication regression captures over 64 MiB of map values, interrupts Applying, reopens the writer, and commits while an older snapshot remains pinned. It verifies every mapped value, old/new revision isolation, actual WAL growth beyond the former cap, logical size beyond main-file size and admitted file bounds. A second regression checks retained reads and recovery from the previous lifetime allowance. These generated fixtures do not copy private indexes.

The larger bound removes the demonstrated fixed-cap mismatch. It is not a proof that every permitted workload fits: cache spills, repeated page updates and long-lived snapshots can still amplify WAL growth. SQLite documents those [large-transaction and checkpoint constraints](https://www.sqlite.org/wal.html). The installed failing projects have not yet been replayed with the new build. A generated native comparison reproduces SQLite FULL on the 1.4.2 distributable, then opens the same generated index with 1.4.3 and completes 128 files / 131,072 functions with unchanged sources and Ready state. That failure leaves Ready after preparation rollback; interrupted Applying replay is verified by the separate storage regression. See the [candidate receipts](releases/release-1.4.3.md).

## Prioritized hardening

1. **Bound actual publication work before Preparing.** Budget extracted facts, postings, affected map buckets/nodes, graph afterimages, lexical work and estimated WAL frames. Source file count/bytes alone do not bound derived work. Split oversized progressive batches while still Ready; preserve one atomic revision across all components in each accepted batch. A single oversized artifact needs a specific admission result.
2. **Reduce write amplification.** Apply each final map bucket/node afterimage once instead of repeatedly updating its ancestor path for every fact. Measure pager writes and WAL bytes per publication against derived work. Preserve authenticated roots and replay validation.
3. **Make recovery advance or report a specific blocker.** Differentiate WAL, shared-memory, main-page, quota and physical-space exhaustion. Include attempted/admitted bytes, publication phase and checkpoint/pinned-reader observations in bounded diagnostics. Retry only when the relevant condition changes; never discard an Applying journal or substitute current source files.
4. **Make status describe usefulness.** Display service liveness, query readiness, source freshness, watcher coverage and recovery blockage independently. A responsive service with repeated failed reconciliation must show stale evidence and the exact blocked job prominently.
5. **Make failure workloads release gates.** Use generated corpora with high fact/posting fan-out, large documents and repeated edits in four concurrent projects. Hold snapshots during indexing; kill workers during preparation and replay; test quota denial, actual disk-full injection and restart. Require eventual recovery, bounded resources, consistent citations and source preservation on Windows, macOS and Linux. Add a sustained soak, not only small successful fixtures.

## Engine options

These are evaluation candidates inside the existing storage boundary. No engine dependency or remote service has been added. DiskANN remains the selected vector engine. Replacing SQL storage does not by itself correct publication admission, resource accounting or recovery policy.

| Option | Potential benefit for AIRK | Main cost or remaining failure mode | Recommendation |
|---|---|---|---|
| SQLite with corrected admission | Preserves FTS5, current atomic publication and existing recovery work | Needs bounded transactions, checkpoint observability and less map write amplification | Immediate stabilization baseline |
| Turso embedded engine | Rust implementation, local SQL, async I/O, testing through deterministic simulation and Antithesis | Missing AIRK-required SQLite APIs and FTS5; experimental FTS and multi-process coordination; WAL still exists | Compatibility spike only; unsuitable as an emergency replacement |
| redb | Rust embedded transactional key/value storage using copy-on-write B+trees and MVCC | SQL and FTS5 need replacement; snapshot retention, quotas, process ownership and atomic lexical/graph publication need new qualification | First focused metadata/map backend experiment |
| LMDB | Embedded copy-on-write storage with one writer and concurrent readers | Map capacity/resize and long-lived readers remain resource risks; SQL and lexical indexing need replacement | Secondary comparison with redb |
| RocksDB | Embedded key/value engine with transactions and snapshots | Compaction, memory, write amplification and write stalls add tuning/packaging work; lexical index still separate | Evaluate only if measurements justify write-heavy complexity |

Engine references: [redb documentation](https://docs.rs/redb/latest/redb/), [LMDB API and limitations](https://github.com/LMDB/lmdb/blob/mdb.master/libraries/liblmdb/lmdb.h), and [RocksDB transactions](https://github.com/facebook/rocksdb/wiki/Transactions) / [tuning](https://github.com/facebook/rocksdb/wiki/RocksDB-Tuning-Guide). The ranking is an AIRK-specific engineering judgment, not a measured engine benchmark. A separate lexical engine such as [Tantivy](https://docs.rs/tantivy/latest/tantivy/) also needs an atomic manifest that binds lexical, catalog and DiskANN state to one revision.

## Turso assessment

The reviewed project is the embedded Rust rewrite, distinct from the older libSQL fork and optional hosted service. Its maintainers report production use and intensive simulation testing, while noting that it has not reached 1.0. They advertise Windows, macOS and Linux support; this is not AIRK platform qualification. Their README labels full-text search and multi-process WAL coordination experimental. [Project status](https://github.com/tursodatabase/turso#faq), [features](https://github.com/tursodatabase/turso#features-and-roadmap).

The compatibility matrix explicitly omits SQLite FTS3/4/5, substitutes Tantivy-based FTS, and lists `sqlite3_set_authorizer` and `sqlite3_file_control` as unsupported. It also lists `journal_size_limit` as unsupported and `locking_mode` as partial. AIRK authenticates physical FTS5 shadow rows, installs a SQL authorizer, and uses file control for sidecar persistence and filesystem inspection. These require adapter and evidence-format redesign, beyond substituting a Rust SQL driver. [Compatibility matrix](https://github.com/tursodatabase/turso/blob/main/COMPAT.md).

The manual documents WAL as the default journal mode; its MVCC journal mode carries a warning against critical-data use. Thus switching does not establish that bounded-log pressure or repeated recovery failure disappears. Concurrent SQL writers also do not remove AIRK's collection-scoped atomic publication coordinator. [Journal modes and experimental FTS](https://github.com/tursodatabase/turso/blob/main/docs/manual.md#journal-mode).

If Turso is prototyped, pin an exact release/commit and first test the actual AIRK schemas and SQL, transaction failure semantics, cancellation, read-only opening and quota enforcement. Then test atomic lexical/catalog/graph publication and kill/restart recovery above the old WAL threshold on each native platform. Require a safe new namespace or explicit migration that preserves the old index; Turso disallows mixed SQLite/Turso multi-process access. Current documentation review alone does not establish migration safety or a reliability improvement.
