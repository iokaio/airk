# Current-index sharding review (2026-10-21)

This is a dated design and qualification record. Physical sharding is not implemented 1.2.5 behavior. The later [FTS5 decision](#decision-replace-tantivy-with-sqlite-fts5) records the selected lexical replacement separately from its implementation status. AIRK keeps one current published index per collection. Git remains the source of revision history; storage replacement must never expose historical search, rollback or checkpoints.

## Evidence and decision

At the start of this review, AIRK already broke scheduled cold scans into committed source batches and semantic work into bounded batches. The pre-replacement Tantivy adapter retained immutable segments, while the current SQLite map and DiskANN graph are bound to one exact publication. A `path_prefix` query narrows lexical candidates and ranks a bounded authenticated graph subset for vector retrieval. A broad query still searches the collection and discloses partial discovery or semantic coverage. See [current runtime](current-index-runtime.md), [architecture](architecture.md) and [local-model retrieval](local-models.md).

The completed 100,000-file lexical capacity run recorded 1,117.97 seconds in scan/capture and 2,256.50 seconds in publication, with a 587.03-second unchanged pass. It overlapped other preparation, used a single synthetic corpus, and did not include neural indexing. The earlier 7,628-file application run took 185.429 seconds to index; its first MCP search took 2.605 seconds and later lexical queries about 13 ms. These are useful bottleneck signals, not proof that extra physical shards will improve total time. Small graph experiments found graph time well below inference time; sharding graphs is not yet a demonstrated semantic-build speedup. See [scale qualification](scale-qualification.md) and the [indexing optimization record](indexingenhancements.md).

**Decision for 1.2.5:** keep the existing single current logical index and progressive work batches. Do not silently split storage or queries into physical shards without a controlled comparison. Sharding adds per-shard authentication, journal, quota, cleanup and query fanout costs. It can hurt broad-query latency and approximate vector recall. The 1.2.5 implementation also defers inline semantic inference until source discovery completes and adapts source batch cadence to publication cost. These performance changes proceed alongside early MCP availability and editor progress without requiring another large-corpus benchmark or an index-format change. Controlled comparisons remain a gate for adopting the proposed physical shard layout, not for fixing known scheduling and publication overhead.

## Implementable path if measurements support it

1. **Measure a baseline.** On isolated copies of the public 7,628-file and 100,000-file fixtures, record scan/capture, model inference, lexical publication, graph update, journal/verification, cold and warm first query, scoped and broad search, process memory, logical and physical disk bytes, and gate wait time. Run the same binary and storage device without concurrent builds. Add a real model and judged semantic queries before claiming vector benefits.
2. **Pilot lexical shards first.** Keep one collection head and one atomic current journal. Let the head reference a bounded set of authenticated Tantivy shard manifests. Assign a path to a stable shard using its collection-relative path hash; choose the shard count at a deliberate rebuild boundary. Update only affected shards. Keep original paths and hashes in citations and the current SQLite map. A move changes shard membership in one publication. Shards are internal derived objects, not collections or revisions.
3. **Route and merge safely.** A path-scoped query may read only shards that can contain that prefix, but a hash-only assignment requires all shards unless an authenticated path-to-shard directory proves the narrower set. Broad queries fan out to every shard. Apply a bounded per-shard candidate budget, merge exact lexical matches deterministically, then enforce the existing global hit and byte budgets. Disclose truncation if any shard exhausts its budget. No shard can be skipped based on a guessed topic, language or query intent.
4. **Consider graph shards separately.** Only after lexical results pass, compare one DiskANN graph with bounded graph shards on the same model and corpus. Broad vector search must rank candidates across every shard with calibrated distances and preserve the existing source/occurrence verification. Path-scoped search may target authenticated members. Measure recall against the current graph and held-out judgments; never treat fewer searched shards as a relevance improvement by itself.
5. **Preserve the current-only contract.** The single head names exactly one active shard set and one revision token. Prepared/Applying recovery captures all changed shard manifests and SQLite afterimages; readers see either the old complete head or the new complete head. Cleanup removes unreferenced derived shard files after reader exclusion. No prior head is queryable, and no shard stores source history. Collection/root isolation, quota reservations, failure reporting and source read-only behavior remain unchanged.

The pilot should show at least a 20% reduction in publication time on the large fixture without a material broad-query or first-query regression, identical exact lexical results, and no loss of judged vector recall before it replaces the current layout. These are go/no-go criteria, not claimed results. A changed on-disk layout needs a separately qualified rebuild path and Windows, macOS and Linux checks. If source scanning or inference still dominates, improve those stages instead of adding physical shards.

## Storage-engine alternatives reviewed on 2026-10-21

Replacing SQLite is a separate decision from sharding Tantivy or DiskANN. The current map and graph-record adapters mostly use keyed records, ordered traversal and atomic batches, making an embedded key-value engine a plausible fit. SQLite also owns scheduler state, usage accounting and quota-bounded temporary work. A replacement must cover those responsibilities or explicitly retain SQLite for them. It cannot remove model inference cost.

| Candidate | Potential fit | Constraint for AIRK |
| --- | --- | --- |
| [redb 4.4.0](https://docs.rs/redb/latest/redb/) | Pure Rust, transactional B+trees and concurrent read transactions; first candidate for a Rust-native map adapter | The published source gates concurrent multi-process readers/writers behind [`experimental-multiprocess`](https://docs.rs/redb/latest/src/redb/db.rs.html). Default exclusive-writer mode does not let separate MCP processes read while another process owns the writer. Adoption needs qualification of that mode or a deliberate change to process ownership. |
| [LMDB through heed](https://docs.rs/heed/latest/heed/) | Typed Rust access to an embedded engine with multi-process reader/writer coordination | The engine remains C. Memory-map growth, reader lifetime, cleanup and hard disk-budget accounting require an adapter; the [environment contract](https://docs.rs/heed/latest/heed/struct.EnvOpenOptions.html) explicitly requires care with mappings and long-lived transactions. |
| [Fjall 3.1.12](https://docs.rs/fjall/latest/fjall/) | Rust-native LSM storage, atomic keyspace batches and optional serializable transactions; candidate for heavy incremental writes | [Multi-process access is unsupported](https://fjall-rs.github.io/post/fjall-3/). A shared database would need one owning process. Background compaction also needs reserved disk space and coordination with foreground retrieval. |
| [RocksDB](https://github.com/facebook/rocksdb/wiki/Read-only-and-Secondary-instances) | Established LSM design with read-only secondary instances | C++ build/runtime dependency, compaction and explicit secondary catch-up add complexity. A caught-up secondary must still prove the exact AIRK publication before returning evidence. |
| [Turso](https://github.com/tursodatabase/turso) | Rust-native SQL engine with partial SQLite compatibility | Its multi-process WAL coordination is experimental and [compatibility remains incomplete](https://github.com/tursodatabase/turso/blob/main/COMPAT.md). It requires database-engine qualification rather than a wrapper substitution. |

**Recommendation:** retain the existing store for the 1.2.5 candidate. Evaluate redb first for a later Rust-native adapter and heed as a comparison when preserving the current multi-process helper arrangement is the priority. This is a source/documentation review, not a measured speed or reliability result. Neither engine has been added to AIRK. The [SQLite registry review](../THIRD_PARTY_NOTICES.md) separately records why issue #32's Git pin remains necessary pending a suitable published bundle.

A useful adapter trial would cover current-map and graph-record reads/writes inside `airk-store`, preserving the existing authenticated encodings, collection/root scopes and publication journal. It must demonstrate reads during indexing, atomic head changes across Tantivy and DiskANN, process-crash recovery, bounded allocation and cleanup on Windows before changing the default. Database transactions may retain pages temporarily for active readers, but AIRK would still expose only its current publication and reclaim obsolete derived data; no revision-history API or persistent source checkpoints would be introduced.

### Consolidating retrieval into SQLite

The DiskANN provider already stores authenticated graph records in SQLite; the replaced Tantivy adapter had separate segment files. Replacing DiskANN changes the vector algorithm and graph data, while replacing Tantivy can remove a separate publication component. Both require preserving candidate authentication, original locations, path scoping and response budgets.

SQLite [FTS5](https://sqlite.org/fts5.html) is a plausible lexical replacement. AIRK's current Tantivy adapter uses precomputed terms, AND matching, a literal path-prefix filter and stable identifier ordering, so a trial should reproduce those semantics first. FTS5 ranking and tokenization changes would be separate retrieval-quality decisions. Contentless-delete or external-content tables can reduce duplicated text, but the retained extracted content and citation metadata still need an authenticated representation. Tantivy compresses stored payloads, so fewer files do not establish lower disk usage. FTS5 also has segment merging and maintenance costs.

An FTS5 table in the current database could commit lexical changes with the map and graph rows in one SQLite transaction, reducing cross-component recovery work. The journal would still coordinate retained objects, the publication head and recovery metadata. A database transaction is not a substitute for source hashes or collection isolation. SQLite still admits one writer at a time. [WAL](https://sqlite.org/wal.html) permits concurrent readers and a writer, but AIRK's current map deliberately uses rollback journaling; adopting WAL would require changes to its reader, journal, quota and cleanup contracts. Consolidation alone does not change those contracts or address the Git dependency pin.

Vector retrieval has two materially different choices. Exhaustive distance scans remove graph-build and adjacency-storage costs but examine every candidate vector; at 384 float32 dimensions, one million vectors contain 1.536 GB of raw numerical data before row overhead. Small or tightly scoped sets may suit exact scans. Large broad queries need a measured latency and memory budget. SQLite's [Vec1 extension](https://sqlite.org/vec1.html), version 0.8 at this review date, offers an ANN alternative based on IVFADC with quantization. Its [manual](https://sqlite.org/vec1doc.html) describes training, compressed-vector scoring and reranking; those introduce different build, update and recall tradeoffs from DiskANN. An extension still requires build, provenance, transaction and recovery qualification.

The initial comparison recommended evaluating FTS5 while retaining DiskANN before attempting a fully consolidated vector engine. The decision below supersedes the undecided lexical recommendation. The redb/heed comparison addresses the separate objective of moving storage to Rust. Extraction and embedding inference remain necessary for semantic search under every option, and no indexing speedup or storage reduction is claimed.

## Decision: replace Tantivy with SQLite FTS5

**Selected and implemented in source on 2026-10-21 for the unreleased 1.2.5 effort; qualification is in progress.** Replace the lexical backend with SQLite FTS5 and retain DiskANN for vector retrieval. This decision does not authorize a release or change the current-only indexing contract.

### Why remove Tantivy

1. **AIRK's lexical contract fits FTS5.** The replaced adapter indexed AIRK-generated terms, required all query terms, applied a literal path prefix and ordered candidates by stable identity. It did not use Tantivy's BM25 ranking. FTS5 can supply an inverted index for that contract without making AIRK depend on a second database engine for lexical retrieval. Preserve whole-identifier aliases, CamelCase components and Unicode handling explicitly; adopting FTS5's default tokenizer without checking equivalence would change results.
2. **The separate segment lifecycle adds publication work.** The replaced publication path created a private Tantivy candidate, hardlinked unchanged immutable files, admitted changed writes, captured and verified a file manifest, selected that component with the SQLite head, and later reclaimed obsolete directories. These steps have quota, ownership, crash-recovery and Windows file-handle consequences. Moving lexical storage into the owning SQLite transaction is the intended way to remove that separate lifecycle. Merely copying a complete FTS database for every publication would retain substantial overhead and is not the intended design.
3. **SQLite already stores AIRK's authenticated map and DiskANN records.** FTS5 is available through the bundled SQLite engine. Reusing it can reduce the number of storage components and dependencies that must be built, packaged and maintained. SQLite transactions can coordinate lexical, catalog and graph changes, while AIRK still authenticates retained evidence and publication identity. Transactional consistency alone does not establish that retrieved evidence matches a source hash.
4. **The observed delays justify reducing publication overhead.** The large lexical fixture recorded substantial publication time, and repeated small publications multiply lifecycle work. Those observations support simplifying publication, but they do not isolate Tantivy as the sole cause or prove that FTS5 is faster. Extraction, authenticated-map maintenance, inference and graph updates have their own costs. In particular, this replacement does not remove semantic embedding inference.

### Tradeoffs and preserved behavior

- FTS5 still writes and merges inverted-index segments. SQLite permits one writer at a time; consolidating work can lengthen that writer's transaction and increase rollback-journal space. Retain bounded batches, capacity admission, reader gates and explicit recovery failures.
- Fewer components do not guarantee a smaller index or faster queries. Tantivy compresses stored payloads; FTS5's content layout, duplicate text, page reuse and merge policy affect disk use. Any speed, memory or storage claim requires measurements of the implemented adapter.
- Keep candidate authentication, detection of missing or corrupted index data, collection/root isolation, exact revision binding, literal path scope, source locations, hit/byte limits and truncation reporting. A SQL match remains a candidate until verified against retained evidence. Empty results must not silently hide an integrity failure.
- Preserve lexical query semantics first. BM25 ranking, different tokenization and mixed-content ranking changes require their own retrieval-quality decision. DiskANN and existing hybrid fusion remain separate from this lexical replacement.
- This is an embedded SQLite implementation, including its C engine; it does not make the stack entirely Rust. It also does not resolve [issue #32's dependency pin](../THIRD_PARTY_NOTICES.md): the fixed upstream SQLite bundle remains necessary until a suitable crate is published.
- Existing Tantivy files cannot be opened as FTS5 indexes. The implementation must identify incompatible storage explicitly and provide a deliberate rebuild path. Normal reads and incremental indexing must not reinterpret old files. An explicitly requested full upgrade rebuild discards the old derived index, including its pending journal, and reconstructs it from saved source; it is not an in-place data migration. Source files remain read-only; obsolete derived data is reclaimed only after ownership and reader checks.
- AIRK continues to expose one current publication per collection. Recovery metadata and temporary publication work are not searchable revision history. Git remains responsible for history.

### Completion evidence

Before describing the replacement as implemented, remove Tantivy from production retrieval and its dependency graph; exercise FTS5 add/update/delete and scoped queries; preserve exact-case reference verification; and check atomic publication, interrupted recovery, corruption rejection and quota failure behavior. The architecture, current-runtime guide, release notes and packaged extension description must describe the resulting implementation consistently. Build a local Windows VSIX for manual testing before any push or publication. This decision record is not a benchmark result or a completed migration receipt.

### Implemented adapter

The replacement lives in `airk-store`, alongside the current SQLite map and graph records; shared term normalization is in `airk-core`. It uses FTS5 with an external-content document table, explicit AND queries, literal case-sensitive path filtering and stable identity ordering. Tantivy, its bounded-directory/fork machinery and the retired 1.1 generation adapter/lexical experiment are removed. Their engine-specific fixtures are retired with them; current publication, DiskANN, recovery, corruption and materialization tests remain and are adapted to FTS5. The native real-model qualification script exercises the supported runtime instead of the removed generation adapter.

Preparation applies only changed paths in a quota-admitted SQLite transaction, flushes and seals FTS5 shadow rows, then rolls back. Prepared captures retained input metadata; Applying repeats the deterministic updates, verifies the sealed digest and commits lexical rows, map, graph and head together. This avoids complete database copies and separate segment directories, but performs changed-path lexical writes twice. Read verification still scans authenticated lexical rows once per request. These costs are explicit remaining optimization targets, not grounds for claiming a measured improvement.

Format 126 requires an explicit full rebuild of a format-120 collection or the earlier local format-125 candidate. The rebuild keeps the same collection ID and saved settings, discards old derived files under writer/request exclusion, and resumes interrupted deletion from a durable marker. It does not convert Tantivy data or keep a historical index copy. No history API is added. Full runtime and package qualification must finish before the source change is described as release-ready.

Local Windows correctness, package and bounded real-workspace observations are recorded in the [1.2.5 qualification status](releases/release-1.2.5.md#qualification-status). The observations did not demonstrate a speedup; per-request lexical authentication and the repeated preparation/replay writes remain explicit costs. Manual installed-editor acceptance and other-platform qualification remain open.
