# MCP response modes

The 1.4.0 development implementation defaults to **Terse response mode**. Choose **Full response mode** in the trusted extension panel's Agent connections section; `airk.mcp.responseMode` persists the machine setting and refreshes the MCP launch definition. Reconnect the agent after changing its launch configuration. Native clients can set `AIRK_MCP_RESPONSE_MODE=full`. An individual tool request can override either default with `response_mode: "full"` or `"terse"`.

Use terse for routine navigation. Use Full for provenance audits, parser/coverage limitations, readiness diagnosis and missing or surprising results. Every tool schema and description supplies this guidance, and initialize instructions retain the existing 512-byte ceiling. Full adds detail; written targets remain candidates, imported assertions depend on their producer and indexed evidence does not verify live files.

Terse keeps the exact current token under `publication.token`. Repeated conditional-read/change endpoints use `{"ref":"publication"}` to refer to that token. Different baseline/requested tokens retain their own identity. Source citations, hashes, read validators, evidence bytes, candidate/imported basis, truncation and work/response budgets remain independent of display mode.

Repeated per-record producer, producer-version and coverage strings move into a response-local `provenance` array. A record's numeric `provenance` selects that descriptor; its syntax/imported basis and candidate target remain on the record. The table has at most 64 descriptors; heterogeneous overflow retains original provenance instead of discarding it. Full preserves detailed envelopes and per-record provenance. Explicit compact/rich evidence options and cursor bindings remain separate; Full defaults to rich code/document facts when no compact option is supplied.

Readiness/freshness is included on first observation, when substantive state changes, or with `include_status: true`. Explicit status/capability/change tools retain their diagnostic information. Observation timestamps alone do not trigger repetition; failure text, completion watermarks, counts, indexing level and pipeline identity do. Unknown observations stay explicit. Availability of source files and independent source freshness are not inferred from index readiness. Service-mode reads currently report unavailable service freshness until the service-registry observation binding is installed; they never substitute the legacy per-root scheduler.

Status memory belongs to a client, with collection/incarnation-bound digests. The direct native adapter carries a fixed content-free receipt across renewed connections; only a completely received result advances the client's receipt. Independent clients, rebuilt incarnations, changed failures and canceled exchanges cannot inherit an unacknowledged observation. Workers retain shared admission limits across their separate client sessions. The bridge does not reformat evidence after native usage accounting.

Development tests cover schema/help guidance, default/override behavior, timestamp-only changes, new failures, client isolation, closing one client without closing another's admission, exact read validators, native receipt bounds, reconnection and rebuild reset, shared provenance and original source bytes. A repeated-provenance fixture checks a byte reduction without claiming a universal token-saving percentage. The full compact outline/symbol representation, consistent fact result keys and retained change baselines remain separate Phase 7 work in the [completion checklist](service-implementation-checklist.md).
