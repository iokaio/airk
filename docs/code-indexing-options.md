# Review of code-indexing recommendations

Reviewed on **13 October 2026** against the supplied recommendations and primary documentation below. The user subsequently authorized implementation: richer native facts, typed relationships, bundled SQLite and revision-bound SCIP import are now an initial working slice. [Implementation details](code-facts-and-relationships.md) distinguish implemented coverage from follow-ups. No external code-graph engine implementation was copied or integrated; the official SCIP format bindings and embedded SQLite library are dependencies. The accepted DiskANN architecture is preserved.

The strongest direction is richer deterministic code facts over the existing Tree-sitter baseline, followed by an optional, revision-bound semantic import path. Keep installation simple: syntax, lexical retrieval and document facts should work with the bundled helper alone. Compiler/indexer/language-server dependencies should be enhancements with visible coverage and failure states.

## Corrections to the proposal

**Syntax is not resolution.** A receiver expression, decorator, return annotation or route registration can be extracted as written. It does not establish the runtime callee, authorization enforcement, an effective inferred type or application behavior. Framework adapters should say “authorization annotation present” rather than assert “endpoint protected” without supporting analysis. Likewise, impact results are candidates unless the relevant relationships and analysis coverage support a stronger interpretation.

**SCIP is not a universal compiler.** Its schema explicitly allows producers ranging from compiler-backed analysis to syntax-directed heuristics. It represents symbol identities, definitions/references and relationships, including implementations. A caller graph still needs appropriate occurrence/containment and provider evidence; ordinary references must not all become call edges. The upstream indexer list is a starting point, not qualification of every language, operating system, framework or build configuration. AIRK should select and test a specific indexer per ecosystem before advertising precision.

**Storage responsibilities differ.** DiskANN remains the selected final disk-backed vector tier. SQLite is now the embedded revision/exact-fact/relationship catalog; FTS5 is not enabled as an additional lexical engine. Persistent Tantivy lexical indexing remains planned. [DiskANN provider documentation](https://github.com/microsoft/DiskANN) distinguishes disk and in-memory providers.

**Hash-based reuse is not a complete semantic invalidation policy.** AIRK currently reuses unchanged source extraction and re-extracts after an extractor-version change. A semantic result can become stale when another file, package lock, compiler flag, target, generated input or configuration changes. Relationship imports need build/dependency fingerprints and invalidation of affected units; if the dependency graph is incomplete, conservatively invalidate the relevant package/provider domain rather than pretending the old resolution remains current.

**Atlas is a reference to investigate, not an automatic dependency.** The reviewed architecture separates persistent facts, scopes, calls, candidate resolutions and extraction state, and documents bounded/partial analysis. Its README also states limitations around preprocessing, classpaths, dynamic behavior and export resolution. These ideas are relevant, but a pinned source/test/benchmark audit still precedes any component reuse. Some engine source URLs could not be fetched during this review; no full implementation audit or comparative benchmark is claimed. StakGraph likewise deserves measured comparison without adopting its full deployment stack or assuming a license from public visibility.

## Prioritized increments for AIRK

The following remains the broader recommendation sequence. Its initial native scopes/signatures/calls, evidence types, SQLite queries, optional bounded SCIP format adapter, conservative source/build invalidation, selected framework cues and original-corpus measurements are implemented. External producer qualification, unlimited streaming, language-specific signature completeness, broader framework/version packs and live LSP/Ctags remain follow-ups; the adapter must not be described as complete semantic analysis.

1. **Enrich the existing syntax layer.** Add qualified/display names, containing scopes, symbol kinds, declaration/signature spans, parameters and returns as written, modifiers/attributes, attached documentation, inheritance syntax and call expressions. Use language-specific queries and fixtures rather than expanding one generic node-name heuristic indefinitely. Repeated names, overloads, nested definitions, decorators/macros, error recovery and embedded-language boundaries require explicit coverage.
2. **Introduce typed code evidence and relationships.** Keep syntax-extracted, text-occurrence, imported-resolution, heuristic and unresolved evidence distinguishable. Record producer/parser/rule versions, original locations, source hash, collection generation, scope owner, identity namespace and analysis coverage. Do not repurpose DocumentEvidence as a semantic-code schema or use one unqualified `verified` Boolean.
3. **Prototype revision-bound SCIP import.** Start with a small qualified ecosystem set, such as TypeScript, Rust and C#, based on their actual indexers. Normalize provider language aliases and UTF-8/UTF-16/UTF-32 coordinates without guessing; validate ranges against retained indexed content and honor half-open source ranges. Bound input bytes/records and stream large indexes. Reject escaped paths and foreign roots; external symbol metadata must not authorize reading outside the active collection.
4. **Bind analysis before calling it current.** SCIP metadata alone does not establish matching source/build hashes. Require a producer-side manifest binding the index to source inventory and build inputs for current semantic evidence; unbound imports should be quarantined or explicitly revision-unverified. A Git commit alone is insufficient for dirty workspaces. Client/editor buffer versions also need a deliberate policy before persisting LSP results.
5. **Add reviewed framework rule packs.** Qualify route declarations, database access patterns, dependency injection, exception handling and test-to-symbol candidates per language/framework version. Report the matched pattern and source evidence. An annotation name or SQL-shaped string alone must not establish runtime security or behavior. Default packs should be bundled, deterministic and versioned.
6. **Expose bounded relationship retrieval only after providers exist.** Current airk_symbols, airk_imports, airk_references and airk_outline remain truthful. Future code-fact/caller/implementation/impact tools need limits on results, hops, time and bytes, explicit coverage and candidate/resolved labels. Update tool inventories, client probes and descriptions together; do not relabel today's textual references as semantic.
7. **Measure before broadening the runtime.** Benchmark typed fact/lexical backends, imported analysis, optional Ctags/LSP and richer rule packs against the same original corpus. Track indexing CPU/RSS/disk, cold/warm query latency, exact-symbol precision, unresolved coverage, dependency-change correctness, result bytes and task usefulness. Include concurrent agents sharing an index. Estimated token reduction remains an explicit scenario until paired tasks establish practical savings.

## Code placement and qualification

| Existing owner | Proposed addition |
|---|---|
| airk-core | Typed code facts, symbol identities, scoped relationships, provider capabilities and provenance contracts |
| airk-ingest::syntax | Per-language query/extraction profiles, signatures/scopes and reviewed framework rules |
| airk-ingest — optional adapters | Bounded SCIP import, later user-configured Ctags/LSP integrations; no automatic toolchain installation |
| airk-store | Exact fact/edge indexes, provider manifests, coherent publication and reader-safe retention; embedded backend evaluation |
| airk-retrieval | Exact symbol/relationship lookup and bounded expansion alongside lexical/vector candidate retrieval |
| airk-kernel | Generation/build binding, capability reporting, dependency invalidation and provider selection |
| airk-mcp / airk-cli / extension | Shared bounded queries and optional-provider setup/status; no duplicated index engine in the editor |

Keep one collection identity per workspace and allow several agents to query its published generation. Semantic enrichment must publish coherently with its source/fact inventory and preserve the existing read-only MCP boundary. Missing optional tools, failed builds or incomplete provider coverage should leave syntax/lexical/document retrieval usable with clear capability states.

Qualification needs source-change/dependency-change/rename/deletion fixtures, overloads and shadowing, duplicate names, Unicode coordinate conversion, generated-code mappings, missing build environments, stale/unbound imports, timeouts, root isolation and concurrent publication on Windows/macOS/Linux. Unknown languages retain honest UTF-8 fallback. Language-count marketing is not an acceptance test for complete understanding.
