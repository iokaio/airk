The host and a fresh Claude peer independently assessed it, froze their findings, and compared them over two paired discussion rounds. **Disabling automatic installation is not isolation.** The peer traced, and the host verified, `start → refresh → discover`: even with `airk.cli.autoInstall=false`, a trusted window invokes the bundled native executable for `runtime self-test` and `runtime location`. See [discovery](https://github.com/iokaio/airk/blob/c62c1e6936500801dbf41dffdd6e21453e48335d/packages/vscode/src/serviceBootstrap.ts#L192). A separate editor profile likewise does not isolate the OS account. This corrected the peer's initial suggestion that disabling auto-install was sufficient for the first trial.

Both independent dependency audits found the same issues. The host's RustSec audit (`host/cargo-audit.json`, not supplied) checked 373 lockfile packages against advisory DB commit `2295466c4e9df26647fd67d8fa1c705ac2fc7f81`, updated that day: five vulnerability matches and three warnings, exit 1. Only the XML CPU issue above was traced as reachable. The other XML alert requires `NsReader`; the three ZIP alerts require filesystem extraction APIs absent from the inspected AIRK calls. Tokio's `AsyncFd` warning had no first-party caller found; `paste` and `ttf-parser` were flagged unmaintained. Yanked-package checking was not run. These are not five demonstrated AIRK exploits.

The npm audit (`host/npm-audit.json`, not supplied), run on copied manifests without installing dependencies or executing scripts, exited 1 with two high package entries representing one underlying advisory and one moderate entry. All are development/publishing dependencies, not the installed extension's runtime dependency set. Their relevance to publishing credentials warrants maintainer attention; an installed-extension exploit was not established. No continuous advisory gate was found in inspected CI.

Positive controls include OS-user authentication for native IPC, owner-private native control directories, no-follow source traversal and identity checks, bounded PDF subprocesses, bundled hash-verified models, restricted webviews, and user-scoped executable/storage settings. No runtime TCP/UDP exfiltration path was found in scoped searches. Native evidence operations are read-only; separate UI suggestion tools submit inert drafts. External provider execution exists in library code, but no production CLI/MCP caller was established, so it is not a demonstrated current attack entry point. Windows Assistance pipe ACLs remain a low-confidence hardening observation; rotating credentials mitigate access and no authentication bypass was shown.

The source describes a development candidate. The [Marketplace page](https://marketplace.visualstudio.com/items?itemName=iokaio.airk) retrieved during review described 1.6.4; the [GitHub releases page](https://github.com/iokaio/airk/releases) showed 1.6.0 as latest. Those observations do not prove tampering, and neither artifact inherits this 1.7.2 review. Recorded Windows candidate tests are maintainer evidence, not tests we ran or macOS/Linux qualification.

For the trial, use a disposable VM without credentials, sensitive folders, or broad host mounts, and a small synthetic/public corpus. The provided restricted container can evaluate the native engine separately; it does not evaluate the VS Code extension. Before later everyday use, review the actual chosen artifact/provenance, deliberately select sources, configure `.airkignore`, use private storage, and consider disabling result persistence. Fix the XML dependency or exclude affected XML/SVG/Office inputs where hostile documents are possible. Building from source also executes dependency build scripts; perform that in the isolated environment.

Uninstall is not complete data erasure. The inspected code preserves native index data and leaves shell/PATH integration behind. Successful [extension cleanup](https://github.com/iokaio/airk/blob/c62c1e6936500801dbf41dffdd6e21453e48335d/packages/vscode/src/extensionUninstall.ts#L141) does attempt to remove Workbench sessions, so it would be wrong to claim those are always retained. Cleanup failures, exports, backups and evidence already sent to agents remain separate. Use explicit project-data removal and inspect the cleanup outcome.
