# Service resource admission and observations

This is implemented native 1.4.0 behavior, used by the default extension and public CLI. Installed-platform and workload qualification remain open. The [completion checklist](service-implementation-checklist.md) records those gates.

The service owns finite resident and work grants across registered projects and storage roots. Workers cannot claim a job without its exact identity-bound grant, or fall back to the old four execution slots per storage root. The legacy scheduler is not consulted for service work. A worker keeps its project lease until actual process exit. Each resident receives one concurrent direct query and 64 KiB of output credit, within the broker's 32-query/2 MiB global ceiling. Up to 32 residents are admitted subject to memory headroom; this replaces the fixed four-worker service scaffold.

All service-bound MCP sessions now share one inner execution permit across evidence, status, rendering and usage accounting. Accepted native work retains that permit through client cancellation and local transport failure, even if its outer IPC grant becomes free. This prevents the standalone adapter’s four evidence plus two control slots from multiplying a resident’s query materializations. Shutdown drains the shared permit once; independent service health and cached observations do not acquire it. The queue remains finite (sixteen waiting, five seconds), and status reports that the execution budget is shared.

A resident reserves 512 MiB including its baseline and one bounded query materialization, the shared model 512 MiB and service overhead 160 MiB (32 MiB main-process allowance plus a 128 MiB watcher reservation). Each source/verification/rebuild job reserves at least 768 MiB of working space; additional parallel extractors reserve their bounded result, transient encoding, source and parser overhead. Jobs receive 1–4 extraction threads from the shared source-thread limit. A single project can use four extraction threads when its grant permits; waiting projects share the source budget. These are admission reservations and library bounds, not OS memory or CPU quotas. Query native work and operating-system threads also consume resources. On a single CPU, source and inference execution time-share it.

The initial presets below are concrete policy defaults for qualification, not a measurement gate on the architecture. CPU counts honor Rust's detected available parallelism; detected total memory honors supported Linux cgroup limits.

| Setting | Responsive | Balanced (default) | Throughput |
|---|---|---|---|
| Source extraction threads | 1 | half available CPUs, at least 1, at most 16 | available CPUs minus 2, at least 1, at most 16 |
| Inference batch workers | 1 | 1 | 1 |
| Memory admission limit | quarter detected memory, 2–4 GiB | half detected memory, 2–4 GiB | three quarters detected memory, 2–8 GiB |
| Source-byte pacing per job | 8 MiB/s | 32 MiB/s | 128 MiB/s |

Default and override admission limits never exceed a known effective machine/cgroup memory ceiling. A smaller machine may run health/control while deferring project work rather than manufacturing headroom.

Validated overrides permit 1–64 source threads (clamped to detected CPUs), 1–4 inference workers (also CPU-clamped), 1–64 GiB memory (a limit below the minimum job headroom can admit queries while deferring background work) and 1–1,024 MiB/s source-byte pacing. Pacing checks between bounded artifacts; it does not claim to limit all physical disk I/O or interrupt an atomic publication. Tract math uses an explicit single-thread executor inside each bounded embedding batch worker, preventing a hidden library-global thread pool from multiplying the allowance. Existing inference already in progress keeps its old bound while a configuration change governs subsequent work.

The scheduler rotates projects, prioritizes fresh source work and ages waiting verification/vector work after five seconds so it cannot starve under continuous source arrivals. Metadata discovery uses a stable 32-project cursor across all 1,024 registrations; inaccessible projects in the first page cannot hide later ones. One project runs one job at a time. A granted job is not replaced with another pending request. Pausing stops new claims and pauses running work at a safe boundary; explicit running cancellation persists intent until the fenced worker records its canceled receipt. Neither a canceled client wait nor an expired work horizon releases an active charge. Completion acknowledgement or confirmed process exit does.

`resources` returns a cached content-free `ResourceSnapshot`, its observation age and a separate configuration-error flag. `configure_resources` validates and persists the user configuration in the protected service directory. A lower limit retains existing charges and blocks new grants until enough capacity drains. An invalid saved configuration blocks admission while health remains usable, until an explicit valid configuration replaces it. Ambiguous configuration timeouts require reading the configuration/status before assuming failure.

The supervisor observes RSS for its own PID, owned project children and the owned embedding and source-watcher children. Windows uses read-only process counters; Linux uses procfs; macOS uses libproc. Admission uses the larger of reservations and observed RSS, rather than adding them and counting memory twice. Summed RSS may conservatively count shared executable pages more than once. Windows/Linux also report available memory; Linux takes the smaller host availability or supported ancestor cgroup limit minus current usage, including a real zero available value; unavailable counters remain unknown, and telemetry completeness is explicit. macOS available-memory pressure is currently unavailable. High RSS or less than 128 MiB available memory stops new admission. Observations do not forcibly reclaim running work; large native operations retain their resources until completion or exit.

Windows supervision and extraction share the native `airk-process` containment primitive. Each owned job has at most 32 processes; PDF extraction can retain its stricter one-process limit. Cleanup closes descendant creation, captures bounded exact process handles, requests termination and waits for both an empty job and captured-handle exit before releasing credit or owner locks. Existing CPU/memory limits remain in force while draining. PID membership is verified before retaining a handle; no PID is used to kill another process. Unknown kernel state keeps cleanup and ownership pending. This logic runs outside health handling. [Unix provider cleanup](service-processes.md) now uses non-reaping group ownership and bounded native exit observations. [Surviving Unix provider guardians](service-provider-lifetime.md) now retain project ownership and durable admission through worker/guardian crashes; installed-platform qualification remains open. Microsoft documents [asynchronous process termination through a job](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject) and [job accounting](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information).
