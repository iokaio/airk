# AIRK 1.2.5 current index (unreleased)

AIRK 1.2 uses one current index for each root/collection. CLI, MCP and extension operations use this store. Source files remain read-only. Source control owns source history; AIRK does not retain searchable historical generations, checkpoints or rollback targets.

## Fresh state and ownership

State lives under `<data-dir>/collections-1.2/<collection>`. The default data directory is `.airk` under the workspace. The quota ledger is `.quota-1.2`; the scheduler uses `scheduler-1.2.sqlite3`. The extension uses a new collection registry. Existing `collections/` indexes and their saved per-collection configuration are left untouched and are not imported. Configure 1.2 roots, extraction detail, vectors and limits afresh. Shared provisioned model assets may be reused only after digest verification and admission into current collection ownership.

`current.sqlite3` has SQLite `user_version=126`. A bounded owner header binds canonical root, collection, incarnation and admitted database capacity. A foreign owner, incompatible version or old catalog/snapshot files inside the new namespace cause explicit failure. They never become an empty index. `index --full` rebuilds compatible current derived evidence from source with the currently saved 1.2 policy; it does not read or migrate a 1.1 index.

### Upgrading a Tantivy collection

Before each extension index pass, `collections prepare-rebuild` checks for a recognized obsolete owned format. If found, it discards obsolete derived state before inspecting saved vector settings or installing model assets, and the pass becomes a full rebuild. It is a no-op for format-126 indexes. The CLI `index --full` performs the same preparation itself.


The 1.2.5 FTS5 format requires a full rebuild of a 1.2.0–1.2.4 Tantivy collection. The extension starts that rebuild automatically when indexing begins and explains the upgrade in a notification. Keep the existing collection ID. For the CLI, run:

```console
airk --root /path/to/workspace --data-dir /path/to/state --collection existing-id index --full
```

The rebuild discards that collection's old derived database, lexical segments, retained objects and pending publication journal under writer/request exclusion. It preserves saved roots, extraction/vector/compression settings, the collection ID, shared provisioned model assets and source files. There is no Tantivy data conversion or retained history copy. A durable rebuild marker permits retry after interrupted deletion; ordinary readers reject that state instead of presenting it as an empty ready index. Unknown versions, foreign ownership and linked targets fail before deletion. Restart extension indexing or repeat the CLI full rebuild after an interrupted upgrade. Normal reads never trigger disposal; extension indexing only does so for a recognized obsolete owned format.

`index --full` on an already compatible FTS5 collection retains the existing full-reindex behavior. The older 1.1 namespace remains a separate fresh-state boundary.

## Publication and reads

A scan hashes eligible saved sources and verifies exact extraction/profile reuse. Only changed paths replace authenticated map entries, native discovery postings, continuity metadata and FTS5 documents. The base commit immediately retires incompatible vectors and saves source/extraction/model/policy-bound semantic work. Later commits add bounded vector batches to the same current index. Identical semantic inputs reuse exact graph IDs; new inputs run bounded embedding batches. DiskANN applies captured record afterimages, including tombstones and exact-input resurrection. Configuration changes replace affected collection evidence; full rebuilds and model changes construct a fresh graph instance. A no-op scan retains its token. Empty collections can publish configuration changes.

The current head binds the collection configuration, counts, artifact map, selected lexical manifest and graph root. Retained source/extraction, model, cache-pack and imported-analysis ownership is authenticated through that head. Imported producers keep their source/build binding and provenance; invalidated analysis is removed on indexing. Compact source-size measurements support optional usage comparisons without decoding the full source corpus.

Each evidence request holds a multiprocess shared gate from selection through materialization. Publication and cleanup require the exclusive gate. Active readers can cause an explicit busy/retry result; requests during Applying are unavailable. Idle kernels and MCP connections hold no generation pins. Later requests see the latest head. Collection removal and relocation also respect active requests.

An exact revision is an equality check against the current token. A superseded token fails explicitly before evidence or inference is returned. File/fact/outline cursors expire when their head or filters change. Conditional validators bind the requested representation, so an unrelated file edit need not invalidate unchanged file content. Move following requires an exact current artifact handle and matching source hash; similarity and an old path alone never redirect a read.

## Semantic readiness and deferred work

The VS Code extension drives remaining semantic work after the base pass and on trusted workspace reopen. In the 1.2.5 candidate, `airk semantic run --scheduled` reuses one model for up to eight selected-collection batches and a 60 s soft budget checked between commits. One running batch may exceed that budget. New source work and pause cause a yield between commits; the command returns readiness and measured work counters. This requires no installed service or open dashboard. Manual mode permits completion of already requested semantic work; Pause prevents further batches. The command shares the native worker lock without executing another collection's jobs.

Scheduled indexing returns after the lexical/fact base commit. The native scheduler then processes at most one 32-artifact semantic batch per worker pass. Each batch commits its vector changes and reduced pending set atomically, advancing the current revision; other collections retain scheduler turns. Explicit `airk index` and `airk index --full` drain the same durable work before returning. `airk semantic run` resumes a pending or failed job using retained inputs after restart, without rereading live source. Pause stops automatic enrichment, and Resume or a new index request clears a scheduler block. A failed batch retains the completed base and earlier vector batches. If index integrity itself prevents a failure-state commit, the scheduler records a blocked error and stops automatic retries.

`airk index --paths path/to/file @alias/other/file` directly publishes a scoped source pass in the selected collection and returns after lexical/fact publication. It preserves unrelated bindings and can leave semantic work pending. Add `--scheduled` to join the shared durable queue; use `semantic run` to finish retained work explicitly without queue registration. It uses normal ignores, protected reads and source hashes. Exact hinted absence may retire that path after reconciliation; unrelated absence is never inferred. Directory and ignore/configuration hints, changed configuration and incomplete discovery fall back to a complete scan. Scoped passes do not finish discovery epochs or advance the complete-inventory timestamp. Watcher/editor hints are bounded, coalesced by revision and retained across concurrent events; periodic full reconciliation covers missed events. See [the terminal loop and review](indexing-speed-review-2026-10-21.md).

Reuse lookup checks the retained objects' presence, regular-file type and stored length. It does not decode unused retained copies to establish reuse. Every read that consumes retained bytes still authenticates them; explicit retained-data diagnostics remain the complete verification route. Same-size corruption can therefore remain undiscovered by an unchanged rescan and still fail an evidence read. Full FTS5, model and publication integrity checks remain in place.

Semantic failures retain their original typed cause when recording the failure also fails; the recording error is added as context. Temporary current-gate contention remains retryable without publishing failed semantic state, and a secondary busy gate cannot turn a corruption or permission failure into a retryable result.

`airk_status`, search results and the extension report `semantic_readiness`: disabled, pending, partial, ready or failed; selected/completed artifacts; optional selected unit count and completed units; saved model/selection identities and a bounded failure reason. An unknown unit total remains null. The base publication removes vectors for changed or deleted inputs immediately. Pending work binds each path to its retained source hash and extraction object plus the saved model and selection digests; a superseding scan replaces incompatible work. Vector results always cite the current retained source. Exact/lexical evidence stays queryable while vectors are pending or failed.

The saved default search policy is `partial_hybrid` unless changed with `airk semantic policy lexical_while_pending` or `airk semantic policy require_complete`. The first discloses partial hybrid results; the second returns lexical evidence while enrichment runs; the third makes default search explicitly unavailable until vectors are ready. Explicit vector and hybrid requests disclose current coverage and never silently become lexical queries. Reads and status never start enrichment. The panel's vector opt-out still selects lexical search. `IndexReport.first_ready_us` measures the base publication; `fully_ready_us` is present only when semantic work completes in that invocation. Readiness timestamps around publication are wall-clock observations, not precise gate timing.

Scheduled cold scans and compatible updates can commit exact source, fact and lexical evidence in bounded batches before traversal finishes. `discovery_readiness` in status and search gives a scan epoch, processed and committed artifact counts, and `pending`, `partial`, `ready` or `failed` state. The total remains unknown until the scan completes and validates its inventory. Search sets `truncated` while discovery is incomplete: a missing result cannot establish that the source is absent. The `require_complete` default policy waits for both discovery and semantic readiness. Each batch advances the current token, and earlier committed batches remain readable after a failed scan. A later complete scan reconciles the inventory before removing absent paths. This progressive path applies to scheduled non-full scans with compatible configuration, including populated collections and interrupted scans. Full rebuilds and configuration changes publish their source inventory at completion.

From 1.2.5, source batches persist pending semantic work without running inference inline; the scheduler enriches it after discovery, so semantic inference cannot stall the remaining source traversal. Cold-scan vectors therefore become available after source discovery. Compatible vectors from an existing index remain usable; changed inputs retire their incompatible vectors when their source batch publishes.

The first batch targets 32 changed files or two seconds of scan time. Each successful batch doubles the count target up to 4,096; the 64 MiB source-byte trigger remains. Later scan intervals are four times the previous publication duration, clamped to 2-30 seconds, to amortize expensive transactions. These are checked between captured artifacts; extraction and publication can take longer than the interval.

`airk_changes` validates current remembered citations/handles and reports freshness independently. A noncurrent baseline is `baseline_unavailable`; there is no complete observed-change history. Historical suggestions report unavailable. The unreleased source removes the unsupported `airk_history` MCP endpoint; published 1.2.4 helpers still list it. Capabilities advertise history/checkpoints as unsupported; the extension exposes no historical controls.

## Recovery and cleanup

Preparation retains and validates bounded inputs. In an admitted SQLite transaction it applies changed-path FTS5 updates, flushes pending postings, captures a digest of the schema, document content and FTS5 shadow rows, then rolls back. Prepared stores the captured input metadata and digest. Applying repeats those exact updates from retained objects and verifies the same digest before the atomic SQLite commit. It neither copies a complete lexical database nor creates immutable segment forks. The two applications add work and must not be presented as a measured speedup. The base is still readable in Prepared. Applying excludes reads until captured catalog, lexical and graph afterimages are committed under one new token. Reopening through the kernel, CLI or MCP recovers durable pending work without rereading live source. Recovery is idempotent. A durable runtime-bootstrap recipe also permits completion of interrupted empty-index initialization.

From 1.2.4, an index scan can recreate missing retained source/extraction objects from freshly captured and hash-validated live sources. If the live file changed or was deleted and its old extraction is missing, the writer can instead retire that path's prior posting memberships from the authenticated current map. A complete traversal proves the committed membership set; canonical posting encodings and collection-scoped keys are checked before staged path removals. Replacements publish new captured evidence under its actual source hash. Deletions remove old evidence without recreating the missing payload or writing the deleted source. Other paths sharing a posting remain intact, and the normal journal publishes the artifact, posting, lexical and vector changes together.

This retirement fallback applies only to missing retained objects. All missing prior paths in one publication share one authenticated base-map traversal, including when healthy changes have already staged afterimages. The scoped map key must establish the Posting domain before strict posting decoding; unrelated JSON fields do not establish that identity. Corruption and permission errors remain failures. Recovery traversal is bounded by four million entries and 1 GiB of cumulative value bytes per transaction, one million nodes per traversal, and 65,536 selectors per artifact. Deferred recovery is additionally bounded by 100,000 paths, four million combined old/new selector memberships and 1 GiB of counted path/language/selector bytes. Exhaustion fails explicitly before publishing a partial retirement. An existing Prepared/Applying journal still requires its captured inputs; this path never substitutes changed live bytes into a pending transaction. Other missing metadata or damaged ownership can still prevent recovery.

Before the one automatic fresh-scan retry, admission requires a Ready index with no pending journal. If a diagnostic reader holds the current gate, typed lock contention gets up to 120 seconds of bounded grace, with polling backing off from 25 ms to at most 250 ms. This allows more time for a foreign `collections diagnose` page of up to 128 files (32 MiB by default, up to 512 MiB explicitly); it does not guarantee completion on every disk. Waiting holds no collection writer, execution lease or quota reservation. Pause is checked between attempts and stops automatic repair before another scan; a subsequent explicit manual request can override the persisted automatic pause. Journal, permission and other errors fail immediately, and contention still fails visibly when the admission budget expires.

Database growth reserves both the larger database capacity and rollback allowance before syncing its owner header. Quota or physical-space denial before Applying preserves the base. Failures after Applying remain unavailable until captured recovery succeeds; they do not promise a readable prior index. Logical quotas are conservative ceilings, not preallocated physical disk space.

Writer connection admission rejects SQLite's silent fallback to a read-only connection before writer PRAGMAs or journal work. On Windows, only a no-write native access probe reporting sharing denial (OS error 32) permits reopening within a five-second allowance, with 25–250 ms backoff. A successful native probe permits one immediate reopen if the conflict cleared between checks. Other access failures remain immediate; the retry never changes permissions or interprets arbitrary SQLite error 8 as transient. Database/probe handles are released between attempts, while caller-held writer/request gates and captured capacity safeguards stay in place. Non-Windows writers reject unexpected read-only connections without this sharing retry.

A failed pre-Prepared transaction intentionally leaves its durable allowance available until rollback/recovery is proven. Ready recovery, after validating the committed lexical component, and new component preparation now retire abandoned current grants under the writer and exclusive request gates. Both require Ready with no pending journal. Every candidate incarnation is validated before any grant is released; a foreign incarnation prevents the whole cleanup. Other collections and Prepared/Applying allowances are preserved. Cleanup changes quota accounting only and leaves the current publication unchanged.

Successful publication attempts bounded cleanup. It removes unreferenced current objects only after a complete authenticated ownership plan under the publication gate. Pending transactions, foreign ownership, links or corrupt ownership metadata prevent deletion. The report exposes `maintenance_error`; a successful publication stays committed if subsequent cleanup fails.

```console
airk collections maintain
```

The extension command **Reclaim Unreferenced Index Objects** runs the same operation. Its result reports `removed_files`, `removed_bytes` and `pending`. Repeat a pending pass after resolving the cause. Historical retention/prune/checkpoint commands return unsupported errors. Source files and other collections are never cleanup candidates.

During a scan, the collection writer also owns captured objects that are not yet in the current head, and prior objects still needed for reuse. From 1.2.3, an in-process capture guard defers object reclamation across intermediate base and semantic publications. The guard is released after scan reconciliation, before the final publication performs normal bounded cleanup. The exclusive collection writer prevents another process from reclaiming these inputs. On failure or process exit, committed/journal ownership remains authoritative; unused captures can be reclaimed on a later maintenance pass. Quota admission remains in force throughout the scan.

## FTS5 evidence integrity

AIRK supplies its own normalized terms, including identifier aliases and CamelCase components, stored as prefixed raw tokens with SQLite's ASCII tokenizer and explicit underscore token characters. This preserves Unicode, accents and whole underscore identifiers without hex expansion. Terms longer than 8,000 UTF-8 bytes use a domain-separated digest to avoid FTS5 token truncation. Query terms are joined with AND; user text cannot introduce FTS operators. Prefix filtering is literal and case sensitive. Results use stable document identity order; this replacement does not introduce BM25 ranking or change hybrid fusion.

Each request verifies the head-bound digest of the FTS5 schema, all document rows and all posting/configuration shadow rows before querying, including queries that return no matches. Verification streams rows and is cached only within that read handle's shared gate. Only citation metadata is stored in the document payload; text is loaded from retained extraction. Candidate hashes and locations are still checked against retained current evidence. This verification remains proportional to lexical index size; fewer files are not a claim of constant query cost. A 64 MiB SQLite value ceiling and document bounds reject oversized rows. SQLite remains on rollback journaling, with the existing quota and reader exclusion contracts.

Publication verifies the physical base once under the exclusive writer gate and retains a transient digest ledger grouped by 256 row IDs. Preparation and replay rehash affected document/data groups reported by SQLite's update hook. The schema and `WITHOUT ROWID` index/configuration tables are scanned separately because the hook does not cover them. The final root folds the group digests and byte counts; recovery reconstructs its ledger from physical rows. No persisted checksum substitutes for verification and no previous index is retained. Unchanged semantic/resource publications reuse the verified base during that transaction. Base verification and digest folding still grow with the corpus.

The 1.2.5 review candidate uses database format 126, so early local format-125 FTS5 candidates also require a full rebuild. Extension indexing starts it automatically; CLI users request `index --full`. The upgrade removes owned retained source copies, extraction payloads and captured model objects, then recaptures them. Original source files and saved collection settings are preserved.

## Work bounds and qualification

The runtime admits at most 100,000 compact scan entries and 512 MiB of compact scan metadata. Per-update capacities distinguish files from their fan-out: 100,000 changed files, one million vector occurrences/keys, and four million final catalog changes with a 1 GiB encoded map-plan/journal byte ceiling. Captured input metadata is capped at 256 MiB; captured evidence at 8 GiB. Prior/generated continuity metadata is processed one file at a time with an 8 GiB cumulative allowance each; individual file metadata remains capped at 16 MiB. These are admission ceilings, not a promise that every combination fits memory, disk quota or acceptable latency.

Preparation reserves at most half the available collection/root quota, capped at 32 GiB, leaving independent room for durable database growth and recovery. Graph staging uses at most one quarter of the remaining preparation reservation, capped at 4 GiB, with at most one million dirty records. Its SQLite page cache remains 16 MiB. Graph operation counts and cumulative logical read bytes are saturating measurements, not transaction failure thresholds. Individual DiskANN insert/search read budgets remain enforced. Map planning has no cumulative mutation-count cutoff: repeated changes to the same posting coalesce, while its final bytes and the journal's rows/bytes remain bounded.

The embedding cache admits one million references, 4,096 packs, a 256 MiB manifest and 64 GiB of cumulative verification/lookup reads. Individual packs remain limited to 16 MiB/4,096 records, decoded pack indexes to 4 MiB and open handles to eight. An exact vector binding supports up to 2,048 sorted occurrence IDs within its unchanged 256 KiB value cap. Storage defaults remain 100 GiB per collection and 500 GiB per root; raising a count ceiling does not bypass those quotas.

Retrieval limits remain independent of indexing capacity. Fact pages examine at most 256 candidate files plus a resumed file and 256 MiB of evidence/metadata work. Relationship traversal additionally bounds hops, symbols and files. Oversized work fails or reports truncation before claiming completeness.

`IndexReport.current` reports changed artifacts, lexical documents, graph records, logical graph-read bytes, verified base-record fetches, update-local proof-cache hits/evictions and linked lexical bytes (zero with FTS5). The proof cache holds at most 256 authenticated base proofs and 8 MiB of record/proof payload per graph update; dirty afterimages always take precedence, and recovery opens a fresh cache. SQLite owns graph page I/O, so these logical counters do not measure physical device reads. One-file changes do not reinsert the complete corpus into FTS5 or DiskANN. Source scanning, streamed FTS5 integrity verification, metadata inventory, complete ownership checks and the missing-extraction retirement fallback still have corpus-dependent work. These counters do not establish constant update latency or a measured end-to-end speedup. The bounded preparation registry lives in memory; `vector_registry_rows` counts its distinct keys and `vector_registry_bytes` is zero because no private registry database is written. That zero is not a measurement of heap use.

The following platform statement records pre-FTS5 qualification; it does not qualify the 1.2.5 replacement. Original small vector fixtures qualify transactional behavior; they are not MiniLM relevance evidence. Process-exit tests are distinct from power-loss durability. Windows and Linux x64 container checks qualify the exercised paths; macOS, other architectures and network filesystems remain unqualified. The stage ledger records executed checks and remaining S10–S12 work.
