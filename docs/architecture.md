# Architecture

The 1.5.1 Explorer presentation and source/file libraries remain extension adapters. Source-file targets are per-project metadata retained across editor focus; choosing another project remains explicit. File libraries enumerate bounded pages under reviewed workspace roots and parse inert plans/strategies/search recipes without executing their instructions. The webview retains UI theme preferences only; native service/index ownership is unchanged.

Explorer Assistance remains an extension adapter alongside native read-only Retrieval. Its fourteen tools include offline template discovery, non-admitting validation, inert navigation proposals and explicit, bounded, expiring user-shared snapshots; they add no engine orchestration or source writes. Explorer and Assistance compile one help catalog from Explorer Markdown plus the native engine's static topic source, making engine guidance available offline in the UI. Live command/tool schemas still come from the selected runtime's airk_help. Plan loading is a bounded editor-owned adapter: Markdown imports remain unverified drafts while JSON preserves state/provenance. Webview deadlines distinguish timed-out reads from unknown action outcomes and never replay actions.

Extension installation updates recognized existing workspace agent connection fields after native registration supplies the stable-launcher binding. Codex TOML, Claude Code JSON and Copilot JSON edits use guarded editor saves, preserve policies and never execute old commands or edit user-wide configuration.

The MCP frontend serves bundled `airk_help` without a worker/evidence query. Native CLI supplies a lazy public-command catalog generated from its parser; MCP supplies topic guidance and its own schemas. Scoped status work observations use existing instance-fenced metadata RPCs; store supplies a bounded read-only FIFO queue observation. Progress/watcher/worker samples remain distinct from kernel publication readiness. No management action or agent reasoning is added to MCP.

The native CLI captures path-free process/build observations for `airk_status.runtime`. Core owns the serialized metadata contracts; MCP adds the native host's bundle before rendering/accounting without taking a dependency on CLI or opening service state itself. The worker observes exact-instance broker health independently of index readiness and labels frontend metadata as client-reported. Kernel status remains collection evidence.

Extension CLI installation removes obsolete terminal executable copies at its own fixed global-storage locations. Native CLI ownership remains responsible for retiring the previous runtime: it fences the active selection, journals inventory-bound cleanup, drains owners, clears rollback and restarts the selected runtime. Sources, indexes and settings remain outside executable retirement. Managed provider payloads are excluded. See [console installation](service-console.md).

Trusted extension activation now installs the approved runtime and terminal forwarding command and sets up new workspace folders automatically. Existing 1.4 project/storage/watching selections remain native and are preserved on compatible runtime updates. Runtime activation and any schema migrations stay in the native adapter; the dashboard renders metadata and does not open indexes.

Store classifies registry storage contention; the CLI applies the existing registry_busy response only to an explicit whitelist of read-only observations. Mutation and receipt recovery contracts remain unchanged, including RequestEpoch receipt pruning.

Current 1.5.2 service lifecycle: the public CLI and extension are service clients. Only native worker roles open project Kernels/stores; the broker remains metadata-only and retrieval/inference use direct scoped transports. Source and lockfile versions are synchronized. Container/package cutover and Windows/Linux qualification receipts refer to the historical 1.4.0 candidate. The 1.4.1 installer/version evidence remains historical. Version 1.4.2 changes machine-scaled resource admission, protects query headroom, caps shared source pacing and expands bounded watcher traversal; validation is recorded in [its release notes](release-1.4.2.md). Native Mac and the broader installed-platform/security matrix remain unqualified; see [the qualification record](service-cutover-qualification.md).


AIRK is an independent local indexing/retrieval kernel. Source workspaces are authoritative; all index state is derived. It does not reason, generate answers, manage agents, route model calls or require an external database.

The [October 17 release summary](releases-2026-10-17.md) covers the 1.1.0–1.1.2 changes and upgrade behavior. This page describes the resulting component boundaries; release publication and workload qualification are recorded separately.

~~~mermaid
flowchart LR
  W[Workspace files] --> I[Native ingestion and format facts]
  I --> K[Collection-scoped kernel]
  K --> S[Collection disk state]
  S --> R[SQLite FTS5 lexical and authenticated fact retrieval]
  V[Default local embeddings and disk-backed DiskANN] --> R
  C[CLI or optional extension] --> N[Native service: registration, grants and durable work]
  A[Coding agent] --> M[Read-only stdio MCP]
  M --> N
  C --> P[Scoped project worker]
  M --> P
  N -. supervises .-> P
  P --> K
  P --> H[Shared inference helper]
  N -. lifecycle and admission .-> H
  R --> K
  K --> E[Bounded evidence and original locations]
~~~

The service brokers connections and schedules metadata-bound work. Evidence and model inputs travel directly between clients, project workers and the shared helper; those payloads do not pass through the broker.

Explicit legacy retirement is an administrative exception to ordinary service-only project access: CLI owns old OS-startup review/removal, while store owns offline deletion of recognized 1.3 derived files under old worker/writer/reader exclusion. This adapter reads ownership/file metadata, never opens the old database or constructs a Kernel, preserves sources/settings/usage, and cannot become a normal query/index fallback. See [the legacy transition contract](service-legacy-transition.md).

Core owns the shared watcher directory bounds; kernel planning and native CLI heartbeat validation consume the same constants. Native CLI retains process supervision, kernel owns admission and traversal, and the extension renders their observations.

Version 1.4.3 derives bounded WAL/shared-memory capacity from the admitted database image and reserves the matching lifetime quota before writer opening or recovery. Store owns that policy and compatibility reads; growth estimation uses logical SQLite pages. See [storage reliability](storage-reliability.md) and the [release record](release-1.4.3.md).

## Dependency boundaries

| Crate | Responsibility | AIRK dependencies |
|---|---|---|
| airk-core | Artifact/query/fact/citation contracts; storage and embedding traits | None |
| airk-process | Native owned-process containment and confirmed descendant cleanup; no indexing or service policy | None |
| airk-ingest | Ignore-aware discovery, hashing, native grammars, document extraction/chunking | core, process |
| airk-store | Content-addressed sources/extractions, authenticated SQLite catalogs/FTS5/postings/graph records, usage ledgers, durable intents, locks, quotas, relocation and current-object cleanup | core |
| airk-retrieval | Local word-vector/ONNX inference, mutable DiskANN algorithms and retrieval primitives | core |
| airk-kernel | Collection-scoped publication, retrieval/rank fusion, response budgets, coverage, scheduling, usage and maintenance services | core, ingest, store, retrieval |
| airk-mcp | Schemas, official SDK transport and result conversion | core, kernel |
| airk-cli | Commands, native client setup, lifecycle and process/IPC adapters | core, process, kernel, mcp, store, retrieval contracts |

Core must remain free of parser, filesystem, inference and transport implementations. Adapters call kernel services rather than bypassing validation or collection scope. MemoryStore is an available in-memory snapshot adapter; the CLI kernel uses FileStore with current SQLite FTS5/DiskANN storage.

The CLI also owns the [bounded process diagnostic ring](service-logging.md). Core supplies content-free record contracts; logging never opens indexes, and diagnostic write failure cannot block health or shutdown.

The [service implementation plan](airkservice-architecture.md) includes core service identity/grant contracts, a kernel in-process broker/admission reference policy, CLI native control transport and a store-owned registry/ownership adapter. `serve` and explicit `service health/shutdown` commands operate without opening collection stores. The CLI owns OS startup-manager adapters and the opt-in [offline installer and stable launcher](service-installation.md); kernel contains no Task Scheduler/systemd/launchd adapter. Native endpoints authenticate same-user peers through Windows user-only ACLs/token checks or Unix private directories/peer UIDs; process-lifetime locks elect one owner. The separate bounded SQLite service registry retains registration, pagination revisions, pause and monotonic worker epochs, with an owned bootstrap receipt for interrupted initialization. The [native service protocol](service-protocol.md) connects supervised lock-bearing project workers, bounded direct query endpoints and a read-only stdio bridge. The service exchanges lifecycle/connection grants only; worker-local policy admits queries without a service payload hop. The [durable service job ledger](service-jobs.md) adds atomic request receipts, bounded queue retention, pending-work joins, pause and fencing-checked recovery/completion. A 32-slot metadata actor connects registration, project pages, enqueue/inspect, pause and queued cancellation to the native control endpoint, keeping SQLite contention off health handlers. Kernel canonical-path checks and store destination-conflict checks protect registrations. Supervised workers now execute accepted index/reconcile/vector/verification jobs, hold ownership through process exit and stop admission on parent loss. The extension and public CLI use these native defaults; the editor-owned scheduler and direct public store writers are retired. A [shared embedding child](service-embedding.md) now provides compatible loaded-session reuse through direct worker IPC, with a separate process lease and bounded initial queue/thread/working-memory policy. [Ordinary/replacement publication and request-held object leases](service-publication.md) are implemented. Captured recovery and bounded retirement now run as service-granted jobs with durable backoff and cached maintenance observations. A separate supervised [source-watcher child](service-source-watching.md) owns directory notifications; fenced metadata-only notices admit durable reconciliation independently of editor windows. [Fenced work observations](service-progress.md) report real advancement and phase timing independently of health, with a pause-aware worker watchdog. Durable recovery receipts and resource observations are integrated; the complete workload and installed-platform qualification remain open.

The service registry now owns transactional source/data isolation, including fenced additional-root metadata and verified installer-private paths. Kernel/native adapters resolve canonical source identity; the store compares bounded metadata and installer ownership receipts without opening source bytes or collection databases. Project workers recheck current source configuration against this ledger before capture. Missing registered roots can open only existing ownership-matched retained state; scans fail explicitly while retained queries remain available. See [source isolation and jobs](service-jobs.md) and [retained worker reads](service-protocol.md).

The shipped inference helper embeds the pinned FP32 MiniLM assets after explicit build preparation and catalog/digest verification. The public `setup-model` command requests a durable native setup job; neither reads nor MCP tools install models. Global model provisioning serializes atomic publication, preserves explicit custom inputs and rejects incomplete inputs. Project workers retain exact lazy references to shared immutable files, without collection-local model weights or network fallback. Model/pipeline identity and platform-specific batching remain unchanged.

The service runtime pair builds `airk-embed` with `embedding-worker` and `airk` with no default features in separate Cargo invocations. `scripts/build-service-runtime.py` stages that pair in a fresh directory after checking the main dependency graph excludes `tract-*` and `tokenizers`. CLI process adapters verify both installed executable hashes, platform and version from `airk-runtime.json`, negotiate bounded anonymous-pipe messages, enforce a finite request deadline and terminate failed helpers. Retrieval uses a host-injected embedding connector; kernel usage calibration delegates transformer tokenization through the same helper while retaining local byte-BPE. The service helper provisions bounded verified global model sets from embedded bytes or explicitly selected local inputs. Collections capture runtime-scoped exact references; metadata-only source setup uses a lazy direct helper session even when Cargo feature unification also enables local inference. A separate durable `model_setup` job installs the bundled default; scans and reads never provision. Installed model inputs persist independently of loaded sessions and collection retirement. Transformer calibration definitions and tokenizer assets use a separately bounded shared cache under the same model owner and disk allowance. Exact definition identity is preserved and checked across direct setup; sample text and per-collection usage ledgers are excluded from global asset storage. The helper does not publish project revisions. Only the helper includes model weights and native inference. The default extension, CLI and packaging adapters use this pair and the shared embedding pool; final installed-artifact qualification remains open. Installed-payload authenticity remains the trusted installer's responsibility; digest checks alone are not publisher authentication.

The retrieval crate owns native CPU feature observations and the embedded qualified model catalog. Kernel exposes this read-only service to `airk model-catalog` before any collection is opened. Extension setup uses its selected profile's pinned manifest/assets; the Python provisioning script reads the same source catalog. Capability observations do not open model plans, alter embedding identity or establish that a particular backend kernel is selected. The only automatic profile remains FP32 MiniLM; INT8 qualification and automatic selection are future work.

The [single-current-index foundation](current-index-foundation.md) provides neutral authenticated graph contracts in core, a mutable DiskANN provider in retrieval and owner-scoped journal, gate and quota support in store. S8 integrates it into normal indexing and request routing at the 1.2 rebuild-only boundary. Production routes use current publication and recovery, with no old-format reader or migration.

The 1.3.0 lexical replacement rationale and tradeoffs are recorded in the [FTS5 decision](index-sharding-review.md#decision-replace-tantivy-with-sqlite-fts5). Database format 126 requires a full rebuild of older Tantivy indexes. Extension indexing detects recognized older formats and requests that rebuild automatically; CLI users request `index --full`. The rebuild keeps the collection ID and saved settings, discards only owned derived state under the writer/request gates, and resumes interrupted deletion from a durable marker.

The [1.2 current-index contract](current-index-runtime.md) is authoritative for production storage, publication and request lifetimes. The v2 publication/history documents describe retired 1.1 implementations; store-level tests retain those primitive contracts, but the kernel does not use them as compatibility readers.

## Current indexing and retrieval

Opt-in native service workers now open the fresh format-140 `collections-1.4` namespace with [WAL publication, durable sidecar admission and request-held object leases](service-publication.md). Ordinary updates permit committed reads during preparation/replay; physical FTS verification follows the request's SQL snapshot. The default 1.3.x collection path described below remains separate until client cutover. Owned sibling replacement, incarnation manifests, request handoff and bounded retirement are implemented; installed-platform qualification and console maintenance integration remain pending.

Each canonical owner root and collection selects an isolated current store. Explicit additional roots retain their citation aliases in authenticated applied configuration. Scanning uses shared discovery/source/extraction budgets, hashes saved sources and selects a complete extraction profile before reuse. Bounded workers perform pure extraction on captured inputs. The coordinator binds path-free payloads and retains source/extraction objects. Full reindexing bypasses extraction reuse.

The 1.3.0 scoped-update path hashes only admitted hinted files and retains other committed bindings. It applies ordinary ignores, protected reads, extraction policy and merged-corpus budgets. Missing exact hinted paths can be retired after reconciliation; directory/global-policy hints, changed applied configuration and incomplete discovery require a complete scan. Durable queue hint revisions preserve concurrent events and overflow promotes to full reconciliation. Complete periodic reconciliation remains authoritative for unhinted changes. Discovery prioritizes documentation/instructions and manifests; semantic selection also favors recent durable hints, without excluding lower-priority evidence.

Search Only (`essential`), Agent Lean (`agent_lean`), Rich Structure (`balanced`) and Detailed extraction remain separate from semantic vector inputs. New collections default to Agent Lean from 1.2.3; existing collections retain saved or published detail. Native structured queries disclose deliberate omissions. Imported producer assertions keep explicit source/build/provenance binding and conservative invalidation. Original document locations, mapped source coordinates, partial extraction and read byte limits remain part of every evidence contract.

The current SQLite map authenticates scoped artifact, continuity, posting, model/resource and graph bindings. DiskANN remains the selected disk-backed vector engine. Indexing applies only changed artifact/posting/lexical/graph records unless a policy or model rebuild requires broader replacement. FTS5 changes affected path documents inside the current SQLite database. Preparation applies captured changes in an admitted transaction, flushes and seals the FTS5 shadow rows, then rolls back. Prepared retains only bounded captured metadata. Applying repeats the captured updates and verifies the sealed digest before committing lexical, map, graph and head rows atomically. This does incremental work twice to preserve an exact predeclared target without copying the complete index; performance remains to be measured. Empty-policy transactions and no-op scans have explicit semantics. Scheduled indexing first commits lexical and fact evidence with incompatible vectors retired, then commits bounded semantic batches with a source-bound pending manifest. Each batch uses the same current publication journal and advances the exact revision.

The store owns a bounded process cache of physically verified lexical snapshots keyed by database path and lexical commit, guarded by file identity/change witnesses and a SQLite change counter (plus local-volume directory notifications on Windows and inode notifications on supported local Linux filesystems). It retains no request gates or read transactions, expires after thirty seconds and releases observers before destructive storage operations. Committed replay seeds the next publication base; diagnostics bypass the cache. This changes the previous per-request physical hashing contract and has [explicit silent-corruption and platform limits](indexing-follow-up-2026-10-21.md#lexical-cache-integrity-contract).

From 1.3.0, progressive source batches do not run semantic inference inline; the existing scheduler drains the durable semantic queue after source discovery. The first source batch targets 32 changed files or two seconds of scan time. Later count targets double up to 4,096 files, with the existing 64 MiB source-byte trigger; the scan interval adapts to four times the preceding publication duration, bounded to 2-30 seconds. Publication time itself is additional. The scheduler owns automatic retries, pause and failure blocking; reads disclose committed semantic coverage without launching work.

From 1.3.2, initialized empty indexes also use progressive source batches, including empty full rebuilds and first-use model/detail changes. Already published batches retain their graph bindings at final publication instead of being rewritten. Empty scans close discovery explicitly and repeated complete empty scans remain no-ops. Populated full or configuration-changing rebuilds retain their atomic replacement boundary; recovery still uses captured journal inputs. See the [1.3.2 validation and limits](release-1.3.2.md).

A durable Prepared/Applying journal and multiprocess request gate coordinate all components. Each read holds a shared gate through materialization; Applying and cleanup require exclusion. Prepared keeps the base readable. Interrupted Applying is unavailable until captured replay finishes. Startup recovery uses retained inputs, never changed live sources. Exact tokens and cursors expire when the current head changes; idle kernels do not retain old generations.

Search verifies current candidates against authenticated source/extraction identities and graph records. Lexical, vector and hybrid search share one request head. Scoped semantic search ranks a bounded authenticated graph subset. Conditional reads bind representations and original locations; current file/unit handles support conservative continuity. Historical search, change history, checkpoints and rollback are unsupported. Native syntax targets remain candidates, and imported resolution remains a producer assertion.

During a scan, the collection writer also owns captured objects that are not yet in the current head, and prior objects still needed for reuse. From 1.2.3, an in-process capture guard defers object reclamation across intermediate base and semantic publications. The guard is released after scan reconciliation, before the final publication performs normal bounded cleanup. The exclusive collection writer prevents another process from reclaiming these inputs. On failure or process exit, committed/journal ownership remains authoritative; unused captures can be reclaimed on a later maintenance pass. Quota admission remains in force throughout the scan.

From 1.2.4, missing retained inputs encountered during reuse cause re-extraction from the scanner's newly captured, hashed source bytes. A typed missing-object failure during indexing can trigger one fresh scan only after the failed attempt releases its writer and the current store proves Ready without a pending journal. Corruption, permission failures and interrupted-journal inputs do not use this repair path. Read-only retained-input diagnostics hold the current read gate, authenticate bounded catalog pages and expire continuation when the publication changes; they never consult live source files or initiate recovery.

When a changed or deleted file's prior extraction is missing, publication can retire its old posting memberships through a complete, bounded traversal of the authenticated committed map. The writer verifies posting encoding and collection-scoped identity, then removes only that path from the staged afterimages. A changed file receives freshly captured evidence under its new hash; a deleted file's missing payload is not recreated. Traversal exhaustion, corrupt proofs and permission failures remain explicit errors. Prepared/Applying journals still require their captured inputs and never substitute changed live sources.

All missing prior paths in one publication share that traversal. Healthy changes retain their normal incremental path; deferred memberships are applied only after the complete base traversal and required memberships verify. The authenticated key must match the scoped Posting domain before a value is decoded as a posting. Other domains may reuse JSON field names without being interpreted as postings. Deferred paths and memberships have separate count and byte ceilings.

## Scheduling, cleanup and scale

The 1.3.0 extension drives bounded native semantic drains for active trusted collections after indexing and on reopen. A call reuses one model for up to eight 32-file batches with a 60 s soft budget checked between commits. These calls share the selected collection’s scheduler worker lock and native pause/failure policy without selecting another collection's jobs. New source work or pause for that collection causes a yield between batches. Foreign source work does not interrupt its semantic drain. Capture guards defer ownership sweeps until the drain boundary; quota grants and byte authentication still apply per publication. The editor rotates ready collections without a fixed successful-drain sleep and uses returned readiness and timings; no service installation is required. The root-wide scheduler retains one semantic batch per worker turn.

From 1.3.1, the native scheduler uses one OS worker lock per collection, allowing distinct projects in the same data root to run concurrently within the existing four execution slots and CPU/memory budgets. Editor source joins advance only the selected collection; root-wide CLI workers skip held collections. Source scans, semantic batches and periodic reconciliation share the collection worker. Crash recovery clears only that locked collection’s running claim. Execution admission precedes retained model parsing, and loading and inference share one lease; synchronous source indexing reuses its original lease through semantic completion. Queue transitions and quota reservations remain short shared transactions; collection deletion locks its own worker, while relocation retains root-wide lifecycle exclusion. A shared lease on the former global worker lock excludes older helpers, which require exclusive ownership; an active older worker produces a restart instruction. Revisions, pause, explicit requests and blocked failures remain in the 1.2 queue namespace. Coverage remains an independent observation of saved source files. A bounded scheduler join returns a typed pending revision; adapters resume that same request without enqueueing or clearing state. The extension manages collection-scoped controls and coalesced requests; it neither implements indexing nor claims live editor buffers are indexed.

The extension rechecks pending work and deadlines when its timer fires. An early callback reschedules rather than dispatching unrequested semantic work. This preserves source requests, semantic retry intervals, pause and storage-selection holds independently of wall-clock timing.

Quota-admitted database growth reserves the larger SQLite bound and rollback allowance before publication. Postcommit cleanup proves current ownership before removing bounded unreferenced objects. `collections maintain` repeats cleanup without publishing. Active requests block destructive collection operations; idle connections do not. Fresh 1.2 collection/settings ownership isolates old indexes rather than migrating them. See [collections](collections.md), [recovery](operations.md#recovery) and [quota limits](storage-quotas.md).

Failed preparation retains its durable allowance until rollback/recovery is proven. Ready recovery and component preparation retire orphan allowances only under the writer and exclusive request gates with no pending journal; all candidate incarnations must validate before release. Windows writer admission separately checks for SQLite's silent read-only fallback and permits bounded reopening only for verified sharing denial. These paths preserve pending-journal capacity and never change source or filesystem permissions.

Changed-component counters measure localized publication work. Scanning, manifest verification and complete ownership checks still grow with corpus size. Large batches have explicit admission limits; no constant total update latency, complete language understanding, power-loss durability or cross-platform qualification is implied.

The 1.4.0 development MCP adapter now defaults to [terse responses](mcp-response-modes.md), with explicit Full overrides and a trusted panel preference. It keeps response observation memory per client, including across direct-worker connection renewal, while sharing native work admission. Evidence retains exact revision identity, read validators and original citations; display policy does not add agent reasoning to the kernel.

## Local usage and reporting boundary

[Local usage reporting](usage-reporting.md) uses core contracts, a bounded transactional store ledger and kernel estimation/report services. CLI/MCP serialization hooks record one observation per outer request. Aggregate counters are the default, scoped by collection/root binding without query/source content or external telemetry; diagnostic events require opt-in. The CLI exports JSON/CSV/Markdown and the extension displays the selected collection's report. Signed context estimates identify their baseline and response framing. Historical recording loss, provider consumption and billed savings remain unobserved; nonempty reports are labeled partial.

Version 1.1.3 adds one bounded cumulative native aggregate in the usage ledger, atomically updated with daily recording and cleared under the same lifecycle lock. Explicit session imports can associate bounded retained request IDs without retaining session names or query content. The extension renders those native reports and supplies guarded report controls. Content-free client-counter conversion and matched-task evaluation live in contributor scripts outside the kernel; no agent execution or external service is introduced. See [usage evaluation](usage-evaluation.md).

Version 1.1.4 stores per-source full-context JSON byte counts in each new immutable catalog. The `source-context-1` retrieval specification binds the additional rows to a distinct publication identity. Counts include nested MCP escaping and are reused only for unchanged sources from an authenticated previous catalog. Usage comparisons lease the exact response revision and read bounded size rows, retaining the existing component-integrity checks. Obsolete catalogs require rebuilding; absent or mismatched sources/revisions and limit failures become fixed reason counters, never live-source substitutions or fabricated savings. Conditional replies without an evidence payload are excluded from comparison.


The opt-in native 1.4 worker binds its data root to the canonical control directory and durable service registry namespace before collection access. Store owns bounded receipt validation, serialized first claims and quota-admitted persistence. The global registry performs metadata-only conflict checks; it does not open project evidence. CLI workers retain that authority and recheck it before queries/jobs. The legacy quota ignores the exact new service receipt/partial/lock names. Final extension/CLI/container cutover remains pending.

The Unix service worker installs a CLI-owned provider guardian adapter through neutral process traits. The existing main executable supplies the actual provider parent; source/result pipes remain direct to the worker. Store owns bounded durable drain metadata, kernel owns retained resource admission, and CLI owns socket descriptor transfer, native boot/process-scope evidence and recovery observations. No service dependency enters the process or ingestion crates. See [provider lifetime](service-provider-lifetime.md).

The development [service console](service-console.md) keeps lifecycle request/phase contracts in core and bounded receipts/explicit-stop policy in the service store. CLI owns approved selection, native instance/OS-manager verification and drain/start effects. The trusted extension host persists exact prepared intents, validates fixed view actions and renders observations/guarded repair previews; it does not open indexes or schedule work itself. Read-only MCP retains direct worker evidence and bounded pre-query brokerage retry. Default adapter cutover remains a separate implementation gate.

Guarded project configuration now supports trusted vectors/detail/selection, source-root, offline-model and usage/calibration choices. Exact settings guards, complete persisted requests and bounded reserved results preserve request identity across recovery; unknown effects require reinspection. See [the configuration contract](service-configuration.md). Default adapters and final platform/editor qualification remain open.

Approved vector repair now regenerates completed retained evidence through bounded service turns, with forced inference, durable per-job progress, atomic citation/node replacement and explicit semantic coverage. See [vector regeneration](service-vector-regeneration.md). Default adapter cutover and final platform/editor qualification remain open.

The trusted console now [reviews runtime upgrades and rollback](service-runtime-transitions.md), fences the captured selection natively and resumes exact saved activations. Different-version pins remain installed with read-only diagnostics; reconnect does not silently replace them. Installer/lifecycle inspection no longer migrates the registry. Default adapters and final platform/editor qualification remain open.

The CLI/native adapter owns [reviewed project registration](service-project-setup.md), canonical planned paths and reserved storage creation; the registry owns serialized source/private-state isolation. Extension bindings select the installed launcher and direct brokered MCP frontend without opening a local Kernel.

The AIRK Explorer Assistance MCP server is extension-owned JavaScript, separate from the 16 read-only retrieval tools. For external agents the CLI contributes only a hidden [descriptor-checked stdio forwarder](service-installation.md) (`explorer-assistance --descriptor`); it depends on no service, store, kernel or MCP crate and never opens AIRK state. Assistance holds help and inert drafts; it does not retrieve evidence or run management actions.

The CLI owns the bounded [client request journal and direct frontend adapter](service-client-adapters.md). Metadata is saved under the already source-isolated control root, while retrieval uses the shared direct-project client. The extension activation delegates watching/indexing to native ownership and retains reviewed opaque workspace selections.

Native startup gates source coordination on completion of the metadata owner’s first registry bootstrap attempt. CLI owns this sequencing and its cached failure observations; no new dependency or source access enters core/store. A failed bootstrap still permits independent service health, and dropping an unreleased source coordinator does not initialize registry state.
