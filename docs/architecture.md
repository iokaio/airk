# Architecture

AIRK is an independent local indexing/retrieval kernel. Source workspaces are authoritative; all index state is derived. It does not reason, generate answers, manage agents, route model calls or require an external database.

The [October 17 release summary](releases-2026-10-17.md) covers the 1.1.0–1.1.2 changes and upgrade behavior. This page describes the resulting component boundaries; release publication and workload qualification are recorded separately.

~~~mermaid
flowchart LR
  W[Workspace files] --> I[Native ingestion and format facts]
  I --> K[Collection-scoped kernel]
  K --> S[Collection disk state]
  S --> R[SQLite FTS5 lexical and authenticated fact retrieval]
  V[Default local embeddings and disk-backed DiskANN] --> R
  C[CLI or optional extension] --> K
  A[Coding agent] --> M[Read-only stdio MCP]
  M --> K
  R --> K
  K --> E[Bounded evidence and original locations]
~~~

## Dependency boundaries

| Crate | Responsibility | AIRK dependencies |
|---|---|---|
| airk-core | Artifact/query/fact/citation contracts; storage and embedding traits | None |
| airk-ingest | Ignore-aware discovery, hashing, native grammars, document extraction/chunking | core |
| airk-store | Content-addressed sources/extractions, authenticated SQLite catalogs/FTS5/postings/graph records, usage ledgers, durable intents, locks, quotas, relocation and current-object cleanup | core |
| airk-retrieval | Local word-vector/ONNX inference, mutable DiskANN algorithms and retrieval primitives | core |
| airk-kernel | Collection-scoped publication, retrieval/rank fusion, response budgets, coverage, scheduling, usage and maintenance services | core, ingest, store, retrieval |
| airk-mcp | Schemas, official SDK transport and result conversion | core, kernel |
| airk-cli | Commands, native client setup and lifecycle | core, kernel, mcp |

Core must remain free of parser, filesystem, inference and transport implementations. Adapters call kernel services rather than bypassing validation or collection scope. MemoryStore is an available in-memory snapshot adapter; the CLI kernel uses FileStore with current SQLite FTS5/DiskANN storage.

The CLI adapter embeds the pinned FP32 model assets after explicit build preparation and build-time catalog/digest verification. Its offline `collections vectors install-bundled` write command stages bounded local bytes and calls the kernel's quota-reserved installer; no read or MCP request performs installation. The native input-model installation lock serializes atomic publication across collections, preserves existing custom inputs and rejects incomplete inputs. Extension setup compares the bundled manifest with the helper catalog and invokes that command without a network fallback. Model/pipeline identity and platform-specific batching remain unchanged.

The retrieval crate owns native CPU feature observations and the embedded qualified model catalog. Kernel exposes this read-only service to `airk model-catalog` before any collection is opened. Extension setup uses its selected profile's pinned manifest/assets; the Python provisioning script reads the same source catalog. Capability observations do not open model plans, alter embedding identity or establish that a particular backend kernel is selected. The only automatic profile remains FP32 MiniLM; INT8 qualification and automatic selection are future work.

The [single-current-index foundation](current-index-foundation.md) provides neutral authenticated graph contracts in core, a mutable DiskANN provider in retrieval and owner-scoped journal, gate and quota support in store. S8 integrates it into normal indexing and request routing at the 1.2 rebuild-only boundary. Production routes use current publication and recovery, with no old-format reader or migration.

The 1.3.0 lexical replacement rationale and tradeoffs are recorded in the [FTS5 decision](index-sharding-review.md#decision-replace-tantivy-with-sqlite-fts5). Database format 126 requires a full rebuild of older Tantivy indexes. Extension indexing detects recognized older formats and requests that rebuild automatically; CLI users request `index --full`. The rebuild keeps the collection ID and saved settings, discards only owned derived state under the writer/request gates, and resumes interrupted deletion from a durable marker.

The [1.2 current-index contract](current-index-runtime.md) is authoritative for production storage, publication and request lifetimes. The v2 publication/history documents describe retired 1.1 implementations; store-level tests retain those primitive contracts, but the kernel does not use them as compatibility readers.

## Current indexing and retrieval

Each canonical owner root and collection selects an isolated current store. Explicit additional roots retain their citation aliases in authenticated applied configuration. Scanning uses shared discovery/source/extraction budgets, hashes saved sources and selects a complete extraction profile before reuse. Bounded workers perform pure extraction on captured inputs. The coordinator binds path-free payloads and retains source/extraction objects. Full reindexing bypasses extraction reuse.

The 1.3.0 scoped-update path hashes only admitted hinted files and retains other committed bindings. It applies ordinary ignores, protected reads, extraction policy and merged-corpus budgets. Missing exact hinted paths can be retired after reconciliation; directory/global-policy hints, changed applied configuration and incomplete discovery require a complete scan. Durable queue hint revisions preserve concurrent events and overflow promotes to full reconciliation. Complete periodic reconciliation remains authoritative for unhinted changes. Discovery prioritizes documentation/instructions and manifests; semantic selection also favors recent durable hints, without excluding lower-priority evidence.

Search Only (`essential`), Agent Lean (`agent_lean`), Rich Structure (`balanced`) and Detailed extraction remain separate from semantic vector inputs. New collections default to Agent Lean from 1.2.3; existing collections retain saved or published detail. Native structured queries disclose deliberate omissions. Imported producer assertions keep explicit source/build/provenance binding and conservative invalidation. Original document locations, mapped source coordinates, partial extraction and read byte limits remain part of every evidence contract.

The current SQLite map authenticates scoped artifact, continuity, posting, model/resource and graph bindings. DiskANN remains the selected disk-backed vector engine. Indexing applies only changed artifact/posting/lexical/graph records unless a policy or model rebuild requires broader replacement. FTS5 changes affected path documents inside the current SQLite database. Preparation applies captured changes in an admitted transaction, flushes and seals the FTS5 shadow rows, then rolls back. Prepared retains only bounded captured metadata. Applying repeats the captured updates and verifies the sealed digest before committing lexical, map, graph and head rows atomically. This does incremental work twice to preserve an exact predeclared target without copying the complete index; performance remains to be measured. Empty-policy transactions and no-op scans have explicit semantics. Scheduled indexing first commits lexical and fact evidence with incompatible vectors retired, then commits bounded semantic batches with a source-bound pending manifest. Each batch uses the same current publication journal and advances the exact revision.

The store owns a bounded process cache of physically verified lexical snapshots keyed by database path and lexical commit, guarded by file identity/change witnesses and a SQLite change counter (plus local-volume directory notifications on Windows and inode notifications on supported local Linux filesystems). It retains no request gates or read transactions, expires after thirty seconds and releases observers before destructive storage operations. Committed replay seeds the next publication base; diagnostics bypass the cache. This changes the previous per-request physical hashing contract and has [explicit silent-corruption and platform limits](indexing-follow-up-2026-10-21.md#lexical-cache-integrity-contract).

From 1.3.0, progressive source batches do not run semantic inference inline; the existing scheduler drains the durable semantic queue after source discovery. The first source batch targets 32 changed files or two seconds of scan time. Later count targets double up to 4,096 files, with the existing 64 MiB source-byte trigger; the scan interval adapts to four times the preceding publication duration, bounded to 2-30 seconds. Publication time itself is additional. The scheduler owns automatic retries, pause and failure blocking; reads disclose committed semantic coverage without launching work.

A durable Prepared/Applying journal and multiprocess request gate coordinate all components. Each read holds a shared gate through materialization; Applying and cleanup require exclusion. Prepared keeps the base readable. Interrupted Applying is unavailable until captured replay finishes. Startup recovery uses retained inputs, never changed live sources. Exact tokens and cursors expire when the current head changes; idle kernels do not retain old generations.

Search verifies current candidates against authenticated source/extraction identities and graph records. Lexical, vector and hybrid search share one request head. Scoped semantic search ranks a bounded authenticated graph subset. Conditional reads bind representations and original locations; current file/unit handles support conservative continuity. Historical search, change history, checkpoints and rollback are unsupported. Native syntax targets remain candidates, and imported resolution remains a producer assertion.

During a scan, the collection writer also owns captured objects that are not yet in the current head, and prior objects still needed for reuse. From 1.2.3, an in-process capture guard defers object reclamation across intermediate base and semantic publications. The guard is released after scan reconciliation, before the final publication performs normal bounded cleanup. The exclusive collection writer prevents another process from reclaiming these inputs. On failure or process exit, committed/journal ownership remains authoritative; unused captures can be reclaimed on a later maintenance pass. Quota admission remains in force throughout the scan.

From 1.2.4, missing retained inputs encountered during reuse cause re-extraction from the scanner's newly captured, hashed source bytes. A typed missing-object failure during indexing can trigger one fresh scan only after the failed attempt releases its writer and the current store proves Ready without a pending journal. Corruption, permission failures and interrupted-journal inputs do not use this repair path. Read-only retained-input diagnostics hold the current read gate, authenticate bounded catalog pages and expire continuation when the publication changes; they never consult live source files or initiate recovery.

When a changed or deleted file's prior extraction is missing, publication can retire its old posting memberships through a complete, bounded traversal of the authenticated committed map. The writer verifies posting encoding and collection-scoped identity, then removes only that path from the staged afterimages. A changed file receives freshly captured evidence under its new hash; a deleted file's missing payload is not recreated. Traversal exhaustion, corrupt proofs and permission failures remain explicit errors. Prepared/Applying journals still require their captured inputs and never substitute changed live sources.

All missing prior paths in one publication share that traversal. Healthy changes retain their normal incremental path; deferred memberships are applied only after the complete base traversal and required memberships verify. The authenticated key must match the scoped Posting domain before a value is decoded as a posting. Other domains may reuse JSON field names without being interpreted as postings. Deferred paths and memberships have separate count and byte ceilings.

## Scheduling, cleanup and scale

The 1.3.0 extension drives bounded native semantic drains for active trusted collections after indexing and on reopen. A call reuses one model for up to eight 32-file batches with a 60 s soft budget checked between commits. These calls share the selected collection’s scheduler worker lock and native pause/failure policy without selecting another collection's jobs. New source work or pause for that collection causes a yield between batches. Foreign source work does not interrupt its semantic drain. Capture guards defer ownership sweeps until the drain boundary; quota grants and byte authentication still apply per publication. The editor rotates ready collections without a fixed successful-drain sleep and uses returned readiness and timings; no service installation is required. The root-wide scheduler retains one semantic batch per worker turn.

From 1.3.1, the native scheduler uses one OS worker lock per collection, allowing distinct projects in the same data root to run concurrently within the existing four execution slots and CPU/memory budgets. Editor source joins advance only the selected collection; root-wide CLI workers skip held collections. Source scans, semantic batches and periodic reconciliation share the collection worker. Crash recovery clears only that locked collection’s running claim. Execution admission precedes retained model parsing, and loading and inference share one lease; synchronous source indexing reuses its original lease through semantic completion. Queue transitions and quota reservations remain short shared transactions; collection deletion locks its own worker, while relocation retains root-wide lifecycle exclusion. A shared lease on the former global worker lock excludes older helpers, which require exclusive ownership; an active older worker produces a restart instruction. Revisions, pause, explicit requests and blocked failures remain in the 1.2 queue namespace. Coverage remains an independent observation of saved source files. A bounded scheduler join returns a typed pending revision; adapters resume that same request without enqueueing or clearing state. The extension manages collection-scoped controls and coalesced requests; it neither implements indexing nor claims live editor buffers are indexed.

The extension rechecks pending work and deadlines when its timer fires. An early callback reschedules rather than dispatching unrequested semantic work. This preserves source requests, semantic retry intervals, pause and storage-selection holds independently of wall-clock timing.

Quota-admitted database growth reserves the larger SQLite bound and rollback allowance before publication. Postcommit cleanup proves current ownership before removing bounded unreferenced objects. `collections maintain` repeats cleanup without publishing. Active requests block destructive collection operations; idle connections do not. Fresh 1.2 collection/settings ownership isolates old indexes rather than migrating them. See [collections](collections.md), [recovery](operations.md#recovery) and [quota limits](storage-quotas.md).

Failed preparation retains its durable allowance until rollback/recovery is proven. Ready recovery and component preparation retire orphan allowances only under the writer and exclusive request gates with no pending journal; all candidate incarnations must validate before release. Windows writer admission separately checks for SQLite's silent read-only fallback and permits bounded reopening only for verified sharing denial. These paths preserve pending-journal capacity and never change source or filesystem permissions.

Changed-component counters measure localized publication work. Scanning, manifest verification and complete ownership checks still grow with corpus size. Large batches have explicit admission limits; no constant total update latency, complete language understanding, power-loss durability or cross-platform qualification is implied.

## Local usage and reporting boundary

[Local usage reporting](usage-reporting.md) uses core contracts, a bounded transactional store ledger and kernel estimation/report services. CLI/MCP serialization hooks record one observation per outer request. Aggregate counters are the default, scoped by collection/root binding without query/source content or external telemetry; diagnostic events require opt-in. The CLI exports JSON/CSV/Markdown and the extension displays the selected collection's report. Signed context estimates identify their baseline and response framing. Historical recording loss, provider consumption and billed savings remain unobserved; nonempty reports are labeled partial.

Version 1.1.3 adds one bounded cumulative native aggregate in the usage ledger, atomically updated with daily recording and cleared under the same lifecycle lock. Explicit session imports can associate bounded retained request IDs without retaining session names or query content. The extension renders those native reports and supplies guarded report controls. Content-free client-counter conversion and matched-task evaluation live in contributor scripts outside the kernel; no agent execution or external service is introduced. See [usage evaluation](usage-evaluation.md).

Version 1.1.4 stores per-source full-context JSON byte counts in each new immutable catalog. The `source-context-1` retrieval specification binds the additional rows to a distinct publication identity. Counts include nested MCP escaping and are reused only for unchanged sources from an authenticated previous catalog. Usage comparisons lease the exact response revision and read bounded size rows, retaining the existing component-integrity checks. Obsolete catalogs require rebuilding; absent or mismatched sources/revisions and limit failures become fixed reason counters, never live-source substitutions or fabricated savings. Conditional replies without an evidence payload are excluded from comparison.
